## 2. 缺陷成因（源码层）

### 2.1 缺陷核心：信任根无完整性保护

```csharp
// ★ DEFECT-01：公钥硬编码于只读数据段，且无任何完整性校验
private static readonly byte[] EmbeddedPublicKey = new byte[]
{
    0x30, 0x59, 0x30, 0x13, 0x06, 0x07, 0x2A, 0x86, ...
};

// ★ DEFECT-02：单点引用 —— 只有一处读这个公钥
public static bool Verify(byte[] msg, byte[] sig)
{
    return VerifySignature(msg, sig);       // 内部直接用 EmbeddedPublicKey
}
```

### 2.2 关键认知：非对称体系有两个前提

```
非对称体系（Ed25519 / ECDSA / RSA）的安全依赖两个前提：

  ① 私钥不可得          ← 服务端保管，✅ 通常满足
  ② 客户端公钥未被篡改   ← ❌ 常被完全忽略！
```

**攻击者不需要破解签名算法**，只需要：

```
1. 生成自己的密钥对
2. 用自己的私钥签发凭据
3. 把客户端里的公钥【原位置换】成自己的公钥
4. 自签凭据 → 验签通过 → 格式完全合法
```

> ### 🔑 核心教训
> **非对称签名 ≠ 绝对安全。**
> 前提是「**公钥本身不可被替换**」。
> 公钥是公开信息（泄露无害），但它的**完整性**必须被保护。

### 2.3 修复方案：多点交叉校验

```csharp
// ✅ 编译期计算公钥指纹
private static readonly byte[] PublicKeyFingerprint =
    Take(ComputeSha256(EmbeddedPublicKey), 16);

// ✅ 在多个不相关位置比对
private static bool VerifyPublicKeyIntegrity(string from)
{
    byte[] actual = ComputeSha256(EmbeddedPublicKey);
    for (int i = 0; i < PublicKeyFingerprint.Length; i++)
        if (actual[i] != PublicKeyFingerprint[i]) return false;
    return true;
}

public static bool VerifyWithCheck1(byte[] m, byte[] s)   // 验签入口
{ if (!VerifyPublicKeyIntegrity("Check1")) return false; return VerifySignature(m, s); }

public static bool VerifyWithCheck2(byte[] m, byte[] s)   // 启动自检
{ if (!VerifyPublicKeyIntegrity("Check2")) return false; return VerifySignature(m, s); }

public static bool VerifyWithCheck3(byte[] m, byte[] s)   // 关键功能前
{ if (!VerifyPublicKeyIntegrity("Check3")) return false; return VerifySignature(m, s); }
```

**为什么多点有效**：攻击者必须**同时**替换全部引用点才能绕过 —— 成本从 O(1) 变为 O(N)。

## 3. 二进制分析（参考构建）

### 3.1 公钥字节序列

公钥常量以**连续字节序列**形式存在于 PE 的只读数据区：

```
30 59 30 13 06 07 2A 86 48 CE 3D 02 01 06 08 2A
86 48 CE 3D 03 01 07 03 42 00 04 11 22 33 44 55
66 77 88 99 AA BB CC DD EE FF 00 11 22 33 44 55
...
```

**特征识别**：以 `30 59`（ASN.1 SEQUENCE）或 `30 2A` 开头，
以 `03 42 00 04`（BIT STRING + 未压缩点标志）为特征 —— 这是 **ECDSA/Ed25519 公钥的标准 DER 编码**。

> 💡 **通用识别技巧**：在二进制中搜索 `03 42 00 04` 或 `03 21 00`，
> 这类字节模式是**非对称公钥的强特征**，可快速定位信任根。

### 3.2 指纹常量偏移

| 常量 | 说明 | 定位方法 |
|:---|:---|:---|
| `EmbeddedPublicKey` | 公钥（43 字节） | 搜索 `30 59 30 13 06 07 2A 86` |
| `PublicKeyFingerprint` | 公钥 SHA256 前 16 字节 | 搜索公钥哈希的前 8 字节 |

## 4. 完整点位表 ★

> 下表针对**参考构建**。

| # | 目标 | 位置 | 原始内容 | 修补思路 | 效果 | 是否被拦截 |
|---:|:---|:---|:---|:---|:---|:---:|
| **P1** | 公钥常量 | 数据段连续字节 | `30 59 30 13 06 07 2A 86 ...` | 替换为攻击者自签公钥 | 自签凭据可通过验签 | ❌ **被指纹校验拦截** |
| **P2** | 公钥指纹 | 指纹常量 | 原公钥哈希前 16 字节 | 同步替换为攻击者公钥哈希 | 绕过 P1 的拦截 | ❌ **被 Check1 拦截** |
| **P3** | 指纹校验点 ×3 | `VerifyPublicKeyIntegrity` 的 3 处调用 | `call` 校验方法 | 需**同时**改 3 处 | 彻底绕过 | ⚠️ 成本 ×3 |
| **P4** | 验签方法 | `VerifySignature` | 返回验签结果 | 改写为恒返回 true | 所有签名都"通过" | ⚠️ 需定位方法体 |

### 4.1 三点对比实验 ★ 核心教学点

| 改法 | 改几处 | 结果 | 教学结论 |
|:---|:---:|:---|:---|
| **只改 P1**（公钥） | 1 处 | 🔴 **失败** —— 指纹校验拦截 | 完整性校验生效 |
| **改 P1 + P2**（公钥+指纹） | 2 处 | 🔴 **失败** —— 3 个校验点之一命中 | 多点交叉校验生效 |
| **改 P1 + P2 + P3** | **2 + 3 = 5 处** | 🟡 绕过 | 成本从 1 处升至 5 处 |
| **改 P4**（验签方法体） | 1 处 | 🟡 绕过 | ★ 攻击**判定函数本身**更省力 |

> ### 🔑 核心结论
> **防御的本质是提高攻击成本。**
> * 无校验：攻击成本 = **1 处修改**
> * 单点指纹校验：攻击成本 = **2 处修改**
> * 三点交叉校验：攻击成本 = **5 处修改**
> * 叠加二进制自校验：攻击成本 = **下一层防御**（需先破坏完整性校验）
>
> **但 P4 暴露了另一个问题**：无论加多少层校验，
> 只要**最终裁决仍在客户端**，攻击者总可以选择**改判定函数本身**。
> **这就是为什么架构修正（服务端权威）不可被替代。**

### 5.3 定位校验点数量（判断是否为多点交叉）

```
1. 用 dnSpy 打开，找到 VerifyPublicKeyIntegrity 方法
2. 右键 → "分析" → "被引用处"（Find Usages）
3. 统计引用次数 N

```

### 对照要点

| 靶场演示的 | 真实产品中的对应 |
|:---|:---|
| 公钥可被原位置换 | Snipaste PRO 的 Ed25519 公钥替换 |
| 单点引用 vs 多点交叉 | Snipaste PRO 公钥未被多点引用 |
| 对称密钥内置（概念对照） | Allen Explorer / BoosterX 的对称密钥缺陷 |
| 指纹校验作为防线 | Snipaste PRO 缺失的正是这一层 |

> **三种形态的区分**（重要）：
> * **公钥可替换** → 非对称体系的**信任根**被绕过（Snipaste）
> * **对称密钥内置** → 客户端**同时持有生成权与验证权**（Allen / BoosterX）
> * 前者"算法正确但保护不完整"，后者"架构方向就错了" —— **修复成本差异巨大**

## 9. 防御加固方案

### 9.1 公钥完整性保护

```csharp
// ✅ 编译期预置指纹
private static readonly byte[] PublicKeyFingerprint = { /* SHA256(pubkey)[0..16] */ };

// ✅ 多点交叉校验（三处以上）
if (!VerifyPublicKeyIntegrity()) return Fail();
if (!Ed25519.Verify(sig, msg, PublicKey)) return Fail();
```

### 9.2 二进制完整性联动

```csharp
// ✅ 运行时校验自身 Authenticode 签名
public static bool VerifySelfIntegrity()
{
    string self = Process.GetCurrentProcess().MainModule.FileName;
    if (!WinVerifyTrust(self)) return false;
    byte[] codeHash = ComputeCodeSectionHash(self);
    return CryptographicOperations.FixedTimeEquals(codeHash, ExpectedCodeHash);
}
// 建议：启动 / 关键操作前 / 定时 三处重复调用
```

### 9.3 加固优先级

```
第一优先（成本最低，收益最高）
  └─ 公钥指纹多点交叉校验（≥3 处）              ← 攻击成本 ×5

第二优先
  └─ 二进制 Authenticode 运行时自校验            ← 提高整体篡改成本

第三优先（架构级）
  ├─ 凭据载荷绑定 设备指纹 + 有效期 + Nonce
  └─ 关键权益由服务端异步二次确认

⚠️ 注意：以上均为「提高成本」，无法根除 ——
   根除需要把裁决权移到服务端（见 Ed25519 方案）。
```
