## 2. 缺陷成因（源码层）

### 2.1 缺陷核心：正确架构 + 薄弱通道

```csharp
// ✅ 架构方向正确：鉴权逻辑独立进程化（提高攻击门槛）
//    鉴权服务进程负责判定，主程序通过 IPC 获取结论

// ★ 缺陷点：IPC 消息无任何完整性保护
public static bool HandlePlaintextResponse(int statusCode)
{
    return statusCode == 3;        // 3 = 已授权
    // ← 只校验数值，不校验来源、不校验完整性、不校验新鲜度
}
```

### 2.2 架构示意

```
┌──────────────────┐   IPC（明文状态码）  ┌──────────────────────┐
│  主程序           │ ←──────────────────→ │  鉴权服务进程          │
│                  │                      │                      │
│ if (code == 3)   │   ★ 攻击点在这条通道   │  （可能使用了          │
│   EnablePro();   │                      │    代码虚拟化强保护）   │
└──────────────────┘                      └──────────────────────┘
         ▲
         │ 攻击者不需要碰那个「强保护」的鉴权服务
         │ 只需在 IPC 通道上伪造一个状态码 3
```

### 2.3 三重缺陷

| # | 缺失的保护 | 后果 |
|---:|:---|:---|
| 1 | **无消息认证（HMAC/签名）** | 消息可被伪造 |
| 2 | **无时戳/序号** | 可重放 |
| 3 | **无对端进程校验** | 可冒充鉴权服务；可抢占通道名 |

### 2.4 值域问题

```
状态码是 int32 → 搜索空间 2^32 ≈ 43 亿

但实际上鉴权状态通常只有 3~5 个含义：
  0 = 未授权
  1 = 试用中
  2 = 已过期
  3 = 已授权    ← 攻击目标
  4 = 已封禁

→ 实际搜索空间 = 5，命中概率极高
```

> ### 🔑 核心教训
> **把逻辑搬到另一个进程 ≠ 安全。**
> **安全强度取决于链路中最薄弱的一环，而非最强的一环。**
>
> 该产品在鉴权内核上投入了商业级虚拟化保护，
> 但**通道零认证**让这些投入完全失效。

## 4. 完整点位表 ★

> ⚠️ **本模式的点位与模式 01/02 形态不同**：
> 它的"点位"是**通道上的消息**，而非文件中的字节。
> 因此点位表分为：**（A）消息级点位**；**（B）代码级点位**。

### 4.1 A 组 · 消息级点位（无需修改二进制）

| # | 目标 | 数据形态 | 原始 | 伪造值 | 效果 |
|---:|:---|:---|:---|:---|:---|
| **P1** | IPC 状态码 | int32 | `0`（未授权） | `3` | 🔴 **主程序认为已授权** |
| **P2** | 共享内存状态位 | DWORD | `0` | `3` | 🔴 同上 |
| **P3** | 管道名抢占 | 字符串 | 由服务端绑定 | 攻击者抢先绑定同名管道 | 🔴 主程序连接到攻击者的管道 |

> ⭐ **本模式最重要的教学点**：
> **攻击者完全不需要逆向鉴权算法**（算法甚至可以是强保护的），
> **攻击点转移到了更薄弱的通信层。**
>
> 这就是"**安全强度取决于最薄弱环节**"的实证。

### 4.2 B 组 · 代码级点位（加固方向）

| # | 加固位置 | 措施 | 效果 |
|---:|:---|:---|:---|
| **G1** | 消息读取后 | 校验 HMAC-SHA256 | 防伪造 |
| **G2** | 消息解析时 | 校验时戳（±5 秒窗口） | 防重放 |
| **G3** | 消息解析时 | 校验单调递增序号 | 防重放 |
| **G4** | 建立连接后 | 校验对端进程路径 + 签名 | 防冒充 |
| **G5** | 创建管道时 | 设置 ACL 限制为当前用户 | 降低接入面 |
| **G6** | 校验失败时 | 拒绝服务（Fail-Closed） | 不降级 |

### 4.3 加固前后对比（靶场内置演示）

| 场景 | 明文版本 | 加固版本 |
|:---|:---|:---|
| 合法消息 | ✅ 通过 | ✅ 通过 |
| 消息被篡改 | 🔴 **通过**（无校验） | 🟢 拒绝（HMAC 不符） |
| 重放攻击 | 🔴 **通过**（无时戳） | 🟢 拒绝（时戳超窗） |
| 序号倒退 | 🔴 **通过** | 🟢 拒绝（序号未递增） |
| 伪造来源 | 🔴 **通过**（不校验对端） | 🟢 拒绝（路径/签名不符） |

## 9. 防御加固方案

### 9.1 消息认证（最高优先级）

```csharp
public static bool TryReadAuthenticatedResponse(NamedPipeServerStream pipe,
                                               out Entitlement result)
{
    result = null;

    // ① 校验对端进程身份（路径 + Authenticode 签名 + PID）
    if (!VerifyPeerProcess(pipe)) return false;

    // ② 读取消息体 + HMAC
    byte[] payload;
    byte[] receivedMac;
    ReadFramed(pipe, out payload, out receivedMac);

    // ③ 校验 HMAC（会话密钥由两进程协商，不落盘）
    byte[] expectedMac = ComputeHmac(_sessionKey, payload);
    if (!FixedTimeEquals(receivedMac, expectedMac)) return false;

    // ④ 校验时戳与单调序号（防重放）
    IpcMessage msg = Deserialize(payload);
    if (!msg.IsFresh(TimeSpan.FromSeconds(5))) return false;
    if (msg.Seq <= _lastSeq) return false;
    _lastSeq = msg.Seq;

    result = msg.Entitlement;
    return true;
}
```

### 9.2 通道访问控制

```csharp
static void SecurePipe(NamedPipeServerStream pipe)
{
    var security = new PipeSecurity();

    // 允许当前用户完全控制
    security.AddAccessRule(new PipeAccessRule(
        WindowsIdentity.GetCurrent().User,
        PipeAccessRights.FullControl,
        AccessControlType.Allow));

    // 显式拒绝其他用户
    security.AddAccessRule(new PipeAccessRule(
        new SecurityIdentifier(WellKnownSidType.WorldSid, null),
        PipeAccessRights.ReadWrite,
        AccessControlType.Deny));

    pipe.SetAccessControl(security);
}
```

### 9.3 对端进程校验

```csharp
static bool VerifyPeerProcess(NamedPipeServerStream pipe)
{
    uint pid;
    if (!GetNamedPipeClientProcessId(pipe.SafePipeHandle, out pid)) return false;

    string path = GetProcessMainModulePath(pid);

    // ① 路径必须在受信任目录内
    if (!IsUnderTrustedDir(path)) return false;

    // ② 必须通过 Authenticode 签名校验
    if (!WinVerifyTrust(path)) return false;

    return true;
}
```

### 9.4 消息帧格式对照

```
❌ 明文帧（当前）
   ┌──────────────┐
   │ 状态码 int32  │  4 字节，无认证
   └──────────────┘

✅ 加固帧
   ┌──────────┬────────┬──────────────┬─────────────────┐
   │ 时戳 i64 │ 序号 i32│ 载荷 bytes    │ HMAC-SHA256 32B │
   │  8 字节  │  4 字节 │  N 字节       │    32 字节       │
   └──────────┴────────┴──────────────┴─────────────────┘
```

### 9.5 加固优先级

```
第一优先（成本低，收益最高）★
  ├─ IPC 消息 HMAC 认证                    ← 防伪造
  ├─ 时戳 + 单调序号                        ← 防重放
  └─ 对端进程校验（路径 + 签名）             ← 防冒充

第二优先
  ├─ 管道 ACL 限制为当前用户                 ← 降低接入面
  └─ 校验失败时 Fail-Closed（不降级）

第三优先（架构级）
  └─ 结果改为服务端签名凭据（而非裸状态码）    ← 提升密码学强度
```
