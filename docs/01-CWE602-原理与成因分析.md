# 01 · CWE-602 原理与成因分析

> 本文从架构视角剖析 CWE-602 的本质，回答一个核心问题：
> **为什么"由客户端裁决自身特权"必然失败？**

---

## 一、 缺陷的正式定义

| 项目 | 内容 |
|:---|:---|
| **CWE 编号** | [CWE-602](https://cwe.mitre.org/data/definitions/602.html) |
| **名称** | Client-Side Enforcement of Server-Side Security |
| **中文** | 客户端强行实施服务端安全机制 |
| **抽象层级** | Class（架构级缺陷类） |
| **典型后果** | 访问控制绕过、授权提升、商业逻辑失效 |

**核心描述**：软件将本应由服务端强制保证的安全策略，交给客户端来执行与裁决。

---

## 二、 威胁模型的根本前提

要理解 CWE-602 为何无法通过"更聪明的代码"修复，必须先接受一个前提：

> ### 🔑 核心公理
> **在客户端运行的任何代码，其运行环境最终都由攻击者掌控。**

这带来三个不可回避的推论：

| 推论 | 含义 |
|:---|:---|
| **推论 1：内存可被改写** | 任何存储在进程内存中的状态标志（`isPro = true`）都可被外部工具修改 |
| **推论 2：代码可被分析** | 任何在客户端执行的判定逻辑，都可被静态反编译或动态调试定位 |
| **推论 3：通信可被伪造** | 任何客户端与服务端之间的数据，都可被拦截、重放或构造 |

**结论**：只要"最终裁决"发生在客户端，攻击者就一定能找到绕过路径。
**这不是工程实现问题，而是架构定位问题。**

---

## 三、 四层审计视角

审计客户端鉴权实现时，建议自顶向下逐层审视。

### L1 · 架构层：谁拥有最终裁决权？

**审计问题清单：**

- [ ] 特权状态的**唯一可信来源**是什么？
- [ ] 该来源是否位于服务端，或由服务端私钥签发的不可伪造凭据？
- [ ] 客户端是否仅仅是"凭据的持有者与呈递者"，而非"凭据的裁决者"？
- [ ] 是否存在"客户端自行决定是否解锁"的代码路径？

**判定标准：**

| 情形 | 判定 |
|:---|:---|
| 客户端本地计算并裁决特权 | 🔴 **CWE-602 高危** |
| 客户端持有服务端签名凭据，仅做**验签** | 🟢 合规 |
| 客户端验签 + 服务端异步二次确认 | 🟢 最佳实践 |

---

### L2 · 密码学层：凭据如何签发与验证？

**审计问题清单：**

- [ ] 凭据的签名是否使用了**标准非对称算法**（Ed25519 / RSA-PSS / ECDSA）？
- [ ] 客户端内置的是**公钥**还是**对称密钥**？
- [ ] 是否存在自研的哈希/编码/校验算法？
- [ ] 凭据是否绑定了**设备指纹 + 有效期 + Nonce**？

**判定标准：**

| 情形 | 判定 |
|:---|:---|
| 客户端内置对称密钥解密凭据 | 🔴 **CWE-321 / CWE-798 高危** |
| 自研多项式哈希 / 查表异或校验 | 🔴 **CWE-327 高危** |
| 客户端仅内置公钥，验签 Ed25519 签名 | 🟢 合规 |

---

### L3 · 运行时层：决策状态存储在哪？

**审计问题清单：**

- [ ] 特权标志是否以**明文可写全局变量**形式存在？
- [ ] 该变量的地址是否可通过符号/字符串轻松定位？
- [ ] 敏感数据在内存中停留多久？用毕是否擦除？
- [ ] 是否存在跨进程传递的、未加保护的授权状态？

**判定标准：**

| 情形 | 判定 |
|:---|:---|
| 全局 `bool is_registered` 明文变量 | 🔴 **高危** |
| 状态加密存储 + 用毕擦除 + 完整性自检 | 🟢 合规 |

---

### L4 · 代码形态层：关键逻辑是否暴露？

**审计问题清单：**

- [ ] 特权判定函数是否为**显式导出符号**（可被工具直接定位）？
- [ ] 判定逻辑是否为**单一条件跳转**（`test` / `jz` 模式）？
- [ ] 是否实施了控制流平坦化或代码虚拟化？
- [ ] 敏感字符串是否明文存在于二进制中？

**判定标准：**

| 情形 | 判定 |
|:---|:---|
| 独立 `IsPro()` 导出函数 + 单点 `if` 判断 | 🔴 **高危** |
| 逻辑内联 + 混淆 + 多点交叉校验 | 🟢 相对安全 |

---

## 四、 常见认知误区

### 误区 1："我把判定函数加密/改名就安全了"

❌ **错误。** 只要判定逻辑在客户端执行，攻击者可以通过动态调试
在**运行时**直接观察判定结果，无需理解你的加密方案。

### 误区 2："我用虚拟机保护（VMP）就够了"

⚠️ **部分有效，但不充分。** VMP 提高了分析成本，但：
- 判定**结果**依然需要在内存中体现；
- 攻击者可以绕过"判定"，直接**patch 判定之后的分支**；
- VMP 只能延缓，不能消除架构缺陷。

### 误区 3："客户端反正会被破解，做防御没意义"

❌ **错误。** 防御的目标不是"绝对不可破"，而是**把攻击成本提高到不经济**：

| 防御强度 | 攻击者所需投入 |
|:---|:---|
| 无防御 | 几分钟 |
| 基础混淆 | 数小时 |
| VMP + 完整性自检 | 数天 ~ 数周 |
| **服务端权威 + 非对称签名** | **架构上不可行** |

**只有把裁决权移到服务端，才能从架构上根除这类缺陷。**

## 五、 从缺陷到加固：决策树

```
                     客户端是否需要裁决特权？
                              │
              ┌───────────────┴───────────────┐
              │                               │
         【必须离线】                    【可联网】
              │                               │
              ▼                               ▼
    使用非对称签名离线许可证            使用服务端在线校验
    ├─ 服务端私钥签发                  ├─ 短时效 Token
    ├─ 客户端仅验签                    ├─ 服务端权威裁决
    ├─ 绑定设备指纹                    ├─ 双向 mTLS
    └─ 附带有效期 + Nonce              └─ 关键操作二次验签
              │                               │
              └───────────────┬───────────────┘
                              ▼
                    叠加运行时防护层
                    ├─ 二进制完整性自检
                    ├─ 反调试 / 反注入
                    └─ 关键逻辑混淆与内联
```
