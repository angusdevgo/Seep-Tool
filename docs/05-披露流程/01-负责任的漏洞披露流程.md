# 06 · 负责任的漏洞披露流程

> 当您在第三方软件中发现 CWE-602 类缺陷时，**正确的做法是联系厂商修复，而非公开利用**。
> 本文给出标准的负责任披露（Responsible Disclosure）流程。

---

## 一、 为什么必须负责任披露？

| 公开利用（❌） | 负责任披露（✅） |
|:---|:---|
| 立即公开漏洞细节 | 先通知厂商，给予修复时间 |
| 提供可运行利用代码 | 只提供缺陷描述与修复建议 |
| 用户长期暴露在风险中 | 修复后用户获得安全保障 |
| 可能触犯法律 | 受法律与行业惯例保护 |
| 损害厂商与用户利益 | 推动整个生态安全水平提升 |
| 个人声誉受损 | 获得厂商致谢与行业认可 |

**核心逻辑**：安全研究的价值在于**让软件变得更安全**，
而不是**让攻击者更容易得手**。

---

## 二、 标准披露流程

```
┌─────────────────────────────────────────────────────────────┐
│  阶段 1 · 发现与验证 (Discovery & Validation)                │
│    • 在受权环境 / 自有设备上验证缺陷                          │
│    • 记录最小必要证据（无需完整利用链）                        │
│    • 评估影响范围与严重性                                     │
├─────────────────────────────────────────────────────────────┤
│  阶段 2 · 私下通知厂商 (Private Notification)                │
│    • 通过官方安全邮箱 / 漏洞平台提交                           │
│    • 提供：缺陷描述 + 影响 + 修复建议                          │
│    • 不提供：完整利用代码                                     │
├─────────────────────────────────────────────────────────────┤
│  阶段 3 · 协商修复期 (Coordinated Fix Window)                │
│    • 常规期限：90 天                                          │
│    • 复杂缺陷可协商延长                                       │
│    • 厂商确认后配合验证修复效果                                │
├─────────────────────────────────────────────────────────────┤
│  阶段 4 · 协调公开 (Coordinated Disclosure)                  │
│    • 厂商修复并发布更新后，双方协商公开时间                     │
│    • 公开内容以"缺陷描述 + 修复方案"为主                        │
│    • 通常可申请 CVE 编号                                      │
├─────────────────────────────────────────────────────────────┤
│  阶段 5 · 归档与致谢 (Archive & Credit)                      │
│    • 厂商在 Release Notes 中致谢                              │
│    • 研究者可撰写技术分析文章（不含利用代码）                    │
└─────────────────────────────────────────────────────────────┘
```

---

## 三、 阶段 1 · 发现与验证

### 授权前提（重要）

在进行任何测试前，必须确认以下**任一**条件成立：

- [ ] 您拥有该软件的合法授权（购买 / 试用许可），且在**自己的设备**上测试
- [ ] 您已获得厂商**书面授权**进行安全测试
- [ ] 您在**隔离的实验环境**中进行分析（不涉及生产系统）
- [ ] 符合当地的**安全研究豁免**条款

> ⚠️ **不得**对他人系统、生产环境或未授权目标进行测试。

### 证据记录规范

记录**最小必要证据**，足以说明问题即可：

| 应记录 ✅ | 不应记录 ❌ |
|:---|:---|
| 受影响的产品与版本 | 完整的利用脚本 |
| 缺陷的类别（CWE 编号） | 精确的内存偏移 + 补丁字节 |
| 架构层的根因描述 | 可直接复制使用的绕过工具 |
| 影响范围评估 | 大规模自动化利用方法 |
| 修复建议 | — |

## 四、 阶段 2 · 私下通知厂商

### 寻找联系方式

| 渠道 | 优先级 |
|:---|:---|
| 官方 `security@` 邮箱 | 🥇 首选 |
| 官方漏洞提交平台（如 HackerOne / 自建） | 🥇 首选 |
| `SECURITY.md` / `security.txt` 文件 | 🥈 |
| 官网联系表单 | 🥉 |
| GitHub Security Advisory（开源项目） | 🥇（开源） |

### 通知邮件模板

```
Subject: [Security] CWE-602 客户端鉴权缺陷报告 - {产品名} {版本号}

尊敬的 {厂商名} 安全团队：

您好。我在对 {产品名} 进行安全研究时，发现一处
CWE-602（客户端强行实施服务端安全机制）类缺陷，特此私下告知，
以便贵司在产品更新中修复。

─────────────────────────────────────────
【缺陷概要】
  • 受影响产品：{产品名}
  • 受影响版本：{版本范围}
  • 受影响组件：{组件名}
  • 缺陷类别：  CWE-602 / CWE-{其他}
  • 风险等级：  高 / 中 / 低

【缺陷描述】
  {用架构层语言描述缺陷，说明"哪里设计有问题"，
   但不提供完整的绕过步骤}

【影响评估】
  {说明可能造成的业务与安全影响}

【修复建议】
  1. {建议一}
  2. {建议二}
  3. {建议三}

【验证说明】
  我已在自有设备 / 隔离环境中验证了该缺陷的存在。
  出于负责任披露原则，本邮件不附带任何可直接运行的利用代码。
  如需进一步技术细节，我可在贵司确认后配合提供。

【披露计划】
  我计划在贵司确认后 90 天协调公开本缺陷的技术分析
  （仅含缺陷描述与修复方案，不含利用代码）。
  如贵司需要更长时间，我们可以协商调整。

期待贵司的回复。

此致
{您的署名}
{联系方式}
```

## 五、 阶段 3 · 协商修复期

### 标准时间线

| 时间 | 动作 |
|:---|:---|
| Day 0 | 提交漏洞报告 |
| Day 1~7 | 厂商确认收到并开始评估 |
| Day 7~30 | 厂商复现与修复开发 |
| Day 30~60 | 修复测试与版本发布 |
| Day 60~90 | 用户更新覆盖期 |
| Day 90 | 协调公开（或协商延长） |

### 沟通原则

- ✅ **耐心**：厂商可能需要时间定位与修复
- ✅ **专业**：只讨论技术问题，不做情绪化表达
- ✅ **配合**：厂商需要细节时，可提供必要的技术说明
- ❌ **不威胁**：不要以"公开漏洞"施压
- ❌ **不勒索**：绝不索取报酬作为不公开的条件

## 六、 阶段 4 · 协调公开

### 公开内容规范

| 应包含 ✅ | 不应包含 ❌ |
|:---|:---|
| 缺陷类别与 CWE 编号 | 完整利用代码 |
| 架构层根因分析 | 精确偏移与补丁字节 |
| 影响范围 | 一键绕过工具 |
| 修复方案 | 大规模利用方法 |
| 厂商致谢 | 未修复产品的利用细节 |
| 披露时间线 | — |

### 申请 CVE 编号

可通过以下渠道申请：

- [MITRE CVE 申请](https://cveform.mitre.org/)
- GitHub Security Advisory（开源项目，自动分配 CVE）
- 各国 CERT（如 CNVD、CNNVD）

**CVE 编号的价值**：
- 行业标准认可
- 厂商修复的正式记录
- 个人安全研究履历

## 七、 常见问题

### Q1：厂商不回复怎么办？

**建议流程**：
1. 等待 7 天，发送一次跟进邮件
2. 等待 14 天，尝试其他联系渠道
3. 等待 30 天，可考虑通过 CERT 协调
4. 等待 90 天，可按计划公开（但仍以"缺陷描述 + 修复建议"为主）

### Q2：厂商威胁要起诉我怎么办？

**保护自己的方式**：
- 确保测试在**自有设备**上进行
- 确保**未获取或传播**任何商业数据
- 确保报告内容**不含利用代码**
- 保留所有沟通记录
- 必要时寻求法律援助

> 💡 在大多数司法管辖区，**善意的安全研究**受到法律保护，
> 前提是：不造成损害、不获取数据、不公开利用方法。

### Q3：厂商给了赏金，可以收吗？

**可以。** 漏洞赏金（Bug Bounty）是厂商对安全研究的**正式认可**，
收取赏金不影响负责任披露的合法性。

但注意：
- ❌ 不要以"不给钱就公开"作为条件（这是勒索）
- ✅ 赏金应是厂商**主动提供**的

### Q4：我可以发布技术分析文章吗？

**可以，但有边界**：

| 可以 ✅ | 不可以 ❌ |
|:---|:---|
| 分析缺陷的架构成因 | 提供完整的绕过步骤 |
| 讲解 CWE 缺陷模式 | 附带可运行的工具 |
| 给出修复方案与代码 | 公开未修复产品的利用细节 |
| 分享研究方法论 | 教读者如何复制攻击 |

### Q5：我发现的是开源项目，流程一样吗？

**基本一致**，但更简单：
- 通过 GitHub Security Advisory 私下报告
- 或提交 Issue（如果项目没有安全政策）
- 开源社区通常响应更快

## 八、 道德底线

> ### 🚫 绝不逾越的四条线
>
> 1. **不获取数据** —— 不读取、不下载、不外传任何用户或商业数据
> 2. **不造成损害** —— 不破坏系统、不影响他人使用
> 3. **不公开利用** —— 不发布可运行的攻击代码或工具
> 4. **不谋取私利** —— 不以漏洞要挟、勒索或非法牟利
