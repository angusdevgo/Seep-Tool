# 02 · 客户端脆弱性模式矩阵

> 本文归纳桌面客户端在鉴权设计中的**七类高频架构缺陷模式**。
> 每种模式给出：**缺陷成因 → 反面代码模式 → 修正方案**。

---

## 模式总览

| # | 模式名称 | 关联 CWE | 风险 | 修复难度 |
|:---:|:---|:---|:---:|:---:|
| 1 | 单点布尔裁决 | CWE-602 | 🔴 高 | 中 |
| 2 | 硬编码密钥材料 | CWE-321 / CWE-798 | 🔴 高 | 高 |
| 3 | 动态库加载顺序缺陷 | CWE-427 | 🔴 高 | 低 |
| 4 | 可写全局状态变量 | CWE-602 | 🔴 高 | 中 |
| 5 | 明文进程间通信 | CWE-311 / CWE-345 | 🟠 中高 | 低 |
| 6 | 自研弱校验算法 | CWE-327 | 🔴 高 | 高 |
| 7 | 空值短路校验（Fail-Open） | CWE-287 | 🔴 高 | 低 |

## 模式 1 · 单点布尔裁决

### 缺陷成因

特权判定被实现为**独立的、可导出的、返回布尔值的函数**，
其返回值直接决定全部特权功能的开放与否。

**为什么这是缺陷？**
- 判定点与业务实现之间存在**清晰边界** → 边界即攻击面；
- 布尔返回值只有两种状态 → 攻击者只需翻转一个 bit；
- 单点结构意味着**改一处即解锁全部**。

### 反面代码模式

```csharp
// ❌ 反例：独立的导出判定函数
public static class License
{
    public static bool IsPro()
    {
        // 判定逻辑（无论多复杂）
        return _cachedResult;
    }
}

// 业务代码中大量调用
if (License.IsPro()) { EnableAdvancedFeature(); }
```

**问题所在**：`IsPro()` 是一个独立的、可被单独定位和改写的"开关"。

### 修正方案

```csharp
// ✅ 正例：判定内联 + 凭据绑定
public sealed class FeatureGate
{
    private readonly byte[] _signedEntitlement;  // 服务端签名凭据
    private readonly byte[] _deviceBinding;      // 设备绑定哈希

    public bool TryExecuteAdvanced(Action action)
    {
        // 1. 验签（公钥验签，私钥在服务端）
        if (!Ed25519.Verify(_signedEntitlement, PublicKey)) return false;

        // 2. 设备绑定校验
        if (!CryptographicOperations.FixedTimeEquals(
                Hash(_signedEntitlement), _deviceBinding)) return false;

        // 3. 有效期校验（防时钟回拨）
        if (!Entitlement.IsWithinValidity(_signedEntitlement)) return false;

        // 4. 直接执行，不暴露"是否Pro"这个中间状态
        action();
        return true;
    }
}
```

**改进点**：
- 取消独立的布尔判定出口；
- 校验与执行**合为一体**，无中间状态可篡改；
- 校验逻辑**多点分散**（验签 + 绑定 + 时效）。

## 模式 2 · 硬编码密钥材料

### 缺陷成因

客户端内置**对称密钥**或**私钥材料**，用于解密或生成授权凭据。

**为什么这是缺陷？**
- 客户端二进制对攻击者**完全可见** → 密钥必然泄露；
- 对称体系下，**持密钥者即可造凭据** → 无信任根；
- 一旦泄露，**所有历史版本同时失效**，只能换密钥（需重新发布）。

### 反面代码模式

```csharp
// ❌ 反例：硬编码对称密钥
private static readonly byte[] AesKey = new byte[] {
    0x4A, 0x7B, 0x1C, 0x3D, /* ... 硬编码在二进制中 ... */
};

public static string GenerateLicense(string machineId)
{
    using (var aes = Aes.Create())
    {
        aes.Key = AesKey;
        return Convert.ToBase64String(
            aes.Encrypt(Encoding.UTF8.GetBytes(machineId)));
    }
}
```

**问题所在**：密钥在客户端，生成权在客户端 → 无信任根。

### 修正方案

```csharp
// ✅ 正例：客户端只持有公钥，仅做验签
public static class LicenseVerifier
{
    // 公钥是公开信息，泄露无害
    private static readonly byte[] ServerPublicKey = Convert.FromBase64String(
        "MCowBQYDK2VwAyEA...");  // Ed25519 公钥

    public static bool Verify(byte[] licenseBlob, byte[] signature)
    {
        // 客户端只能验证，无法生成
        return Ed25519.Verify(signature, licenseBlob, ServerPublicKey);
    }
}
```

**改进点**：
- 客户端仅持**公钥**（公开信息，泄露无害）；
- 生成权完全保留在**服务端私钥**（离线保管 / HSM）；
- 参见 [文档 04 · Ed25519 离线许可体系设计](../02-防御体系/02-Ed25519离线许可体系设计.md)。

## 模式 3 · 动态库加载顺序缺陷

### 缺陷成因

程序以**裸 `LoadLibrary`** 加载动态库，未限定搜索路径，也未校验签名。

**为什么这是缺陷？**
- Windows DLL 搜索顺序会**优先加载程序目录**中的同名文件；
- 攻击者放置同名代理库 → 在**合法进程内**执行任意代码；
- 由于是合法进程加载，**不触发安全软件告警**。

### 反面代码模式

```cpp
// ❌ 反例：不受控的库加载
HMODULE hMod = LoadLibrary(L"helper.dll");
// 攻击者只需在同目录放一个 helper.dll 即可劫持
```

### 修正方案

```cpp
// ✅ 正例：限定搜索路径 + 签名校验
int wmain()
{
    // 1. 启动首行限定 DLL 搜索路径为系统目录
    SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32);

    // 2. 使用绝对路径加载
    HMODULE hMod = LoadLibraryExW(
        L"C:\\Program Files\\MyApp\\helper.dll",
        nullptr,
        LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR);

    // 3. 校验签名
    if (!VerifyAuthenticodeSignature(L"C:\\Program Files\\MyApp\\helper.dll"))
    {
        return -1;  // 拒绝启动
    }
    return Run();
}
```

**改进点**：
- `SetDefaultDllDirectories` 从根源切断搜索路径劫持；
- 绝对路径 + `LOAD_LIBRARY_SEARCH_*` 标志双重限定；
- 签名校验确保模块未被替换。

## 模式 4 · 可写全局状态变量

### 缺陷成因

授权等级以**进程内可写全局变量**形式存在，且被多处 UI 逻辑直接引用。

**为什么这是缺陷？**
- 内存可被外部工具扫描与修改；
- 变量地址可通过字符串引用、符号表轻松定位；
- 状态被多处引用 → 改一处即全局生效。

### 反面代码模式

```csharp
// ❌ 反例：可写全局状态
public static class AppState
{
    public static bool IsRegistered = false;   // 明文可写
    public static int LicenseType = 0;         // 明文可写
}

// UI 直接依赖
if (AppState.LicenseType == 2) ShowProFeatures();
```

### 修正方案

```csharp
// ✅ 正例：凭据驱动 + 加密暂存 + 用毕擦除
public sealed class EntitlementCache
{
    private byte[] _encrypted;      // 加密存储
    private byte[] _sessionKey;     // 会话密钥

    public bool HasFeature(Feature f)
    {
        // 每次查询都重新验签，不缓存布尔结果
        var entitlement = Decrypt(_encrypted, _sessionKey);
        try
        {
            return Ed25519.Verify(entitlement.Signature, entitlement.Payload,
                                  ServerPublicKey)
                   && entitlement.Grants(f);
        }
        finally
        {
            // 用毕立即擦除敏感数据
            CryptographicOperations.ZeroMemory(entitlement.Payload);
        }
    }
}
```

**改进点**：
- 不存储明文布尔状态，改为**凭据驱动**；
- 凭据加密存储，会话密钥不落盘；
- **每次查询重新验签**，且用毕擦除内存。

## 模式 5 · 明文进程间通信

### 缺陷成因

鉴权服务与主程序通过**本地 IPC**（命名管道 / 共享内存）传递状态码，
但消息**无完整性保护**。

**为什么这是缺陷？**
- 本地 IPC 通道可被同用户下的其他进程接入或伪造；
- 状态码是小整数，搜索空间极小；
- 主程序**无条件信任**对端，未校验进程身份。

### 反面代码模式

```csharp
// ❌ 反例：明文 IPC，无认证
// 鉴权服务端
pipe.Write(BitConverter.GetBytes(3));   // 3 = 已授权

// 主程序
int code = BitConverter.ToInt32(pipe.Read(4));
if (code == 3) EnablePro();             // 无条件信任
```

### 修正方案

```csharp
// ✅ 正例：HMAC 认证 + 时戳防重放 + 身份校验
public static bool TryReadAuthenticatedResponse(NamedPipeServerStream pipe,
                                                out Entitlement result)
{
    // 1. 校验对端进程身份（路径 + 签名）
    if (!VerifyPeerProcess(pipe)) { result = null; return false; }

    // 2. 读取消息体 + HMAC
    var payload = ReadFramed(pipe, out byte[] receivedMac);

    // 3. 校验 HMAC（会话密钥由两进程协商，不落盘）
    var expectedMac = HMACSHA256.HashData(_sessionKey, payload);
    if (!CryptographicOperations.FixedTimeEquals(receivedMac, expectedMac))
    { result = null; return false; }

    // 4. 校验时戳与序号（防重放）
    var msg = Deserialize(payload);
    if (!msg.IsFresh(TimeSpan.FromSeconds(5))) { result = null; return false; }

    result = msg.Entitlement;
    return true;
}
```

**改进点**：
- HMAC 保证消息完整性与来源真实性；
- 时戳 + 序号防重放；
- 对端进程身份校验（路径 + 签名）；
- 管道 ACL 限制访问。

## 模式 6 · 自研弱校验算法

### 缺陷成因

为"防止被破解"，开发者**自行设计**哈希/加密/编码算法用于凭据校验。

**为什么这是缺陷？**
- 自研算法**未经公开密码学审查**，抗分析强度远低于标准算法；
- 算法完全暴露在客户端 → 可被逆向还原；
- 校验段长度通常不足 → 可被离线穷举；
- 通常跨版本复用 → 一次还原影响所有历史版本。

### 反面代码模式

```csharp
// ❌ 反例：自研"混合哈希"
static bool CheckKey(string key)
{
    int h1 = 0;
    foreach (char c in key) h1 = (h1 * 43 + c) & 0xFFFF;    // 多项式
    int h2 = ElfHash(key);                                   // 变种
    int h3 = 0;
    for (int i = 0; i < 4; i++) h3 ^= (h1 << i) | h2;        // 多轮异或
    return (h3 & 0x3FF) == Extract(key, 160, 179);           // 仅 10 bit 校验
}
```

**问题所在**：10 bit 校验段 → 仅需尝试约 1024 次即可碰撞。

### 修正方案

```csharp
// ✅ 正例：标准算法 + 足够熵 + 服务端签名
static bool CheckLicense(byte[] license, byte[] signature)
{
    // 1. 标准非对称验签（Ed25519）
    if (!Ed25519.Verify(signature, license, ServerPublicKey))
        return false;

    // 2. 解析载荷并校验绑定关系
    var payload = LicensePayload.Parse(license);
    return payload.DeviceHash == ComputeDeviceHash()
        && payload.ExpiresAt > DateTimeOffset.UtcNow
        && payload.Nonce == _expectedNonce;
}
```

**改进点**：
- 使用**标准密码学原语**（Ed25519）；
- 256 bit 安全强度（vs 自研的 10 bit）；
- 服务端签名提供**不可伪造性**。

## 模式 7 · 空值短路校验（Fail-Open）

### 缺陷成因

鉴权分支在处理"**凭据缺失 / 为空 / 格式非法**"时，把"**无法判定**"错误地当作"**判定通过**"，
直接跳入成功分支。

**为什么这是缺陷？**
- 安全上正确的默认姿态是 **Fail-Closed**（默认拒绝）：无法判定 ⇒ 拒绝；
- Fail-Open 把"配置缺失"变成了"免检通道" —— **无需任何代码修改，仅靠空配置即可触发**；
- 客户端在旁路状态下**可能完全不向服务端发请求**，服务端风控无任何异常信号可捕获；
- 若该分支同时存在于"首次运行 / 配置损坏 / 网络不可达"等容错路径上，
  则**容错逻辑会与鉴权逻辑相互污染**。

**常见变体**：

| 变体 | 表现 |
|:---|:---|
| 空值短路 | 凭据为 `null` / `""` 时直接放行 |
| 字面量短路 | 把 `"null"` / `"none"` / `"undefined"` 等字符串当作"无凭据"特殊处理 |
| 异常吞没 | 验签抛异常时 `catch { return true; }` |
| 超时放行 | 服务端校验超时后默认放行（离线宽容） |
| 降级放行 | 校验服务不可用时自动降级为"本地信任" |

### 反面代码模式

```csharp
// ❌ 反例：Fail-Open —— 空凭据被解释为"无需校验"
static async Task<AuthResult> VerifyAsync(string? credential)
{
    if (string.IsNullOrEmpty(credential))   // ← 致命分支
    {
        // 认为"没填凭据 = 无需校验"
        return AuthResult.Success();        // ✗ 应当返回 Failed
    }

    // 只有非空凭据才走服务端校验
    return await VerifyWithServerAsync(credential);
}
```

**问题所在**：把"**没有凭据**"与"**不需要凭据**"混为一谈。
调用方传入 `null`（未登录、配置损坏、字段缺失）时，会意外获得**最高权限**。

### 修正方案

```csharp
// ✅ 正例：Fail-Closed —— 无法判定即拒绝
static async Task<AuthResult> VerifyAsync(string? credential)
{
    // 1. 输入校验：空值 / 非法格式 → 一律拒绝
    if (string.IsNullOrWhiteSpace(credential))
        return AuthResult.Failed("missing_credential");

    // 2. 拒绝已知占位符字面量
    if (PlaceholderValues.Contains(credential.Trim().ToLowerInvariant()))
        return AuthResult.Failed("placeholder_credential");

    // 3. 验签失败 / 超时 / 异常 → 一律拒绝（不得 catch 后放行）
    try
    {
        var result = await VerifyWithServerAsync(credential);
        return result.IsValid ? result : AuthResult.Failed("invalid_signature");
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "license verification failed");
        return AuthResult.Failed("verification_error");   // ✓ 拒绝，不是放行
    }
}
```

**改进点**：
- 所有"无法判定"路径统一收敛到 **Failed**；
- 显式拒绝占位符字面量，堵住"字面量短路"变体；
- 异常与超时**不降级放行**；
- 离线场景应走**预签发签名凭据**（本地验签），而非"跳过校验"。

## 修正优先级建议

若您的产品同时命中多种模式，建议按以下顺序修复：

```
第一优先（架构级，必须做）
  ├─ 模式 2：硬编码密钥材料  → 迁移至非对称签名体系
  ├─ 模式 1：单点布尔裁决    → 判定内联化 + 凭据驱动
  └─ 模式 7：空值短路校验    → 鉴权分支全面 Fail-Closed（修复成本极低，收益极高）

第二优先（安全级，强烈建议）
  ├─ 模式 3：DLL 加载缺陷    → 修复成本低，收益高
  └─ 模式 5：明文 IPC        → 修复成本低，收益高

第三优先（加固级，视成本）
  ├─ 模式 4：可写全局状态    → 加密存储 + 用毕擦除
  └─ 模式 6：自研弱算法      → 迁移至标准算法
```
