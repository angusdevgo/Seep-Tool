# Bandizip · 单点布尔裁决

> **公告编号**：02
> **缺陷模式**：模式 01 · 单点布尔裁决（兼 模式 03 / 模式 04）
> **关联 CWE**：`CWE-602` · `CWE-427`
> **风险等级**：🔴 高（含**代码执行类**缺陷）
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

Bandizip 企业版存在**两项彼此独立的高危缺陷**：

1. **动态库搜索顺序缺陷（CWE-427）** —— 主程序以不受控路径加载动态库，
   攻击者可在**合法签名进程上下文内获得任意代码执行权**；
2. **版本等级由进程内可写标志单点裁决（CWE-602）** ——
   社区版 / 专业版 / 企业版的区分仅由一个内存标志决定。

> ⚠️ **严重性排序**：第 1 项的危害**高于授权绕过本身** ——
> 它是真实的本地代码执行漏洞，**即使对完全不在意授权的用户也存在风险**。

## 攻击接入点分析 ★

### 接入点清单

| # | 接入点 | 所在组件 / 机制 | 攻击者前提 | 可获得能力 | 影响 |
|:---:|:---|:---|:---|:---|:---:|
| **AP-1** | **动态库加载路径** | `Bandizip.exe` 启动阶段对同目录 DLL 的加载调用 | 对**安装目录**有写权限 | **在合法签名进程内执行任意代码** | 🔴 严重 |
| **AP-2** | **版本等级内存标志** | 进程内区分 社区版 / 专业版 / 企业版的可写标志 | 同用户权限的进程内存读写 | 单点改写 → 企业版全功能 | 🔴 高 |
| **AP-3** | **授权信息展示 API** | 主程序 IAT 中的 `SetDlgItemTextW` 导入项 | 同 AP-2 | 篡改"关于"对话框中的授权信息显示 | 🟡 中 |
| **AP-4** | **服务端黑名单校验** | 版本启动时的黑名单核验逻辑 | 本地可控校验结果 | 被拉黑用户仍可正常使用 | 🔴 高 |
| **AP-5** | **授权信息配置文件** | 自定义授权用户名/邮箱的 ini 配置 | 用户态文件写权限 | 定制界面显示的授权信息 | 🟡 低 |

### 接入点性质分类

| 类型 | 接入点 | 说明 |
|:---|:---|:---|
| **代码执行类** | AP-1 | 🔴 **最高危** —— 与授权问题无关，本身就是安全漏洞 |
| **状态裁决类** | AP-2 | 单点标志决定全部等级差异功能 |
| **展示篡改类** | AP-3 · AP-5 | 仅影响界面呈现，危害相对较低 |
| **风控绕过类** | AP-4 | 使厂商封禁机制失效 |

### 攻击链组合分析

| 攻击链 | 组合路径 | 门槛 | 最终效果 |
|:---|:---|:---:|:---|
| **链 A**（最高危） | **AP-1 → 进程内代码执行 → 直接改写 AP-2 / AP-3** | 中（需目录写权限）<br>但**普通用户目录常可写** | **任意代码执行 + 企业版全功能 + 黑名单绕过** |
| **链 B**（仅授权） | AP-2 单独改写 | 中（需内存操作） | 企业版全功能 |
| **链 C**（风控规避） | AP-4 绕过黑名单 | 低 | 被拉黑用户继续使用 |

> ⚠️ **链 A 的核心风险**：
> 攻击者一旦通过 `AP-1` 取得进程内执行权，**后续所有接入点都不再需要独立突破** ——
> 它可以在进程内部以最高效率完成全部后续操作。
> 而且由于宿主进程签名合法，**常规安全软件通常不告警**。
>
> 更值得警惕的是：**该风险的存在与"是否想绕过授权"无关** ——
> 任何获得目录写权限的本地攻击者（含其他恶意软件）都能利用它。

### 攻击面收敛建议（厂商视角）

```
接入点优先级（按风险排序）

  AP-1  代码执行类  ──→ 最高优先（成本最低：SetDefaultDllDirectories + 签名校验）
  AP-2  状态裁决类  ──→ 架构级重构（改为服务端签名凭据）
  AP-4  风控绕过类  ──→ 校验结果必须服务端签名 + Fail-Closed
  AP-3  展示篡改类  ──→ 随 AP-2 解决
  AP-5  展示篡改类  ──→ 配置文件不再作为权益判据
```

## 技术细节

### 1 · 运行时层：动态库搜索顺序不受控

**观测事实**：主程序启动阶段以**裸 `LoadLibrary`** 方式加载动态库，
**未调用 `SetDefaultDllDirectories`** 限定搜索路径，也未对加载的库做签名校验。

**安全含义**：符合 **CWE-427** 与 **MITRE ATT&CK T1574.001** 的定义。

| 维度 | 说明 |
|:---|:---|
| Windows DLL 搜索顺序 | 默认**优先搜索程序所在目录** |
| 攻击者前提 | 对安装目录有写权限 |
| 获得能力 | 在合法签名进程内执行任意代码 |
| 检测难度 | 高 —— 进程签名合法，常规安全软件不告警 |
| 可利用后果 | 可读取已解压文件、窃取剪贴板、注入持久化载荷 |

---

### 2 · 决策层：版本等级由内存标志单点裁决

**观测事实**：社区版 / 专业版 / 企业版的区分由**进程内一个可写标志**决定，
判定逻辑为**单点分支**，且**无任何完整性保护**。

**安全含义**：

1. 等级标志是**唯一的差异来源** —— 改一处即解锁全部企业版功能；
2. 无校验和、无加密、无防篡改；
3. 标志可通过内存模式匹配轻松定位。

**核心教训**：**"等级标志驱动"的设计，等于把授权开关暴露在进程内存中。**

---

### 3 · 风控层：黑名单校验结果可由客户端单方面决定

**观测事实**：被拉黑用户的核验逻辑在客户端完成，且**结果无服务端签名保护**。

**安全含义**：厂商的封禁措施**丧失实际约束力** ——
被拉黑的用户仍可正常使用全部功能，且厂商难以察觉。

## 影响面

### 商业影响

- 企业版全部功能可被本地获取；
- **黑名单封禁机制失效**，厂商无法处置滥用账号；
- 企业版与社区版的价格差异**失去技术保障**。

### 安全影响

- 🔴 **本地任意代码执行** —— 严重性最高，且与授权问题无关；
- 合法签名进程被劫持，破坏代码签名的信任语义；
- 可能被其他恶意软件作为本地提权/持久化的跳板。

### 合规影响

- 企业采购场景下，签名信任链断裂可能不符合安全基线要求；
- 授权不可远程吊销，不满足软件资产管理审计要求。

## 加固方案

### 1 · 加载安全层（最高优先级，成本最低）

```cpp
// ✅ 程序入口点首行必须调用
int wmain()
{
    // 限定搜索路径：仅系统目录 + 应用目录
    SetDefaultDllDirectories(
        LOAD_LIBRARY_SEARCH_SYSTEM32 |
        LOAD_LIBRARY_SEARCH_APPLICATION_DIR);

    // 加载非系统库：绝对路径 + 签名校验
    HMODULE hMod = LoadLibraryExW(
        L"C:\\Program Files\\Bandizip\\plugin.dll",
        nullptr,
        LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR);

    if (!hMod || !VerifyAuthenticode(hMod)) return -1;   // 拒绝启动

    return Run();
}
```

### 2 · 状态保护层

```csharp
// ❌ 反面：等级标志单点裁决
public static int Edition = 0;   // 0=社区 1=专业 2=企业
if (AppState.Edition >= 2) EnableEnterpriseFeatures();

// ✅ 正面：凭据驱动 + 每次重新验签
public static bool TryExecuteEntitled(string feature, Action action)
{
    using var cred = LicenseStore.LoadDecrypted();
    if (cred is null) return false;

    if (!Ed25519.Verify(cred.Signature, cred.Payload, ServerPublicKey)) return false;
    if (!cred.Payload.MatchesDevice(DeviceFingerprint.Compute()))       return false;
    if (!cred.Payload.IsValidNow(MonotonicClock.Now))                   return false;
    if (!cred.Payload.Grants(feature))                                  return false;

    action();          // 校验与执行合一
    return true;
}
```

### 3 · 风控层

| 措施 | 说明 |
|:---|:---|
| 黑名单结果**服务端签名** | 客户端仅验签，不得自行判定 |
| **Fail-Closed** | 无法确认时按"已拉黑"处理 |
| 通道加固 | HTTPS + 证书绑定 + 防重放 |

### 4 · 加固优先级

```
第一优先（架构级 + 成本最低）
  └─ SetDefaultDllDirectories + 模块签名校验   ← 直接消除 AP-1

第二优先（架构级）
  └─ 等级标志改为服务端签名凭据                 ← 消除 AP-2 / AP-3

第三优先
  ├─ 黑名单校验结果服务端签名 + Fail-Closed      ← 消除 AP-4
  └─ 运行时二进制完整性自检
```
