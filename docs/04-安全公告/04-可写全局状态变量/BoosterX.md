## 摘要

该产品采用了**商业级混淆器全保护模式**
（符号重命名 + 字符串加密 + 程序集代码加密 + 代码虚拟化），
保护强度在所有分析样本中**属于上乘**。

> ### 📌 但审计结果表明
> **混淆与虚拟化只能提高分析成本，无法改变"裁决权在客户端"这一架构事实。**

本案例的价值恰在于它提供了一个「**保护层很厚、架构层很薄**」的典型样本。
该产品存在**四处彼此独立的架构缺陷**，可分别或组合利用。

> ⚠️ **链 A 的独特危险性 —— Fail-Open 是本案例最严重的缺陷**

> * 在**流量层表现为"客户端完全静默"** —— 不发任何请求；
> * 因此**服务端侧的风控系统收不到任何异常信号**。
>
> 这意味着厂商投入巨资的代码虚拟化保护，
> **在一条"配置空缺"路径面前完全失效**。

## 技术细节

### 1 · 保护层与架构层的错位（本案例核心观察）

**观测事实**：该产品的混淆保护强度**在所有样本中最高**，
但架构层缺陷**依然完整存在**。

**这个对比本身就是最重要的发现**：

| 维度 | 保护强度 | 说明 |
|:---|:---:|:---|
| 符号重命名 | ✅ 高 | 函数/变量名不可读 |
| 字符串加密 | ✅ 高 | 静态字符串不可直接检索 |
| 程序集代码加密 | ✅ 高 | 代码段加密存储 |
| 代码虚拟化 | ✅ 高 | 关键逻辑编译为自定义字节码 |
| — | — | — |
| **裁决权位置** | ❌ **完全在客户端** | **架构层缺陷未受任何缓解** |
| **Fail-Open 语义** | ❌ **存在免检通道** | **一条空配置即绕过全部保护** |

> **核心结论**：**混淆强度与安全架构是两个正交维度。**
> 前者提高"分析成本"，后者决定"是否存在缺陷"。
> **再高的分析成本，也无法弥补一个语义层面的设计错误。**

---

### 2 · 缺陷一：付费权益的裁决权完全在客户端

**观测事实**：付费权益由**本地布尔量**决定 ——
全部功能设置项中存在若干项在构造时被打上"PRO 专属"标记，
另有一个**全局授权态查询入口**被多处 UI 与业务逻辑直接引用
（激活页状态显示、任务执行流程、设置项可编辑性、页面级功能门控）。

**安全含义**：

```
┌──────────────────────────────────────────────────┐
│  [全局授权态查询入口]  ← 单点                          │
│         ↓  ↓  ↓  ↓  ↓                            │
│   激活页  任务执行  设置项  页面门控   ...   ← 多处引用  │
└──────────────────────────────────────────────────┘
     单点失守 → 全部引用点同时失效（扩散效应）
```

**核心教训**：整个权益判定链路**不依赖任何服务端签发的权益凭证** ——
**客户端既是运动员又是裁判。**

---

### 3 · 缺陷二：Fail-Open 空值短路 ★ 最严重

**观测事实**：启动期授权装载流程中，判定点的语义是"**凭据是否为空 / 无效**"。
当凭据为 `null`、空字符串或字面量 `"null"` 时，
客户端将其解释为"**无需校验**"，直接跳入"**校验通过**"分支。

**这是典型的 Fail-Open 设计**：

```
❌ 当前实现（Fail-Open —— 危险）
   凭据为空？─是→ [ 进入"校验通过"分支 ]  ← 免检通道
            └─否→ [ 正常校验 ]

✅ 应有实现（Fail-Closed —— 安全）
   凭据为空？─是→ [ 判定失败，拒绝服务 ]
            └─否→ [ 正常校验 ]
```

**为什么这是最严重的缺陷**：

| 维度 | 说明 |
|:---|:---|
| **触发成本** | 极低 —— **一份空配置即可**，无需任何技术手段 |
| **服务端可见性** | **零** —— 客户端完全不发请求，风控无异常信号 |
| **绕过范围** | 全部 —— 跳过整条校验链 |
| **与保护强度的关系** | **无关** —— 混淆/虚拟化**完全无法防护语义缺陷** |

> ### 🔑 核心教训
> **Fail-Open 是最危险的鉴权反模式** ——
> 它把「**无法判定**」错误地当作「**判定通过**」，
> 让"配置缺失"变成了"免检通道"。

---

### 4 · 缺陷三：特权状态存放于用户可写位置

**观测事实**：全部功能开关（含所有 PRO 相关开关，共数十项）
以**明文布尔值**存放于当前用户注册表 hive。
该位置**任何用户态进程均可读写**，且客户端读取后**未做任何完整性或来源校验**。

**安全含义**：

| 维度 | 现状 | 应有措施 |
|:---|:---|:---|
| 存储形式 | 明文布尔值 | 加密/签名存储 |
| 存放位置 | 用户可写 hive | 受保护位置或凭据化 |
| 读取校验 | 无 | 完整性校验 |
| 利用方式 | **无需触碰二进制** | — |

**核心教训**：**本地配置只能作为"用户偏好"，绝不能作为"权益判据"。**

---

### 5 · 缺陷四：传输层与密钥材料缺陷

**观测事实**：授权校验接口走**明文 HTTP**，
且请求/响应体仅用**全局硬编码的对称密钥**加密。

**安全含义**：

| 问题 | 关联 CWE | 后果 |
|:---|:---|:---|
| 明文 HTTP | `CWE-319` | 可被拦截、篡改、重放 |
| 硬编码对称密钥 | `CWE-798` | 密钥随客户端分发 → **必然泄露** |
| 可离线解密 | — | 历史流量可被离线解密 |
| 可构造响应 | — | 可伪造格式合法的授权响应 |
| 裸 IP 兜底地址 | — | 绕过 DNS 层管控 |

**核心教训**：**随包分发的密钥 = 公开的密钥。**

---

### 6 · 代码虚拟化的还原特征（防御研究视角）

**观测事实**：虚拟化保护伴随可识别的结构性特征 ——
"方法名自描述令牌"（名称本身编码了方法在字节码流中的位置）
与"位置相关的流加密"。

**安全含义**：这类设计的可预测性一旦被识别，
**整条保护链可被系统性分析** —— 保护强度会显著下降。

> 💡 **对防御方的启示**：虚拟化保护的设计应避免
> "元数据自描述"与"位置相关密钥流"的组合 ——
> 它们为分析者提供了稳定的切入点。

## 影响面

### 商业影响

- **付费墙失效**：客户端侧全部 PRO 权益可被离线获取；
- **服务端不可感知**：旁路状态下客户端完全不发请求，风控无异常信号；
- **保护投入被抵消**：代码虚拟化的成本**无法转化为实际的安全收益**；
- **授权体系丧失商业保护能力**。

### 安全影响

- **明文传输泄露**：授权协议与硬编码密钥暴露，可被离线分析；
- **响应可伪造**：可构造格式合法的授权响应；
- **配置层攻击面**：用户可写位置存放权益状态，为其他恶意软件提供便利；
- **绕过尝试可能被其他软件复用**。

### 合规影响

- 明文 HTTP 传输授权相关数据，**可能不符合数据安全传输的合规要求**；
- 本地配置作为权益判据，不满足软件资产管理的可审计性要求；
- 缺乏远程吊销能力，不满足企业授权治理要求。

## 加固方案

### 1 · 鉴权语义层（最高优先级，零成本）★

```csharp
// ✅ 全面 Fail-Closed 重构
public static class AuthDecision
{
    public static bool IsAuthorized(string? credential, out string reason)
    {
        // ① 缺失 → 拒绝
        if (string.IsNullOrWhiteSpace(credential)
            || credential == "null")
        {
            reason = "凭据缺失或为空";
            return false;                     // ← Fail-Closed
        }

        // ② 格式非法 → 拒绝
        if (!TryParse(credential, out var cred))
        {
            reason = "凭据格式非法";
            return false;                     // ← Fail-Closed
        }

        // ③ 验签失败 → 拒绝
        if (!Ed25519.Verify(cred.Signature, cred.Payload, ServerPublicKey))
        {
            reason = "签名验证失败";
            return false;                     // ← Fail-Closed
        }

        // ④ 过期 → 拒绝
        if (!cred.Payload.IsValidNow(MonotonicClock.Now))
        {
            reason = "凭据已过期";
            return false;
        }

        reason = "OK";
        return true;
    }
}
```

> 📌 **这是本案例中"投入产出比最高"的修复** ——
> 只需**消除所有"空值即通过"的分支**，就能封堵最危险的免检通道。

### 2 · 传输与密钥层（成本低）

```csharp
// ✅ 加固后的授权校验
public static async Task<Entitlement?> VerifyAsync(string licenseId)
{
    using var http = new HttpClient(new HttpClientHandler
    {
        ServerCertificateCustomValidationCallback = PinServerCertificate  // 证书绑定
    });

    // ① 强制 HTTPS，移除裸 IP 兜底
    var nonce = Convert.ToBase64String(RandomNumberGenerator.GetBytes(16));
    var ts    = DateTimeOffset.UtcNow.ToUnixTimeSeconds();

    // ② 会话临时密钥（ECDH 协商），不再使用随包分发的对称密钥
    using var ecdh = ECDiffieHellman.Create(ECCurve.NamedCurves.nistP256);
    var sessionKey = DeriveSessionKey(ecdh, ServerPublicKey);

    // ③ 请求签名防重放
    var body = BuildRequest(licenseId, nonce, ts);
    var req  = SignRequest(body, sessionKey, ts, nonce);

    var resp = await http.PostAsync("https://api.vendor.com/verify", req);

    // ④ 响应必须验签（防伪造）
    var payload = await resp.Content.ReadAsByteArrayAsync();
    if (!Ed25519.Verify(resp.Headers.GetValues("X-Signature").First(), payload, ServerPublicKey))
        return null;                          // ← Fail-Closed

    return Parse(payload);
}
```

### 3 · 状态与判据层

| 措施 | 说明 |
|:---|:---|
| **本地配置不作判据** | 仅供用户偏好，权益判据必须来自签名凭据 |
| **凭据形态升级** | 改用 Ed25519 / RSA-PSS，绑定硬件指纹 + 有效期 + Nonce |
| **本地状态完整性** | 若必须本地存储，需加密 + 校验和 |
| **运行时完整性** | 关键判定下沉 Native 并做自校验 |

### 4 · 架构层（根本上）

| 措施 | 说明 |
|:---|:---|
| **服务端权威** | 客户端只持有并呈递凭据，不参与"是否付费"的裁决 |
| **权益数据服务端加密下发** | 核心权益对应的资源/数据由服务端加密，客户端无法本地生成 |
| **远程吊销** | 服务端记录设备指纹与请求频率，异常模式告警 |

### 5 · 加固优先级

```
第一优先（零成本，收益最高）★
  └─ 全面 Fail-Closed 重构                        ← 消除 AP-1（最严重）

第二优先（成本低）
  ├─ HTTPS + 证书绑定 + 响应验签 + 会话密钥协商      ← 消除 AP-5
  └─ 移除随包分发的对称密钥

第三优先（架构级）
  ├─ 权益判据改为服务端签名凭据                     ← 消除 AP-2 / AP-3
  └─ 本地配置不得作为权益判据                       ← 消除 AP-4

第四优先
  └─ 关键判定下沉 Native + 运行时完整性自检
```
