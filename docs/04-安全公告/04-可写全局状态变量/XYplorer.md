# XYplorer · 单点布尔裁决

> **公告编号**：09
> **缺陷模式**：模式 01 · 单点布尔裁决（兼 模式 03 / 模式 04）
> **关联 CWE**：`CWE-602` · `CWE-427`
> **风险等级**：🔴 高
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

XYplorer 的文件管理器专业版授权体系存在**四层递进的架构缺陷**：
授权状态由**进程内可写全局变量**单点驱动、注册码校验强度不足、
动态库加载路径不受控、且**全链路不存在任何服务端参与**。

其中"全局变量单点驱动"是核心缺陷 —— 由于该状态被多处 UI 与业务逻辑直接引用，
**任何对该状态的改写都会自动扩散到整个产品界面**，无需逐个处理功能点。

## 攻击接入点分析 ★

下表列出该产品授权体系中的**全部可攻击接入点**，
按**攻击者所需门槛从低到高**排列。

### 接入点清单

| # | 接入点 | 所在组件 / 机制 | 攻击者前提 | 可获得能力 | 影响 |
|:---:|:---|:---|:---|:---|:---:|
| **AP-1** | **动态库加载路径** | `XYplorer.exe` 启动阶段的 `LoadLibrary` 调用点 | 对安装目录有**写权限**（多为普通用户可写） | 在**合法签名进程上下文**内执行任意代码 | 🔴 严重 |
| **AP-2** | **进程内授权状态全局变量** | `XYplorer.exe` 数据段中的 `license_type` 整型变量 | 同用户权限的进程内存读写 | 单点改写即可**全功能解锁** | 🔴 高 |
| **AP-3** | **注册码校验函数** | 授权装载流程中的前缀匹配逻辑 | 本地生成任意字符串即可 | 通过校验，写入合法授权状态 | 🔴 高 |
| **AP-4** | **授权配置文件** | `XYplorer.ini` 的 `[Register]` 节 | 用户态文件写权限 | 影响重启后的授权装载结果 | 🟠 中高 |
| **AP-5** | **试用态 UI 渲染分支** | 标题栏渲染 / 关于框 / 功能门控的判定分支 | 同 AP-2 | 界面降级（去试用横幅） | 🟡 中 |

### 接入点性质分类

| 类型 | 接入点 | 说明 |
|:---|:---|:---|
| **代码执行类** | AP-1 | 严重性最高 —— **与授权问题无关，本身就是安全漏洞** |
| **状态改写类** | AP-2 · AP-5 | 单点改写，因状态被多处引用而**自动扩散** |
| **凭据伪造类** | AP-3 | 校验强度不足，可离线构造通过校验的输入 |
| **持久化类** | AP-4 | 影响重启后状态，但不即时生效 |

### 攻击链组合分析

> 单个接入点已足以突破，但**组合使用时危害显著上升**：

| 攻击链 | 组合路径 | 门槛 | 最终效果 |
|:---|:---|:---:|:---|
| **链 A**（最低门槛） | AP-3 单独利用 | 极低 | 获取完整专业版授权 |
| **链 B**（持久化） | AP-4 → 重启 → 生效 | 低 | 授权状态长期保持 |
| **链 C**（最高危） | **AP-1 → 获得进程内代码执行 → 操纵 AP-2 / AP-5** | 中（需目录写权限） | **任意代码执行 + 全 UI 去试用** |

> ⚠️ **链 C 的严重性远超授权绕过本身**：
> `AP-1` 使攻击者可在 XYplorer 的合法签名进程内执行代码。
> 这意味着该风险**即使对完全不在意授权的用户也真实存在**，
> 且因进程签名合法，**常规安全软件通常不会告警**。

### 攻击面收敛建议（厂商视角）

```
接入点优先级（按风险排序，建议按序整改）

  AP-1  代码执行类  ──→ 最高优先，成本最低（SetDefaultDllDirectories + 签名校验）
  AP-3  凭据伪造类  ──→ 迁移至非对称签名（架构级重构）
  AP-2  状态改写类  ──→ 改为凭据驱动，取消全局可写状态
  AP-4  持久化类    ──→ 配置文件不再作为权益判据
  AP-5  界面降级类  ──→ 随 AP-2 一并解决（状态源修正后自动消失）
```

## 技术细节

### 1 · 架构层：完全离线的授权模型

**观测事实**：对 `XYplorer.exe` 的导入表（Import Table）做静态枚举，
**不存在任何网络相关 API** —— 无 `WinINet`（`InternetOpen*` / `HttpSendRequest*`）、
无 `WinHTTP`、无 `Ws2_32`（Winsock）导入。

**推论**：该产品的授权校验与状态维护**100% 在客户端本地完成**，
服务端在整个授权生命周期中**零参与** —— 既无在线激活，也无周期性校验，
更无远程吊销能力。

**安全含义**：这是 CWE-602 的**结构性根源**。
只要"授权是否有效"的最终判定发生在客户端，
攻击者就必然能在本地找到改写该判定的路径 —— 这与混淆强度无关。

---

### 2 · 决策层：授权状态由可写全局变量单点驱动 ★ 核心缺陷

**观测事实**：产品的授权等级由一个**进程内全局变量**（下称 `license_type`）承载。
该变量的特征：

| 特征 | 说明 |
|:---|:---|
| **存储位置** | 进程内可写数据段（非只读、非加密） |
| **数据类型** | 整型枚举（非布尔，可取多个授权等级值） |
| **写入点** | 授权初始化流程中一次性赋值 |
| **读取点** | **多处**：标题栏渲染、功能门控、设置项可编辑性、关于框分支… |

**为什么这是致命缺陷**：

1. **单点决定全局**：全部专业版功能共享同一个状态源，改一处即全开；
2. **无完整性保护**：该变量无校验和、无加密、无防篡改；
3. **明文可定位**：数据类型简单（整型），可通过内存模式匹配定位；
4. **扩散效应**：因为它被 UI 直接引用，状态一旦改变，
   界面上的试用横幅、功能锁、提示语会**同时消失**。

**核心教训**：**"全局状态变量驱动"等于把授权开关直接暴露在进程内存里。**

---

### 3 · 密码学层：注册码校验强度不足

**观测事实**：注册码校验仅执行**短固定前缀的静态字符串匹配**，
**不包含任何数字签名**，也**不向服务端回执验证**。

**安全含义**：

| 维度 | 现状 | 应有强度 |
|:---|:---|:---|
| 校验方式 | 短前缀静态匹配 | 非对称签名验证（Ed25519 / RSA-PSS） |
| 密钥熵 | 极低（前缀空间可穷举） | ≥ 128 bit |
| 防伪能力 | 无（可离线构造通过校验的字符串） | 私钥签名，客户端不可伪造 |
| 服务端参与 | 无 | 签名凭据 + 远程吊销 |

**结论**：该校验在密码学意义上**等同于无校验** ——
它只能过滤"格式完全错误"的输入，无法区分"官方签发"与"本地伪造"。

---

### 4 · 运行时层：动态库加载路径不受控

**观测事实**：主程序启动阶段**未调用 `SetDefaultDllDirectories`**，
且存在以**不受控搜索路径**加载动态库的调用点。

**安全含义**：符合 **CWE-427（不受控搜索路径元素）** 与
**MITRE ATT&CK T1574.001（DLL 搜索顺序劫持）** 的定义。

> ⚠️ **严重性提示**：本项的严重性**高于授权绕过本身**。
> DLL 劫持使攻击者可在**父进程上下文内获得任意代码执行权** ——
> 由于是合法签名进程加载，通常不触发安全软件告警。
> 这意味着**即使用户从未关注授权问题，该缺陷依然构成真实的本地代码执行风险**。

## 可观测证据

上述结论的得出依据（研究方法，非利用步骤）：

| # | 观测项 | 方法 | 结论 |
|:---|:---|:---|:---|
| 1 | 导入表无网络 API | `dumpbin /imports` / PE 解析 | 授权完全离线 |
| 2 | 全局变量可写 | 静态定位写入点 + 运行时读取验证 | 存在单点可写状态源 |
| 3 | 状态被多处引用 | 交叉引用（Xref）分析 | 扩散效应成立 |
| 4 | 校验为前缀匹配 | 静态分析校验函数边界 | 无签名、无服务端 |
| 5 | 无 `SetDefaultDllDirectories` | 导入表 + 入口点反汇编 | 加载链不受控 |
| 6 | 本地状态与 UI 一致 | 还原后试用横幅恢复显示 | 状态驱动 UI 得到反向验证 |

> 💡 **反向验证**：执行完整还原操作后，标题栏试用提示
> （形如 `### 30 - 天试用版本 - 第 1 天 ###`）**重新出现**，
> 这从反面证实了"授权状态 → UI 表现"的驱动关系。

## 影响面

### 商业影响

- **付费墙完全失效**：客户端侧的全部专业版权益可被本地获取；
- **服务端零感知**：由于无网络交互，厂商风控**收不到任何异常信号**；
- **无法远程处置**：缺少吊销通道，已泄露的授权无法远程封禁。

### 安全影响

- **本地任意代码执行**：加载链缺陷使攻击者可在合法进程内执行代码；
- **信任链断裂**：用户无法通过"官方签名进程"这一信号判断进程是否可信；
- **横向影响**：文件管理器持有大量文件系统权限，进程被控后果严重。

### 合规影响

- 授权完全离线意味着**无法满足软件资产管理的可审计性要求**，
  对企业批量授权场景构成合规风险。

## 检测与自查

### 面向开发者：如何在自有产品中检查同类问题

```powershell
# ① 检查是否存在不受控的 DLL 加载路径
#    期望：无输出（即不存在受控风险）
dumpbin /imports .\YourApp.exe | Select-String "LoadLibrary"

# ② 检查是否调用了加载路径限定 API
#    期望：有输出（即已加固）
dumpbin /imports .\YourApp.exe | Select-String "SetDefaultDllDirectories"

# ③ 检查是否存在网络 API（判断授权是否完全离线）
#    若完全无输出 → 授权 100% 本地裁决 → 高危 CWE-602
dumpbin /imports .\YourApp.exe | Select-String "InternetOpen|WinHttp|WSAStartup"
```

```csharp
// ④ 检查代码中是否存在"全局可写授权状态"
```

## 加固方案

### 1 · 架构层：确立服务端权威（最高优先级）

| 措施 | 说明 |
|:---|:---|
| **服务端签发凭据** | 授权凭据由服务端私钥签发，客户端仅验签 |
| **引入网络校验** | 至少保留周期性（如每 7 天）的授权态复核 |
| **远程吊销能力** | 建立凭据黑名单与下发通道 |

> 📖 完整实现见 [Ed25519 离线许可体系设计](../../02-防御体系/02-Ed25519离线许可体系设计.md)

### 2 · 加载安全层：封堵 DLL 劫持

```cpp
// ✅ 程序入口点首行必须调用
int wmain()
{
    // 限定 DLL 搜索路径为系统目录 + 应用目录
    SetDefaultDllDirectories(
        LOAD_LIBRARY_SEARCH_SYSTEM32 |
        LOAD_LIBRARY_SEARCH_APPLICATION_DIR);

    // 加载非系统库时：绝对路径 + 签名校验
    HMODULE hMod = LoadLibraryExW(
        L"C:\\Program Files\\YourApp\\plugin.dll",
        nullptr,
        LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR);

    if (!hMod || !VerifyAuthenticode(hMod)) return -1;   // 拒绝启动

    return Run();
}
```

### 3 · 状态保护层：消除单点可写状态

```csharp
// ❌ 反面：全局可写状态，被多处 UI 直接读取
public static class AppState
{
    public static int LicenseType = 0;        // 明文、可写、单点
}
if (AppState.LicenseType >= 2) ShowProFeatures();

// ✅ 正面：凭据驱动 + 每次重新验签 + 用毕擦除
public sealed class EntitlementGate
{
    public static bool TryExecutePro(string feature, Action action)
    {
        // 每次调用都重新验签，不缓存布尔结果
        using var cred = LicenseStore.LoadDecrypted();
        if (cred is null) return false;

        // 1) 非对称验签（私钥在服务端）
        if (!Ed25519.Verify(cred.Signature, cred.Payload, ServerPublicKey))
            return false;

        // 2) 设备绑定
        if (!cred.Payload.MatchesDevice(DeviceFingerprint.Compute()))
            return false;

        // 3) 有效期（配合单调时钟防回拨）
        if (!cred.Payload.IsValidNow(MonotonicClock.Now)) return false;

        // 4) 功能授权位
        if (!cred.Payload.Grants(feature)) return false;

        action();            // 校验与执行合一，不暴露中间状态
        return true;
    }
}
```

### 4 · 校验强度层：迁移至非对称签名

| 现状 | 目标 |
|:---|:---|
| 短前缀静态匹配 | Ed25519 签名验证 |
| 无密钥熵要求 | 签名载荷绑定 `设备指纹 + 有效期 + Nonce` |
| 无服务端回执 | 关键权益由服务端二次确认 |

### 5 · 加固优先级建议

```
第一优先（架构级，必须做）
  ├─ 引入服务端签发凭据
  └─ 消除全局可写授权状态

第二优先（安全级，成本低收益高）
  └─ SetDefaultDllDirectories + 模块签名校验

第三优先（加固级）
  ├─ 运行时二进制完整性自检
  └─ 关键判定逻辑控制流平坦化
```
