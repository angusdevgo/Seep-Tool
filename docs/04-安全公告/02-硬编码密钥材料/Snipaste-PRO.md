> **披露状态**：待联系厂商
> **最后更新**：2026-10

## 摘要

> ### 📌 这是一个"**方向正确但实现不完整**"的典型案例，很值得学习。

Snipaste 采用了**正确的密码学方向** —— 使用 **Ed25519 非对称签名**校验授权码，
私钥保留在服务端，客户端只内置公钥。这在架构上**符合最佳实践**。

然而实现上存在两个缺口：

1. **公钥硬编码且无完整性校验** —— 公钥以明文常量形式存在于只读数据节区，
   **没有任何机制校验公钥自身是否被替换**；
2. **公钥未被多点引用** —— 单点引用意味着**只需替换一处**。

**核心教训**：**非对称签名 ≠ 绝对安全，前提是公钥本身不可被替换。**

## 攻击接入点分析 ★

### 接入点清单

| # | 接入点 | 所在组件 / 机制 | 攻击者前提 | 可获得能力 | 影响 |
|:---:|:---|:---|:---|:---|:---:|
| **AP-1** | **内嵌验签公钥** | 主程序只读数据节区中的公钥常量 | 二进制写权限（原位置换） | **用自签私钥生成的凭据即可通过验签** | 🔴 高 |
| **AP-2** | **公钥密钥流混淆层** | 公钥材料的加密/掩码处理（固定周期密钥流） | 同 AP-1 | 降低公钥替换的实现难度 | 🟠 中高 |
| **AP-3** | **持久化校验失败出口** | 授权校验失败后的持久化决策逻辑（多处出口） | 内存/二进制改写 | 免填码启动即 PRO | 🔴 高 |
| **AP-4** | **授权凭据本地存储** | 客户端读取的授权数据文件 | 用户态文件写权限 | 注入自签凭据 | 🟠 中高 |

### 接入点性质分类

| 类型 | 接入点 | 说明 |
|:---|:---|:---|
| **信任根类** | AP-1 · AP-2 | **核心缺陷** —— 非对称体系的信任根（公钥）可被替换 |
| **状态持久类** | AP-3 | 绕过持久化校验，免填码启动 |
| **凭据注入类** | AP-4 | 注入自签凭据（依赖 AP-1 成立） |

### 攻击链组合分析

| 攻击链 | 组合路径 | 门槛 | 最终效果 |
|:---|:---|:---:|:---|
| **链 A**（核心） | **AP-1 替换公钥 → AP-4 注入自签凭据** | 中 | 永久 PRO，凭据"看起来完全合法" |
| **链 B**（免验签） | AP-3 直接改写持久化出口 | 中 | 免填码启动即 PRO |
| **链 C**（降低难度） | AP-2 分析密钥流 → 辅助 AP-1 | 中 | 替换过程更易实现 |

> ⚠️ **链 A 的特殊性 —— "绕过的是信任根，而非逻辑"**：
> 该攻击**完全没有破解 Ed25519 算法**，也**没有获取服务端私钥**。
> 它绕过的是"**公钥不可替换**"这一**隐含前提**。
>
> 这带来一个严重后果：
> **攻击者签发的凭据在格式上与官方凭据完全一致** ——
> 客户端无法区分，服务端若不做二次校验也无法区分。

### 攻击面收敛建议（厂商视角）

```
接入点优先级（按风险排序）

  AP-1  信任根类    ──→ 最高优先（公钥指纹多点交叉校验 + 二进制自校验）
  AP-3  状态持久类  ──→ 消除"校验失败但持久化成功"的路径
  AP-2  混淆层类    ──→ 加固密钥流，但不可作为唯一防线
  AP-4  凭据注入类  ──→ 凭据载荷绑定设备指纹 + 有效期 + 服务端二次确认
```

## 技术细节

### 1 · 架构层：非对称方向正确，但信任根未加固

**观测事实**：

| 项 | 现状 | 评价 |
|:---|:---|:---|
| 签名算法 | **Ed25519** | ✅ 方向正确 |
| 私钥位置 | 服务端（未出现在客户端） | ✅ 符合最佳实践 |
| 客户端持有 | 仅公钥 | ✅ 正确 |
| **公钥保护** | **明文常量，无任何完整性校验** | ❌ **关键缺口** |
| **公钥引用点** | **单一位置** | ❌ 替换成本极低 |

**安全含义**：非对称体系的全部安全性建立在
"**私钥不可得**"这一前提上。但该前提**隐含了第二个前提**：

> ### 🔑 隐含前提
> **客户端内置的公钥必须是真实的、未被篡改的。**

一旦公钥可被替换，攻击者用自己的私钥签发凭据即可通过验证 ——
**Ed25519 算法本身依然安全，被绕过的是信任根的完整性。**

---

### 2 · 密码学层：公钥材料被密钥流混淆

**观测事实**：公钥并非以裸常量形式存在，而是经过**定周期密钥流**处理
（固定字节周期的掩码），运行时还原为可用公钥。

**安全含义**：

| 评价维度 | 说明 |
|:---|:---|
| **作为混淆手段** | ✅ 合理 —— 提高了静态定位门槛 |
| **作为安全边界** | ❌ 无效 —— **混淆不是加密**，密钥流可被静态还原 |
| **实际效果** | 仅延缓分析，不改变"公钥可被替换"的事实 |

**核心认知**：**混淆提升成本，但不提供任何密码学保证。**

---

### 3 · 状态层：持久化校验存在可利用路径

**观测事实**：授权校验失败后的**持久化决策**存在多个出口，
且部分出口未与验签结果严格绑定。

**安全含义**：即使不替换公钥，仅改写**持久化出口**也能达到免填码启动的效果 ——
**这是独立于 AP-1 的第二条攻击路径**。

---

### 4 · 影响评估：修复成本相对较低

**这是本案例的重要价值点**：

由于该产品**已经使用了标准非对称算法**，
修复**不需要重构整个授权体系** —— 只需**补齐公钥完整性保护**：

| 修复项 | 工作量 | 效果 |
|:---|:---|:---|
| 公钥指纹多点交叉校验 | 低 | 消除 AP-1 |
| 二进制 Authenticode 运行时自校验 | 中 | 消除 AP-1 / AP-2 |
| 持久化出口与验签结果强制绑定 | 低 | 消除 AP-3 |

> 💡 **对比参照**：与那些使用**自研对称算法**的案例（如 04 号、01 号）相比，
> 本案例的修复属于"**补短板**"，而非"**推倒重建**"。

## 影响面

### 商业影响

- 可自行签发有效授权码，实现永久激活；
- **该缺陷不影响服务端私钥安全** —— 服务端资产未泄露；
- **修复成本较低**（补充公钥完整性校验即可），是厂商可快速处置的窗口。

### 安全影响

- 信任根可被替换，**非对称体系的完整性保证失效**；
- 攻击者签发的凭据与官方凭据**格式一致**，服务端侧难以区分；
- 二进制可被原位置换而不改变文件大小，**哈希校验可被规避**。

### 合规影响

- 公钥可替换意味着软件完整性保证不成立，
  可能不满足企业终端的代码完整性基线要求。

## 检测与自查

### 面向开发者

```powershell
# ① 检查公钥是否位于可写节区
dumpbin /headers .\YourApp.exe | Select-String -Pattern "\.data|\.rdata"

# ② 检查是否实施了二进制完整性自检
dumpbin /imports .\YourApp.exe | Select-String "WinVerifyTrust|CryptHashData"

# ③ 检查公钥引用点数量（引用点越多越安全）
#    使用静态分析工具统计公钥常量的交叉引用次数
```

```csharp
// ④ 检查代码中是否校验了公钥自身完整性
//    ❌ 反例：直接用公钥验签，从不校验公钥本身
Ed25519.Verify(sig, msg, PublicKey);

//    ✅ 正例：先校验公钥指纹，再验签
if (!VerifyPublicKeyFingerprint()) return Fail();   // 公钥完整性
if (!Ed25519.Verify(sig, msg, PublicKey)) return Fail();
```

|:---|:---|

## 加固方案

### 1 · 公钥保护层（最高优先级，成本最低）

```csharp
// ✅ 公钥指纹多点交叉校验
public static class LicenseVerifier
{
    // 公钥（公开信息，泄露无害）
    private static readonly byte[] PublicKey = Convert.FromBase64String(
        "MCowBQYDK2VwAyEA...");

    // 公钥指纹（SHA-256 前 16 字节）
    private static readonly byte[] PublicKeyFingerprint = Convert.FromHexString(
        "3A7F9C2E...");

    /// <summary>公钥完整性校验 —— 应在多处不相关的位置重复调用</summary>
    private static bool VerifyPublicKeyIntegrity()
    {
        byte[] actual = SHA256.HashData(PublicKey);
        for (int i = 0; i < PublicKeyFingerprint.Length; i++)
            if (actual[i] != PublicKeyFingerprint[i]) return false;
        return true;
    }

    public static bool Verify(byte[] msg, byte[] sig)
    {
        // ① 先校验公钥完整性
        if (!VerifyPublicKeyIntegrity()) return false;

        // ② 再验签
        return Ed25519.Verify(sig, msg, PublicKey);
    }
}
```

**关键点 —— 多点交叉校验**：

```
❌ 单点引用（当前状态）
   [校验函数 A]  ──引用──→ [公钥]     ← 替换公钥只需改一处

✅ 多点交叉引用（加固后）
   [校验函数 A]  ─┐
   [启动自检 B]  ─┼──引用──→ [公钥]     ← 攻击者须同时处理全部引用点
   [关键功能 C]  ─┤
   [定时自检 D]  ─┘
```

### 2 · 完整性层：绑定 Authenticode

```csharp
// ✅ 运行时校验自身二进制签名（与公钥校验联动）
public static bool VerifySelfIntegrity()
{
    string selfPath = Process.GetCurrentProcess().MainModule.FileName;

    // Authenticode 签名校验
    if (!WinVerifyTrust(selfPath)) return false;

    // 关键代码段哈希与编译期预置值比对
    byte[] codeHash = ComputeCodeSectionHash(selfPath);
    return CryptographicOperations.FixedTimeEquals(codeHash, ExpectedCodeHash);
}

// 建议在多个时机重复调用：启动 / 关键操作前 / 定时
```

### 3 · 载荷层：强化凭据绑定

```csharp
// ✅ 签名载荷强制包含设备指纹 + 有效期 + Nonce
public sealed class LicensePayload
{
    public string DeviceHash { get; set; }   // SHA-256(设备指纹)
    public long   ExpiresAt  { get; set; }   // 有效期
    public string Nonce      { get; set; }   // 防重放
    public string[] Features { get; set; }   // 权限位图
}
```

**验证时必须逐项检查**：设备绑定、有效期（配合单调时钟防回拨）、Nonce 新鲜度。

### 4 · 持久化层

| 措施 | 说明 |
|:---|:---|
| 强制绑定 | 持久化写入必须与验签结果强绑定 |
| 消除旁路 | 移除"校验失败但持久化成功"的路径 |
| Fail-Closed | 校验不确定时一律按未授权处理 |

### 5 · 纵深兜底

| 措施 | 说明 |
|:---|:---|
| **服务端异步确认** | 关键权益由服务端二次确认，离线凭据仅作临时宽限 |
| **远程吊销** | 服务端记录凭据指纹，异常模式告警 |

### 6 · 加固优先级

```
第一优先（成本最低，收益最高）
  ├─ 公钥指纹多点交叉校验                        ← 消除 AP-1
  └─ 持久化出口与验签结果强制绑定                 ← 消除 AP-3

第二优先
  └─ 二进制 Authenticode 运行时自校验             ← 消除 AP-1 / AP-2

第三优先（纵深兜底）
  ├─ 载荷绑定设备指纹 + 有效期 + Nonce
  └─ 服务端异步二次确认 + 远程吊销
```

> 📌 **对厂商的提示**：本案例是**修复性价比最高**的样本 ——
> 架构方向已经正确，只需补齐"公钥完整性"这一个短板。
