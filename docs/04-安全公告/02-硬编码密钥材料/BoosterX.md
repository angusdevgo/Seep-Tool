### 架构层根因分析

该产品采用了**商业级混淆器全保护模式**（符号重命名 + 字符串加密 + 程序集代码加密 + 代码虚拟化），
保护强度在同类产品中属于上乘。但审计结果表明：
**混淆与虚拟化只能提高分析成本，无法改变"裁决权在客户端"这一架构事实。**
本案例的价值恰在于它提供了一个"**保护层很厚、架构层很薄**"的典型样本。

该产品存在**四处彼此独立的架构缺陷**，可被分别或组合利用：

**缺陷一：付费权益（PRO）的裁决权完全在客户端**（模式 1）

产品的付费权益由**本地布尔量**决定：全部功能设置项中存在若干项在构造时被打上"PRO 专属"标记，
另有一个**全局授权态查询入口**被多处 UI 与业务逻辑（激活页状态显示、任务执行流程、
设置项可编辑性、页面级功能门控）直接引用。

整个权益判定链路**不依赖任何服务端签发的权益凭证** —— 客户端既是运动员又是裁判。
一旦该布尔量的判定被改写，绕过效果会**自动扩散到所有引用点**，无需逐处处理。

**缺陷二：授权校验存在 Fail-Open 短路**（模式 7 · 本案例新识别模式）

启动期授权装载流程中，判定点的语义是"**凭据是否为空 / 无效**"。
当凭据为 `null`、空字符串或字面量 `"null"` 时，客户端将其解释为"**无需校验**"，
直接跳入"校验通过"分支 —— **整个过程中不向服务端发起任何请求**。

这是典型的 **Fail-Open** 设计：把"**无法判定**"错误地当作"**判定通过**"。
安全上正确的做法应当是 **Fail-Closed**：凭据缺失或无效时一律视为校验失败。

该缺陷的严重性在于：它**不需要任何代码修改**，仅靠一份空配置即可触发，
且在流量层表现为"客户端完全静默"，难以被服务端侧的风控发现。

**缺陷三：特权状态存放于用户可写位置**（模式 4）

全部功能开关（含所有 PRO 相关开关，共数十项）以**明文布尔值**存放于当前用户注册表 hive。
该位置任何用户态进程均可读写，且客户端读取后**未做任何完整性或来源校验**。

这意味着：**无需触碰二进制文件**，仅靠配置写入即可改变功能行为。

**缺陷四：传输层与密钥材料缺陷**（模式 2）

授权校验接口走 **明文 HTTP**，且请求/响应体仅用**全局硬编码的对称密钥**加密。
由于该密钥随客户端分发，任何持有客户端的攻击者都能离线解密历史流量并自行构造
格式合法的授权响应。

**核心教训**：
1. **保护层 ≠ 安全架构** —— 代码虚拟化把分析成本从"小时级"提升到"天级"，
   但一旦架构层存在"裁决权在客户端"的根本缺陷，最终仍会被突破；
2. **Fail-Open 是最危险的鉴权反模式** —— 它让"配置缺失"变成了"免检通道"；
3. **布尔量是授权体系的最弱环节** —— 无论它藏得多深，本质都只是一个可被翻转的状态位。

### 影响面

- **付费墙失效**：客户端侧的全部 PRO 权益可被离线获取，授权体系丧失商业保护能力；
- **服务端不可感知**：客户端在旁路状态下完全不发请求，服务端风控无任何异常信号；
- **明文传输泄露**：授权协议与硬编码密钥暴露，可被离线分析并用于伪造响应；
- **横向扩散**：由于授权态被多处 UI 直接引用，单一判定点的失守会自动扩散至整个界面；
- **合规风险**：明文 HTTP 传输授权相关数据，可能不符合数据安全传输的合规要求。

### 审计要点

审计同类"重型混淆 + 本地授权"实现时，重点关注：

1. **剥离保护层看架构**：不要被混淆强度吓退 —— 先问"**最终裁决权在谁手里**"，
   再决定是否值得投入时间还原被保护逻辑；
2. **枚举权益判定出口**：统计"PRO 专属"标记的**总数**，以及授权态查询入口的**被引用次数**
   —— 引用点越多，单点失守的扩散面越大；
3. **审计鉴权分支的空值语义**：逐一检查"凭据为空 / 缺失 / 格式错误"时程序走向哪个分支，
   重点找 **Fail-Open** 短路；
4. **检查本地状态的存放位置与完整性**：特权状态是否落在用户可写位置？读取时是否校验完整性？
5. **检查传输层与密钥来源**：授权接口是否强制 HTTPS？密钥是协商产生还是随包分发？
6. **识别代码虚拟化的还原特征**：虚拟化保护常伴随"方法名自描述令牌"
   （名称本身编码了方法在字节码流中的位置）与"位置相关的流加密"，
   这类设计一旦被识别，整条保护链可被系统性还原。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **架构** | 确立"**服务端权威**"：客户端只持有并呈递凭据，不参与"是否付费"的裁决；核心权益对应的资源/数据由服务端加密下发 |
| **鉴权逻辑** | 全面改为 **Fail-Closed**：凭据缺失、为空、格式非法一律判定失败；消除"空值即通过"的所有分支 |
| **凭据形态** | 改用**非对称签名凭据**（Ed25519 / RSA-PSS）：服务端私钥签发，客户端仅做验签；绑定硬件指纹与有效期，支持远程吊销 |
| **传输层** | 全链路 HTTPS + 证书绑定（SSL Pinning）；移除裸 IP 兜底地址；请求加入 Nonce + 时戳 + 请求签名防重放 |
| **密钥管理** | 移除随包分发的对称密钥，改为每次会话协商的临时密钥（ECDH）+ 服务端签名 |
| **本地状态** | 本地配置仅作为"用户偏好"，**不得作为权益判据**；权益判据必须来自签名凭据 |
| **运行时** | 关键判定下沉 Native 并做完整性自校验；现有反篡改机制应"解不开即拒绝运行"，而非静默降级 |
| **兜底** | 服务端记录授权请求的设备指纹与频率，对异常模式告警；关键权益接口做服务端二次鉴权 |
