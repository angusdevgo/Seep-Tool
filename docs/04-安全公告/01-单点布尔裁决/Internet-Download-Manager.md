# Internet Download Manager · 单点布尔裁决

> **公告编号**：11
> **缺陷模式**：模式 01 · 单点布尔裁决（兼：模式 04 · 可写全局状态变量）
> **关联 CWE**：`CWE-602`
> **风险等级**：🔴 高
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

Internet Download Manager（下称 IDM）的授权裁决最终收敛于**客户端本地**的
一组布尔判定与状态标志。攻击者只需在客户端二进制的**判定面**上实施改动，
即可在完全不接触服务端协议的情况下解锁全部授权权益。

本案例最具警示价值的发现是：**该产品为对抗篡改布置了多达六个守护线程与一个
看门狗关联函数，却未能改变任何结论** —— 因为所有这些对抗措施与授权裁决处于
**同一信任层级**（均运行在同一进程、同一权限、同一台机器上）。
对抗强度与裁决位置是两个**正交维度**，前者无法弥补后者。

另一项典型教训：**官方更新机制会静默覆盖已改动的二进制**，
而社区流传的注册表"屏蔽更新"配方中包含至少一项**从未被程序读取的伪配置**，
以及一项**删除后反而加速更新探测的时间戳键**。
这印证了审计中的普遍规律：**对未经验证的"公开配方"必须逐项做二进制级证实**。

> ⚠️ **本案例的特殊警示 —— "高强度对抗"的假象**：
>
> IDM 是本系列**对抗措施数量最多的样本**（6 守护线程 + 1 看门狗 + 完整性联动）。
> 但逐一审计后发现：
>
> * 六个守护线程**彼此冗余** —— 它们做的是同类周期性校验，缺谁都不影响结论；
> * 看门狗与守护线程**共享代码折叠**（编译器 COMDAT 优化所致），
>   说明它们在二进制层面就已是同一段代码的复用；
> * 所有对抗措施都运行在**同一进程、同一权限、同一台机器** ——
>   与授权裁决处于同一信任层级。
>
> **核心教训**：**对抗措施的数量与裁决位置的正确性是两个正交维度。**
> 只要裁决在客户端，布置一百个守护线程也只是把"改一处"变成"改一百零一处"。
> 真正的修正只有一条路：**把裁决权移到服务端**。

## 技术细节

### 层级一：授权判定层（观测事实 → 安全含义 → 核心教训）

**观测事实**：主程序内存在一条授权状态条件判定链，
其分支形态为"对校验结果做等值测试，非零则进入授权路径"。
该判定在进程启动早期即执行一次，其结果被缓存在全局可写内存中。

**安全含义**：判定本身完全依赖客户端可得的输入（注册表状态 + 二进制内常量），
**没有任何服务端参与**。条件分支指令的语义反转即可让判定永远走向"已授权"分支。

**核心教训**：**条件判定是客户端授权最常见的单点**。
修正方案不是把判定改复杂，而是让"判定的输入"必须由服务端签发且无法本地伪造。

### 层级二：试用与常量层

**观测事实**：试用期天数由数据段中的常量参与计算，上界值与试用标志位相邻存放；
两处均可被用户态直接改写。

**安全含义**：即使授权分支保持原样，仅改写数据段常量即可将试用上界提升至实际无限，
并让试用状态标志呈现"已激活"语义。**数据段与代码段同等脆弱**，
而多数开发者只对代码段有防御直觉。

**核心教训**：**授权相关的常量必须由服务端随凭据下发**，
而不是编译期固化在客户端二进制里。

### 层级三：对抗线程层

**观测事实**：六个守护线程以不同周期轮询授权状态，任一检测到篡改即触发响应；
一个看门狗函数与之联动做兜底。全部线程的入口函数在二进制中高度相似，
部分甚至被编译器折叠为共享代码。

**安全含义**：线程的启动点位于客户端代码内，
入口指令的改写（如替换为立即返回）即可让全部轮询成为死代码。
**对抗方与攻击方在同一权限平面运行**，任何"检测→响应"逻辑都可以被连同检测者一起修改。

**核心教训**：**同权限平面内的自我监控无法对抗同平面的攻击者。**
完整性校验必须由**进程外、更高权限、独立信任根**的组件执行（如受保护的系统服务），
且该校验本身必须防篡改 —— 否则只是增加了攻击者的补丁位点数量。

### 层级四：更新与状态持久层

**观测事实**：
1. 程序启动时安装一个后台更新定时器，周期到点后经系统网络栈探测官方更新；
2. 更新下载成功后**静默替换主程序**，本地改动随之丢失；
3. 注册表中存在一个记录"上次快速更新时间"的时间戳键；
4. 社区流传的"屏蔽更新"配方包含一项从未被程序读取的键，
   以及"删除上述时间戳键"的步骤。

**安全含义**：
1. 静默替换是**对防御方有利的自带修复通道**（官方新版本可能修复旧版缺陷）；
2. 但对已改动的客户端而言，它同时也是"改动丢失"的第一大原因；
3. "从未被读取的键"证明部分社区配方是**纯粹的仪式性行为**（安慰剂）；
4. "删除时间戳键反而触发强制更新探测"证明部分配方**存在反向效果**。

**核心教训**：**任何"公开配方"都必须在二进制级逐项证实。**
审计方法论上，判定一个配置项是否有效，唯一可靠的方式是确认
"程序在读取路径上确实引用了它"（如运行时钩取注册表 API 观测读取行为），
而不是"写入了它之后现象消失"—— 后者存在大量混淆因素。

> 而是证明**程序根本不读它**。这一条直接推翻了流传多年的社区实践。

## 影响面

### 商业影响

* 授权收入完全依赖客户端状态，**技术门槛极低的改写即可绕过付费**；
* 对抗措施（六线程 + 看门狗）显著增加了产品复杂度与维护成本，
  却**未提高任何攻击成本** —— 投入产出严重倒挂；
* 官方更新通道与本地改动相互冲突，形成"更新丢激活 / 不更新留缺陷"的两难。

### 安全影响

* 客户端授权逻辑的复杂对抗代码**扩大了攻击面**：
  每个守护线程都是可被逆向利用的代码入口；
* 无完整性自检意味着**任何第三方都能分发修改版二进制**，
  终端用户无从分辨 —— 修改版分发链本身成为恶意软件传播载体；
* 静默更新机制若被劫持（DNS / 代理层面），可向已装用户**推送任意替换二进制**。

### 合规影响

* 授权裁决客户端化属于 **CWE-602** 架构缺陷，
  在软件采购安全评估中通常被列为**高风险项**；
* 修改版二进制分发涉及著作权侵权，终端用户面临法律风险。

## 检测与自查

### 面向开发者

**自查一：授权判定是否只依赖客户端输入？**

```csharp
// 反模式：判定输入全部来自本地
bool isLicensed = ReadRegistrySerial() != null
               && CheckLocalSerial(serial);   // 校验也在本地

// 修正方向：判定输入必须由服务端签发
// 客户端只持有凭据并呈递，裁决在服务端完成
LicenseToken tok = await server.IssueChallenge(deviceId);
bool ok = server.Verify(tok);                 // 服务端裁决
```

**自查二：是否存在"同权限平面的自我监控"？**

```csharp
// 反模式：同进程内线程监控自己的内存
var watchdog = new Thread(() => {
    while (true) {
        if (ComputeState() != Expected) Shutdown();
        Thread.Sleep(PollInterval);
    }
});

// 修正方向：进程外独立信任根（受保护服务 / 驱动级 /
// 或至少是带独立签名的看门狗进程 + IPC 鉴权）
```

**自查三：更新前是否校验自身完整性？**

```
反模式：更新器直接下载替换主程序。
修正：更新器先对当前主程序做签名复核；校验失败 → 视为被篡改，
走重装流程而非静默覆盖（静默覆盖会把"被篡改"状态洗白成"正常"）。
```

### 面向用户

* 从官方渠道获取安装包，核对发布签名；
* 警惕任何"修改版 / 激活版"二进制 —— 无法验证其未捆绑恶意负载；
* 不要信任来历不明的"屏蔽更新"注册表配方 —— 本案例已证明其中
  既存在无效项也存在反效果项。

## 加固方案

### 优先级路线图

| 优先级 | 措施 | 解决的接入点 | 成本 |
|:---:|:---|:---|:---:|
| **P0** | 授权裁决移至服务端：客户端仅持有不可自签的服务端凭据 | AP-1 / AP-2 / AP-7 / AP-8 | 高 |
| **P0** | 移除"客户端判定即生效"的分支结构，改为"服务端会话有效才启用功能" | AP-1 | 高 |
| **P1** | 试用期常量与状态由服务端下发并随凭据签名 | AP-2 / AP-8 | 中 |
| **P1** | 更新器增加自身与主程序的签名复核 | AP-11 / AP-12 | 中 |
| **P2** | 收敛冗余守护线程（六线程无法补救架构缺陷，只增加维护与攻击面） | AP-4 / AP-5 | 低 |
| **P2** | 注册对话框等体验性防御降级为服务端会话校验的一部分 | AP-3 | 低 |
| **P3** | 控制流混淆（仅提高成本，不解决架构） | AP-11（部分） | 中 |

### 修正后的参考架构

```
┌──────────────────────────────┐      ┌──────────────────────────────┐
│  客户端（不可信平面）            │      │  服务端（权威平面）             │
│                              │      │                              │
│  持有: 设备指纹 + 服务端签发的    │      │  签发: 授权会话令牌             │
│        会话令牌（短时效）         │ ◀── │        （Ed25519 签名）        │
│                              │      │  裁决: 每次功能调用验令牌        │
│  无任何"本地判定即生效"的分支     │      │  审计: 异常模式检测             │
│  无试用期本地常量               │      │                              │
│  更新器带双向签名复核            │      │  下发: 版本 + 常量随令牌签发     │
└──────────────────────────────┘      └──────────────────────────────┘
```

> **核心原则**：客户端可以**离线降级运行**（这是桌面软件的合理需求），
> 但**降级后的权益边界必须由上次会话的签发内容决定**，
> 而不是由客户端本地任何可写状态决定。
