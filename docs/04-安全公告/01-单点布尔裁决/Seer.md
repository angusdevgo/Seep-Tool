# Seer · 单点布尔裁决

> **公告编号**：06
> **缺陷模式**：模式 01 · 单点布尔裁决
> **关联 CWE**：`CWE-602`
> **风险等级**：🔴 高
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

Seer 的授权判定集中在**单一决策函数**上：一个 `isLicensed()` 判定决定全部授权状态；
另一个独立函数负责试用倒计时与购买弹窗的触发。

该产品**尝试了"双点防护"**（授权判定 + 弹窗拦截），
但由于两个点都处于**同一层级（均为客户端本地逻辑）**，
防护效果**等同于单点** —— 且因二进制未做控制流混淆，
判定入口可被直接定位。

## 攻击接入点分析 ★

### 接入点清单

| # | 接入点 | 所在组件 / 机制 | 攻击者前提 | 可获得能力 | 影响 |
|:---:|:---|:---|:---|:---|:---:|
| **AP-1** | **授权判定函数** | 主程序 `AppLicenser` 模块的 `isLicensed` 判定入口 | 本地二进制改写 / 进程内存修补 | **单点改写即可解锁全部特权** | 🔴 高 |
| **AP-2** | **试用限制与弹窗封装** | 独立的试用倒计时 / 购买弹窗触发函数 | 同 AP-1 | 消除倒计时与模态弹窗 | 🔴 高 |
| **AP-3** | **试用期本地计数** | 试用天数记录的本地存储 | 用户态文件/注册表写权限 | 重置试用周期 | 🟡 中 |
| **AP-4** | **主程序二进制自身** | 无完整性自检、无控制流混淆 | 文件写权限 | 单点补丁即生效，且无对抗措施 | 🟠 中高 |

### 接入点性质分类

| 类型 | 接入点 | 说明 |
|:---|:---|:---|
| **授权裁决类** | AP-1 | **核心缺陷** —— 单点决定全部特权 |
| **限制解除类** | AP-2 | 与 AP-1 同层级，不构成独立防护 |
| **状态重置类** | AP-3 | 影响试用周期 |
| **对抗缺失类** | AP-4 | 攻击成本极低的直接原因 |

### 攻击链组合分析

| 攻击链 | 组合路径 | 门槛 | 最终效果 |
|:---|:---|:---:|:---|
| **链 A**（单点突破） | AP-1 单独改写 | **极低** | 全部特权解锁 |
| **链 B**（体验完整） | AP-1 + AP-2 | 极低 | 权限解锁 + 无弹窗干扰 |
| **链 C**（长期试用） | AP-3 重置计数 | 极低 | 试用期无限延长 |

> ⚠️ **本案例的特殊警示 —— "双点防护"的假象**：
> 该产品在设计上确实布置了**两个防护点**（授权判定 + 弹窗拦截），
> 看起来更安全。但两者处于**同一层级**（都是客户端本地逻辑），
> 因此：
> * **不构成纵深防御** —— 纵深防御要求不同层级、不同机制；
> * **防护强度等于单点** —— 攻击者只需分别处理两个函数即可；
> * **反而暴露了两个入口** —— 增加了攻击面。
>
> **核心教训**：**"同一层级的多点"不是纵深防御，只是把单点拆成了两点。**

### 攻击面收敛建议（厂商视角）

```
接入点优先级（按风险排序）

  AP-1  授权裁决类  ──→ 最高优先（改为服务端签名凭据驱动）
  AP-4  对抗缺失类  ──→ 引入控制流平坦化 + 二进制完整性自检
  AP-2  限制解除类  ──→ 与 AP-1 合并为同一凭据校验
  AP-3  状态重置类  ──→ 试用状态改由服务端记录
```

## 技术细节

### 1 · 决策层：授权由单一函数决定

**观测事实**：授权状态由一个判定函数的返回值完全决定，
该返回值为**显式的布尔量**，可通过单条指令改写。

**安全含义**：

| 问题 | 后果 |
|:---|:---|
| 单点决定全局 | 改一处即解锁全部 |
| 返回值为显式布尔量 | 攻击成本极低（无需理解逻辑） |
| 无完整性保护 | 无校验和、无加密、无防篡改 |
| 未做控制流混淆 | 判定入口可被直接定位 |

**核心教训**：**"单点故障"式的安全设计，在最坏情况下只需一条指令即可瓦解。**

---

### 2 · 架构层：双点防护的层级错配

**观测事实**：产品布置了授权判定与弹窗拦截两个防护点，
但二者处于**同一层级**。

**为什么这不构成纵深防御**：

```
❌ 当前结构（同层双点 —— 无效纵深）
   ┌─────────────────────────────────┐
   │  客户端本地逻辑层                 │
   │   ├─ 判定点 1: isLicensed        │  ← 同一层
   │   └─ 判定点 2: 弹窗/倒计时拦截    │  ← 同一层
   └─────────────────────────────────┘
   攻击者突破该层后，两个点同时失守

✅ 应有结构（跨层纵深）
   ┌─────────────────────────────────┐
   │  第 1 层: 服务端签名凭据校验      │  ← 架构层
   ├─────────────────────────────────┤
   │  第 2 层: 运行时完整性自检        │  ← 运行时层
   ├─────────────────────────────────┤
   │  第 3 层: 关键逻辑混淆/虚拟化     │  ← 代码形态层
   └─────────────────────────────────┘
   任一层被突破，其他层仍然有效
```

**结论**：**纵深防御的关键是"层级差异"，而非"数量堆叠"。**

---

### 3 · 对抗层：二进制无任何防护措施

**观测事实**：主程序**未做控制流混淆**，也未实施运行时完整性自检。

**安全含义**：判定入口可被静态分析工具直接定位，
攻击成本**在所有样本中属于最低梯队** —— 因此本案例
**适合作安全教学的入门样本**（理解 CWE-602 的最简形态）。

## 影响面

### 商业影响

- 攻击者可永久解除试用限制，无限期使用完整功能；
- 试用倒计时机制形同虚设，**产品无法有效转化付费用户**；
- 攻击面清晰且唯一，**商业保护能力实质为零**。

### 安全影响

- 主程序无完整性自检，可被植入修改版本分发；
- 无混淆保护，降低了恶意改造的技术门槛。

### 合规影响

- 缺乏对抗措施可能不满足部分企业终端的软件完整性基线。

## 加固方案

### 1 · 架构层：分散化 + 绑定

```csharp
// ❌ 反面：单点判定
if (LicenseManager.IsLicensed()) { EnableAllFeatures(); }

// ✅ 正面：多点交叉 + 校验与执行合一
public static class FeatureGate
{
    public static bool TryExecute(string feature, Action action)
    {
        using var cred = LicenseStore.LoadDecrypted();
        if (cred is null) return false;
        if (!Ed25519.Verify(cred.Signature, cred.Payload, ServerPublicKey)) return false;
        if (!cred.Payload.MatchesDevice(DeviceFingerprint.Compute()))       return false;
        if (!cred.Payload.IsValidNow(MonotonicClock.Now))                   return false;
        if (!cred.Payload.Grants(feature))                                  return false;
        action();
        return true;
    }
}
```

**要点**：**特权功能实现中内嵌校验，而非先判后用。**

### 2 · 对抗层：跨层纵深

| 层级 | 措施 |
|:---|:---|
| **架构层** | 服务端签名凭据（本案例完全缺失） |
| **运行时层** | 二进制 Authenticode 运行时自校验 |
| **代码形态层** | 关键判定**控制流平坦化**（OLLVM） |
| **虚拟化** | 授权核心逻辑使用 **VMP** 保护 |

```cpp
// ✅ 控制流平坦化的效果示意
// 混淆前：清晰的判定分支
if (IsLicensed()) { EnablePro(); } else { ShowTrial(); }
// 混淆后：状态机分发，消除直接的 cmp/test + jz 模式
while (state != END) {
    switch (dispatcher[state]) {
        case 0x3F2A: state = cond ? 0x11B4 : 0x9C07; break;
        case 0x11B4: EnablePro();  state = END; break;
        case 0x9C07: ShowTrial();  state = END; break;
        /* 大量虚假分支 */
    }
}
```

### 3 · 加固优先级

```
第一优先（架构级）
  └─ 授权判定改为服务端签名凭据驱动              ← 消除 AP-1 的根本原因

第二优先（成本低）
  ├─ 二进制完整性自检（多时机重复校验）           ← 缓解 AP-4
  └─ 试用状态改由服务端记录                       ← 消除 AP-3

第三优先
  ├─ 关键判定控制流平坦化                        ← 提高分析成本
  └─ 授权核心 VMP 保护
```
