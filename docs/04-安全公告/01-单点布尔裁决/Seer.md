### 架构层根因分析

该产品的授权判定集中在**单一决策函数**上：
一个 `isLicensed()` 判定决定全部授权状态，
另一个独立的函数负责试用倒计时与购买弹窗的触发。

**这是"单点故障"式的安全设计**：
- 授权状态由一个函数的返回值完全决定；
- 该函数的返回值是**显式的布尔量**，可通过单条指令改写；
- 试用期的限制逻辑与授权判定**完全解耦**，因此可以独立解除；
- 二进制未做控制流混淆，判定入口可被直接定位。

值得注意的是，该产品**尝试了"双点防护"**（授权判定 + 弹窗拦截），
但由于两个点都是**同一层级的客户端逻辑**，防护效果等同于单点。

### 影响面

- 攻击者可永久解除试用限制，无限期使用完整功能；
- 试用倒计时机制形同虚设，产品无法有效转化付费用户；
- 攻击面清晰且唯一，**攻击成本极低**（适合作为入门级研究样本）。

### 审计要点

1. 授权判定是否集中在**单一函数**；
2. 该函数的返回值是否**直接控制**全部特权；
3. 是否存在"补丁一个点就能解锁全部"的结构；
4. 是否有反调试、控制流混淆等对抗措施。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **分散化** | 授权校验**多点交叉**：在 3~5 处不相关的代码路径中重复校验 |
| **绑定** | 特权功能实现中**内嵌**授权校验，而非先判后用 |
| **混淆** | 关键判定采用**控制流平坦化 + 虚假控制流**（OLLVM） |
| **虚拟化** | 授权核心逻辑使用 **VMP** 保护，消除直接的 `cmp/test` 模式 |
