# PixPin · 单点布尔裁决

> **公告编号**：05
> **缺陷模式**：模式 01 · 单点布尔裁决
> **关联 CWE**：`CWE-602`
> **风险等级**：🔴 高
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

PixPin 的 **14 项会员功能**，每一项都由独立动态链接库中的
**独立导出布尔函数**（形如 `IsVipFeatureXxx()`）判定是否开放。

这种设计存在**三重架构缺陷**：判定点分散且显式、判定与业务解耦、
模块自身无完整性保护。结果是**攻击面从 1 个扩大到 14 个**，
且由于判定与实现之间存在清晰边界，**让判定恒真即等于全部功能开放**。

## 攻击接入点分析 ★

### 接入点清单

| # | 接入点 | 所在组件 / 机制 | 攻击者前提 | 可获得能力 | 影响 |
|:---:|:---|:---|:---|:---|:---:|
| **AP-1** | **鉴权库导出判定函数** | 动态链接库中 **14 个独立导出布尔函数** | 可替换/改写该 DLL 或进程内存 | 逐项解锁会员功能（14 个独立入口） | 🔴 高 |
| **AP-2** | **鉴权库模块自身** | 该 DLL **无自身完整性校验**，也未与主程序交叉验证 | 文件写权限 | 整体替换判定逻辑 | 🔴 高 |
| **AP-3** | **判定与业务的调用边界** | 判定函数仅返回布尔值，与功能实现**完全解耦** | 同 AP-1 | **单点恒真即全部业务开放** | 🔴 高 |
| **AP-4** | **云端配置 / 更新检查通道** | 云控通信链路 | 网络层/本地拦截 | 屏蔽云控下发与更新检测 | 🟠 中高 |
| **AP-5** | **大模型翻译端点配置** | 用户可配置的 API 端点与密钥 | 用户态配置写权限 | 指向自建端点（属设计特性，非绕过） | 🟢 低 |

### 接入点性质分类

| 类型 | 接入点 | 说明 |
|:---|:---|:---|
| **判定点类** | AP-1 · AP-3 | 14 个独立判定入口，**修复需重构 14 处调用关系** |
| **模块完整类** | AP-2 | 鉴权模块可被整体替换，无交叉验证 |
| **云控类** | AP-4 | 影响厂商的下发与管控能力 |
| **配置类** | AP-5 | 设计上允许，非安全缺陷 |

### 攻击链组合分析

| 攻击链 | 组合路径 | 门槛 | 最终效果 |
|:---|:---|:---:|:---|
| **链 A**（最小改动） | 改写 **任意 1 个** AP-1 判定点 | 低 | 对应 1 项功能开放 |
| **链 B**（全量开放） | 批量改写 **14 个** AP-1 判定点 | 中 | 14 项会员功能全解锁 |
| **链 C**（整体替换） | AP-2 替换整个鉴权模块 | 中 | 一次性解决全部判定点 |
| **链 D**（云控规避） | AP-4 拦截云控通道 | 低 | 屏蔽下发与更新，状态长期稳定 |

> ⚠️ **链 C 的高效性揭示了架构问题的本质**：
> 因为鉴权逻辑**集中在一个可替换的模块中**且无完整性校验，
> 攻击者无需逐个处理 14 个判定点，**整体替换即可**。
>
> **这印证了核心教训**：把鉴权逻辑单独封装成一个模块，
> 在架构上等于给攻击者提供了一个**清晰的替换边界**。

### 攻击面收敛建议（厂商视角）

```
接入点优先级（按风险排序）

  AP-2  模块完整类  ──→ 最高优先（鉴权模块加自身哈希校验 + 与主程序交叉验证）
  AP-3  调用边界类  ──→ 架构级重构（判定内联进业务实现，取消中间布尔层）
  AP-1  判定点类    ──→ 取消导出符号，避免被工具直接枚举
  AP-4  云控类      ──→ 通道签名 + 响应验签 + Fail-Closed
  AP-5  配置类      ──→ 设计特性，无需整改
```

## 技术细节

### 1 · 决策层：14 个分散的显式判定点

**观测事实**：会员功能判定由鉴权库中**独立导出的布尔函数**承担，
每个函数对应一项功能，形如 `IsVipFeatureXxx()`。

**安全含义**：

| 问题 | 后果 |
|:---|:---|
| **导出符号可见** | 可用 `dumpbin /exports` 等标准工具直接枚举全部判定点 |
| **判定点分散（14 个）** | 攻击面从 1 扩大到 14，**修复成本同步放大** |
| **逻辑简单（单点分支）** | 每个判定函数体量小，分析成本极低 |

**核心教训**：**导出符号本身就是攻击面的索引。**

---

### 2 · 架构层：判定与业务解耦

**观测事实**：判定函数**只返回布尔值**，与真正的功能实现之间存在**清晰的调用边界**。

**为什么这是架构缺陷**：

```
❌ 当前结构（分层）
   [判定层: IsVipFeatureA() → bool]  ← 攻击者只需攻击这一层
              ↓ 清晰边界
   [业务层: 功能 A 的真实实现]

✅ 应有结构（合一）
   [功能 A 的实现内部内嵌校验]
   → 无独立判定出口，攻击者无法通过单点恒真解锁
```

**结论**：**把"是否允许"和"如何实现"分成两层，
等于把前者变成一个可以单独攻破的开关。**

---

### 3 · 完整性层：鉴权模块无自校验

**观测事实**：鉴权动态库**未做自身完整性校验**，
也未与主程序或其他模块做交叉验证。

**安全含义**：

| 维度 | 现状 | 应有措施 |
|:---|:---|:---|
| 模块自校验 | 无 | 自身哈希校验 |
| 交叉验证 | 无 | 与主程序互相校验 |
| 替换检测 | 无 | 加载时校验 Authenticode 签名 |

**后果**：模块可被**整体替换**，一次性绕过全部 14 个判定点。

---

### 4 · 云控层：下发通道可被拦截

**观测事实**：云端配置下发与更新检查通道**未做完整性保护**。

**安全含义**：厂商对客户端的**远程管控能力受限** ——
可被单方面屏蔽，且厂商难以感知。

## 影响面

### 商业影响

- 14 项 VIP 功能可被全部解锁（长截图、离线 OCR、翻译、高级标注等）；
- **修复成本高** —— 需重构 14 处调用关系，而非打一个补丁；
- 云控更新与配置下发可被屏蔽，厂商管控能力下降。

### 安全影响

- 鉴权模块可被整体替换，**为加载伪造模块提供了便利**；
- 若鉴权库同时承载云端配置逻辑，其完整性缺失会**波及云控安全机制**；
- 模块替换属于文件级篡改，存在被其他恶意软件利用的可能。

### 合规影响

- 鉴权模块无完整性校验，不满足部分企业终端的软件完整性要求。

## 加固方案

### 1 · 完整性层（最高优先级，成本最低）

```csharp
// ✅ 鉴权模块加载时校验完整性
public static bool LoadAuthModule(string path, out IntPtr handle)
{
    handle = IntPtr.Zero;

    // 1) Authenticode 签名校验
    if (!WinVerifyTrust(path)) return false;

    // 2) 自身内容哈希与编译期预置值比对
    var actual = SHA256.HashData(File.ReadAllBytes(path));
    if (!CryptographicOperations.FixedTimeEquals(actual, ExpectedAuthModuleHash))
        return false;

    handle = LoadLibraryEx(path, IntPtr.Zero, LOAD_LIBRARY_SEARCH_SYSTEM32);
    return handle != IntPtr.Zero;
}
```

### 2 · 架构层：消除判定与业务的边界

```csharp
// ❌ 反面：独立判定出口
public static bool IsVipFeatureA() => _isVip;   // 可被枚举、可被恒真
if (Auth.IsVipFeatureA()) { DoFeatureA(); }

// ✅ 正面：判定内联进业务实现
public static class FeatureGate
{
    public static bool TryExecute(string feature, Action action)
    {
        using var cred = LicenseStore.LoadDecrypted();
        if (cred is null) return false;
        if (!Ed25519.Verify(cred.Signature, cred.Payload, ServerPublicKey)) return false;
        if (!cred.Payload.MatchesDevice(DeviceFingerprint.Compute()))       return false;
        if (!cred.Payload.IsValidNow(MonotonicClock.Now))                   return false;
        if (!cred.Payload.Grants(feature))                                  return false;

        action();      // 无独立判定出口，无中间布尔状态
        return true;
    }
}

// 业务代码
FeatureGate.TryExecute("screenshot.longshot", () => CaptureLongShot());
```

### 3 · 符号与模块层

| 措施 | 说明 |
|:---|:---|
| **取消独立导出** | 特权判定不再作为导出符号暴露 |
| **权限位图化** | 改为"服务端签发的权限位图"，由签名保护 |
| **交叉校验** | 鉴权模块与主程序互相校验哈希 |
| **混淆** | 判定逻辑做控制流平坦化，消除显式条件跳转 |

### 4 · 云控层

| 措施 | 说明 |
|:---|:---|
| 通道签名 | 下发内容由服务端签名，客户端验签 |
| Fail-Closed | 无法验证时拒绝应用远程配置 |
| 防阻断 | HTTPS + 证书绑定 |

### 5 · 加固优先级

```
第一优先（成本最低）
  └─ 鉴权模块自身哈希校验 + 签名校验            ← 消除 AP-2

第二优先（架构级）
  ├─ 判定内联进业务实现                          ← 消除 AP-1 / AP-3
  └─ 取消特权判定导出符号

第三优先
  ├─ 权限位图化 + 服务端签名                     ← 补齐密码学强度
  └─ 云控通道签名 + Fail-Closed                 ← 消除 AP-4
```
