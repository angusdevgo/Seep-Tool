# Allen Explorer · 单点布尔裁决

> **公告编号**：01
> **缺陷模式**：模式 01 · 单点布尔裁决（兼 模式 02）
> **关联 CWE**：`CWE-602` · `CWE-321`
> **风险等级**：🔴 高
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

Allen Explorer 采用**完全离线**的授权模型：客户端依据本机硬件指纹与**内置对称派生算法**
在本地自行生成授权凭据。这意味着**凭据的生成权与验证权同时存在于客户端** ——
在密码学上等价于"锁和钥匙都挂在门上"。

配套的云端吊销通道（用于封禁异常设备）**未做完整性保护**，
使客户端可单方面阻断该通道，导致**已吊销设备仍能维持授权**。

## 攻击接入点分析 ★

### 接入点清单

| # | 接入点 | 所在组件 / 机制 | 攻击者前提 | 可获得能力 | 影响 |
|:---:|:---|:---|:---|:---|:---:|
| **AP-1** | **本地凭据生成算法** | 客户端内置的机器指纹 → 对称派生流程 | **无特殊前提** —— 算法完全在本地 | 在任意机器生成"合法"授权凭据 | 🔴 严重 |
| **AP-2** | **本地授权配置文件** | 客户端读取的授权存储文件 | 用户态文件写权限 | 直接注入伪造凭据 | 🔴 高 |
| **AP-3** | **云端吊销心跳通道** | 使用**明文 HTTP** 的授权状态上报接口 | 本地 `hosts` 改写 / 网络层拦截 | 单方面阻断吊销通道，维持已失效授权 | 🔴 高 |
| **AP-4** | **设备指纹采集** | 硬件标识读取逻辑 | 可影响采集输入 | 影响派生结果，便于复现凭据 | 🟠 中高 |
| **AP-5** | **试用期计数存储** | 本地计数字段 | 用户态文件/注册表写权限 | 重置试用周期 | 🟡 中 |

### 接入点性质分类

| 类型 | 接入点 | 说明 |
|:---|:---|:---|
| **凭据生成类** | AP-1 · AP-2 | **根本缺陷** —— 客户端同时持有生成权与验证权 |
| **通道阻断类** | AP-3 | 吊销机制失效，且使用明文 HTTP 便于本地拦截 |
| **输入影响类** | AP-4 | 削弱设备绑定的有效性 |
| **状态重置类** | AP-5 | 试用周期可被重置 |

### 攻击链组合分析

| 攻击链 | 组合路径 | 门槛 | 最终效果 |
|:---|:---|:---:|:---|
| **链 A**（最低门槛） | AP-1 单独利用 —— 复现派生算法 | 极低 | 任意机器生成有效凭据，永久授权 |
| **链 B**（免算法还原） | AP-2 直接写入配置 | 极低 | 无需理解算法即可注入凭据 |
| **链 C**（吊销规避） | AP-3 阻断上报通道 | 低 | 已吊销设备继续可用，厂商无感知 |
| **链 D**（组合） | AP-3 + AP-1 | 低 | **伪造凭据 + 屏蔽吊销 = 永久免疫封禁** |

> ⚠️ **链 D 是最危险的组合**：它同时使"激活"与"吊销"两个机制失效 ——
> 厂商既无法阻止激活，也无法事后处置。

### 攻击面收敛建议（厂商视角）

```
接入点优先级（按风险排序）

  AP-1  凭据生成类  ──→ 最高优先，必须架构重构（改非对称签名）
  AP-3  通道阻断类  ──→ 立即可改（HTTP → HTTPS + 证书绑定 + 响应验签）
  AP-2  凭据注入类  ──→ 随 AP-1 一并解决（凭据不可伪造则配置无意义）
  AP-4  输入影响类  ──→ 设备指纹多源组合 + 密码学绑定
  AP-5  状态重置类  ──→ 试用状态改由服务端记录
```

## 技术细节

### 1 · 架构层：凭据的生成权与验证权同源

**观测事实**：客户端依据本机硬件特征与内置算法在本地完成凭据生成，
**整个流程无任何服务端私钥参与**。

**安全含义**：这是 CWE-602 的经典形态。
由于客户端**既能生成也能验证**，攻击者只需复现生成逻辑，
即可产生服务端"无法区分真伪"的凭据 —— 因为**服务端本身并不参与验证**。

**核心教训**：**对称体系下，掌握客户端的任何人都掌握签发权。**

---

### 2 · 密码学层：对称密钥硬编码

**观测事实**：客户端内置**对称密钥材料**用于凭据的派生或加密。

**安全含义**：

| 维度 | 现状 | 应有强度 |
|:---|:---|:---|
| 密钥类型 | 对称（客户端内置） | 非对称（私钥仅在服务端） |
| 密钥位置 | 客户端二进制内 | HSM / 离线签名机 |
| 泄露后果 | 一次性永久失效 | 私钥不泄露则体系安全 |

**结论**：客户端二进制对攻击者完全可见 → **密钥必然泄露** →
一旦泄露，**所有历史版本同时失效**，无法通过"换密钥"修复。
📌 关联 CWE-321（使用硬编码的加密密钥）。

---

### 3 · 通道层：吊销机制可被本地阻断

**观测事实**：设备吊销状态的上报/校验通道使用**明文 HTTP**。

**安全含义**：

| 问题 | 后果 |
|:---|:---|
| 明文传输（CWE-319） | 可被本地或链路层拦截、篡改、重放 |
| 未做响应签名 | 客户端无法辨别响应真伪 |
| 本地 `hosts` 可改写 | **单方面阻断通道，且不触发任何异常上报** |
| 无失败告警 | 通道被阻断时，客户端**静默降级**为"信任本地状态" |

**结论**：吊销机制形同虚设，厂商**丧失事后处置能力**。

| # | 观测项 | 方法 | 结论 |

| 1 | 授权流程无服务端参与 | 网络行为监控 | 凭据 100% 本地生成 |

## 影响面

### 商业影响

- 未授权用户可获得完整专业版功能；
- **设备吊销机制完全失效**，无法远程封禁滥用账号；
- 无法区分"合法购买"与"本地伪造"，商业损失不可计量；
- 算法一旦被还原，**修复需重构整个授权体系**（无法打补丁了事）。

### 安全影响

- 明文 HTTP 传输授权数据，存在中间人篡改风险；
- 本地 `hosts` 可被任意程序改写，可能被其他恶意软件利用。

### 合规影响

- 授权数据明文传输可能不符合数据安全传输的合规要求；
- 设备吊销能力缺失，不满足部分企业软件资产管理的审计要求。

## 加固方案

### 1 · 架构层（最高优先级）

| 措施 | 说明 |
|:---|:---|
| **凭据由服务端签发** | 客户端仅做**公钥验签**，不具备生成能力 |
| **迁移至非对称签名** | 弃用对称派生，改用 **Ed25519** |
| **绑定设备指纹** | 指纹写入签名载荷内，防跨机复用 |

> 📖 完整实现见 [Ed25519 离线许可体系设计](../../02-防御体系/02-Ed25519离线许可体系设计.md)

### 2 · 通道层

```csharp
// ✅ 加固后的吊销通道
public static async Task<RevocationStatus> CheckRevocationAsync(string licenseId)
{
    using var http = new HttpClient(new HttpClientHandler
    {
        // 1) 证书绑定，防中间人
        ServerCertificateCustomValidationCallback = PinServerCertificate
    });

    // 2) 强制 HTTPS
    var resp = await http.GetAsync($"https://api.vendor.com/revoke?id={licenseId}");
    var body = await resp.Content.ReadAsByteArrayAsync();
    var sig  = Convert.FromBase64String(resp.Headers.GetValues("X-Signature").First());

    // 3) 响应必须验签，防伪造
    if (!Ed25519.Verify(sig, body, ServerPublicKey))
        return RevocationStatus.Unknown;      // ⚠️ Fail-Closed

    // 4) 通道异常时不得静默降级为"信任本地状态"
    return Parse(body);
}
```

> ⚠️ **关键点：通道失败必须 Fail-Closed** —— 无法确认时按"已吊销"处理，
> 而非默认"有效"。

### 3 · 加固优先级

```
第一优先（架构级）
  └─ 凭据改为服务端私钥签发（彻底消除 AP-1）

第二优先（成本低、收益高）
  └─ 吊销通道 HTTPS + 证书绑定 + 响应验签 + Fail-Closed

第三优先
  ├─ 设备指纹多源组合与密码学绑定
  └─ 试用状态改由服务端记录
```
