# Uninstall Tool · 明文进程间通信

> **公告编号**：08
> **缺陷模式**：模式 05 · 明文进程间通信（兼 模式 01）
> **关联 CWE**：`CWE-311` · `CWE-602` · `CWE-345`
> **风险等级**：🔴 高
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

Uninstall Tool 将授权鉴权逻辑**下沉到独立的外部服务进程**，
并通过**进程间通信（IPC）**将鉴权结果传回主程序。

> ### 📌 架构上，"鉴权逻辑独立进程化" 是一个**好设计** —— 它提高了攻击门槛。

但实现上存在**致命缺口**：

1. **IPC 消息无完整性保护** —— 主程序仅校验返回值的**数值表示**，
   未对消息来源做任何认证（无 HMAC、无签名、无时戳）；
2. **信任边界模糊** —— 主程序**无条件信任**来自 IPC 通道的状态码，
   未验证对端进程的真实性；
3. **结果可预测** —— 鉴权结果是一个**小整数**，搜索空间极小。

**核心教训**：**把逻辑搬到另一个进程，如果通信通道不安全，等于没搬。**

## 攻击接入点分析 ★

### 接入点清单

| # | 接入点 | 所在组件 / 机制 | 攻击者前提 | 可获得能力 | 影响 |
|:---:|:---|:---|:---|:---|:---:|
| **AP-1** | **进程间通信通道** | 鉴权服务 ↔ 主程序的本地 IPC（命名管道 / 共享内存） | **同用户权限进程**即可接入 | 伪造鉴权响应 | 🔴 严重 |
| **AP-2** | **鉴权结果数值表示** | IPC 传输的鉴权状态码（小整数） | 同 AP-1 | 搜索空间极小，易于命中期望值 | 🔴 高 |
| **AP-3** | **IPC 对端进程身份** | 主程序对对端进程的信任判定（**未校验**） | 同用户权限 | 冒充鉴权服务进程 | 🔴 高 |
| **AP-4** | **注册表授权键值** | `RN` / `RC` 授权键 | 用户态注册表写权限 | 直接播种授权状态 | 🟠 中高 |

### 接入点性质分类

| 类型 | 接入点 | 说明 |
|:---|:---|:---|
| **通道完整类** | AP-1 | **核心缺陷** —— 逻辑下沉了，但通道未加固 |
| **值可预测类** | AP-2 | 结果域极小，暴力枚举成本可忽略 |
| **身份认证类** | AP-3 | 未校验对端身份，任何同用户进程均可接入 |
| **状态播种类** | AP-4 | 绕过 IPC 直接写入本地授权状态 |

### 攻击链组合分析

| 攻击链 | 组合路径 | 门槛 | 最终效果 |
|:---|:---|:---:|:---|
| **链 A**（核心） | **AP-3 冒充服务 → AP-1 伪造响应 → AP-2 填入期望值** | 中 | 主程序认为已获商业授权 |
| **链 B**（免协议分析） | AP-2 枚举结果值 | 低 | 小搜索空间内快速命中 |
| **链 C**（免 IPC） | AP-4 直接写注册表 | 低 | 授权状态被播种 |
| **链 D**（组合） | AP-1 + AP-4 | 中 | **双路径冗余，长期稳定** |

> ⚠️ **链 A 揭示的核心问题 —— "下沉"的安全收益被"通道"的缺陷抵消**：
>
> 该产品的设计者显然意识到"客户端裁决"的风险，
> 因此**把鉴权逻辑放到了独立进程**（这是正确方向）。
> 但**主程序与鉴权进程之间的通道完全明文、无认证** ——
> 攻击者无需逆向受强保护的鉴权内核（该内核甚至使用了代码虚拟化），
> 只需攻击**更薄弱的通信层**即可。
>
> **核心教训**：**安全强度取决于链路中最薄弱的一环，而非最强的一环。**

### 攻击面收敛建议（厂商视角）

```
接入点优先级（按风险排序）

  AP-1  通道完整类  ──→ 最高优先（消息 HMAC + 时戳 + 序号）
  AP-3  身份认证类  ──→ 校验对端进程路径 + Authenticode 签名
  AP-2  值可预测类  ──→ 结果改为服务端签名凭据（而非裸状态码）
  AP-4  状态播种类  ──→ 注册表不得作为权益判据
```

## 技术细节

### 1 · 架构层：鉴权逻辑下沉（✅ 正确方向）

**观测事实**：授权鉴权逻辑**不在主程序内**，而是由**独立的外部服务进程**承担，
主程序通过 IPC 获取鉴权结论。

**评价**：

| 维度 | 评价 |
|:---|:---|
| 提高分析门槛 | ✅ 有效 —— 攻击者需先突破进程边界 |
| 隔离敏感逻辑 | ✅ 有效 —— 鉴权逻辑不暴露在主程序空间中 |
| 支持独立保护 | ✅ 有效 —— 鉴权内核可单独施加代码虚拟化保护 |

**这是一个值得肯定的设计决策。** 但——

---

### 2 · 通道层：IPC 消息无任何完整性保护 ★ 核心缺陷

**观测事实**：主程序**仅校验返回值的数值表示**，
未对消息做任何来源认证。

**缺失的保护措施**：

| 应有措施 | 现状 | 后果 |
|:---|:---:|:---|
| 消息认证码（HMAC） | ❌ 无 | 消息可被伪造 |
| 数字签名 | ❌ 无 | 无法验证来源 |
| 时戳 / 序号 | ❌ 无 | 可重放 |
| 对端进程身份校验 | ❌ 无 | 可被冒充 |
| 通道访问控制（ACL） | ❌ 无 | 同用户进程均可接入 |

**核心教训**：**未认证的 IPC 通道 = 开放的信任缺口。**

---

### 3 · 值域层：鉴权结果可预测

**观测事实**：鉴权结果是一个**小整数状态码**。

**安全含义**：

| 值域大小 | 暴力枚举量级 | 评价 |
|:---:|:---|:---|
| < 8 bit | 瞬间 | ❌ 等同于无校验 |
| 8 ~ 16 bit | 毫秒级 | ❌ 不可接受 |
| 16 ~ 32 bit | 秒级 | ❌ 高风险 |

**结论**：**结果域过小是"单点布尔裁决"在 IPC 场景下的变体** ——
本质仍是"小状态位决定全局权益"。

---

### 4 · 身份层：对端进程未校验

**观测事实**：主程序**不校验** IPC 对端进程的身份
（未检查路径、未验证签名、未绑定 PID）。

**安全含义**：任何**同用户权限**的进程都可以：
* 接入该通道；
* 冒充鉴权服务；
* 在主程序之前抢先绑定通道名（通道抢占）。

---

### 5 · 对照：强保护的内核 vs 薄弱的通道

**观测事实**：鉴权内核使用了**商业级代码虚拟化保护**，强度较高。

**这形成了鲜明的对比**：

```
┌─────────────────────────────────────────────────────────────┐
│  鉴权内核（强保护 ✅）                                        │
│    • 代码虚拟化                                              │
│    • 符号重命名                                              │
│    • 高强度分析成本                                          │
├─────────────────────────────────────────────────────────────┤
│           ↓  IPC 通道（零认证 ❌）                            │
│    明文状态码 · 无 HMAC · 无时戳 · 无身份校验                 │
├─────────────────────────────────────────────────────────────┤
│  主程序（无条件信任 ❌）                                      │
│    if (code == EXPECTED) EnablePro();                        │
└─────────────────────────────────────────────────────────────┘
```

> **攻击者不需要碰那个"很硬"的内核** ——
> 他只需要在那个"很软"的通道上做文章。
>
> **核心教训**：**保护强度应该按"最薄弱环节"分配，而非按"最重要环节"分配。**

## 影响面

### 商业影响

- 可通过伪造 IPC 响应让主程序认为已获商业授权；
- **该缺陷不依赖逆向鉴权算法** —— 即使算法是强保护的，
  攻击点也**转移到了更薄弱的通信层**；
- 厂商在鉴权内核上的保护投入**被通道缺陷完全抵消**。

### 安全影响

- IPC 通道可被同用户进程接入，存在**本地提权**风险；
- 通道抢占可能导致**拒绝服务**（合法服务无法绑定通道名）；
- 明文通道无认证，可被重放攻击。

### 合规影响

- 本地 IPC 缺乏访问控制与消息认证，
  可能不满足企业终端的安全通信基线要求。

## 检测与自查

### 面向开发者

```powershell
# ① 检查是否使用本地 IPC（命名管道 / 共享内存）
dumpbin /imports .\YourApp.exe | Select-String "CreateNamedPipe|CreateFileMapping|ConnectNamedPipe"

# ② 检查是否实现了消息认证
dumpbin /imports .\YourApp.exe | Select-String "BCryptCreateHash|CryptCreateHash"
```

```csharp
// ③ 检查 IPC 消息处理是否做了认证
//    ❌ 反例：仅校验状态码
int code = ReadInt32(pipe);
if (code == 3) EnablePro();

//    ✅ 正例：校验 HMAC + 时戳 + 序号
var (payload, mac) = ReadFramed(pipe, out int seq, out long ts);
if (!VerifyHMAC(payload, mac, sessionKey)) return;         // 消息认证
if (!IsFresh(ts, seq))                     return;         // 防重放
if (!VerifyPeerProcess(pipe))              return;         // 身份校验
```

### 面向用户

| 风险 | 缓解措施 |
|:---|:---|
| IPC 被冒充 | 以**非管理员**权限运行；避免运行来源不明的同用户进程 |
| 注册表被注入 | 监控授权相关注册表键的异常改动 |

## 加固方案

### 1 · 通道完整性层（最高优先级）

```csharp
// ✅ 加固后的 IPC 服务端
static bool TryReadAuthenticatedResponse(NamedPipeServerStream pipe,
                                        out Entitlement result)
{
    result = null;

    // ① 校验对端进程身份（路径 + 签名 + PID）
    if (!VerifyPeerProcess(pipe)) return false;

    // ② 读取消息体 + HMAC
    var payload = ReadFramed(pipe, out byte[] receivedMac);

    // ③ 校验 HMAC（会话密钥由两进程协商，不落盘）
    byte[] expectedMac = HMACSHA256.HashData(_sessionKey, payload);
    if (!CryptographicOperations.FixedTimeEquals(receivedMac, expectedMac))
        return false;

    // ④ 校验时戳与单调序号（防重放）
    var msg = Deserialize(payload);
    if (!msg.IsFresh(TimeSpan.FromSeconds(5))) return false;

    result = msg.Entitlement;
    return true;
}
```

```csharp
// ✅ 通道访问控制（ACL）—— 仅本用户可访问
static void SecurePipe(NamedPipeServerStream pipe)
{
    var security = new PipeSecurity();
    security.AddAccessRule(new PipeAccessRule(
        WindowsIdentity.GetCurrent().User!,
        PipeAccessRights.FullControl,
        AccessControlType.Allow));
    // 显式拒绝其他用户
    security.AddAccessRule(new PipeAccessRule(
        new SecurityIdentifier(WellKnownSidType.WorldSid, null),
        PipeAccessRights.ReadWrite,
        AccessControlType.Deny));

    pipe.SetAccessControl(security);
}
```

### 2 · 身份校验层

```csharp
// ✅ 校验对端进程的完整路径与签名
static bool VerifyPeerProcess(NamedPipeServerStream pipe)
{
    if (!GetNamedPipeClientProcessId(pipe.SafePipeHandle, out uint pid))
        return false;

    string path = GetProcessMainModulePath(pid);

    // 1) 路径必须在受信任目录内
    if (!IsUnderTrustedDir(path)) return false;

    // 2) 必须通过 Authenticode 签名校验
    if (!WinVerifyTrust(path)) return false;

    return true;
}
```

### 3 · 值域层：结果凭据化

| 措施 | 说明 |
|:---|:---|
| 结果改为签名凭据 | 不传裸状态码，改传服务端签名的权益位图 |
| 单次令牌 | 每次鉴权使用一次性令牌，防重放 |
| Fail-Closed | 认证失败时一律按未授权处理 |

### 4 · 状态层

| 措施 | 说明 |
|:---|:---|
| 注册表不作判据 | 本地存储仅作偏好，权益判据必须来自签名凭据 |
| 完整性校验 | 读取本地状态时校验完整性 |

### 5 · 加固优先级

```
第一优先（成本低，收益最高）
  ├─ IPC 消息 HMAC 认证 + 时戳 + 序号              ← 消除 AP-1 / AP-2
  └─ 对端进程身份校验（路径 + 签名）               ← 消除 AP-3

第二优先
  ├─ 管道 ACL 限制为当前用户                       ← 降低接入面
  └─ 结果改为服务端签名凭据                         ← 提升密码学强度

第三优先
  └─ 注册表不得作为权益判据                         ← 消除 AP-4
```

> 📌 **对厂商的提示**：该产品的**架构方向是正确的**（鉴权逻辑下沉）。
> 只需**把通道保护好**，就能让已投入的鉴权内核强保护真正发挥价值 ——
> 本案例属于"**补通道**"而非"**改架构**"。
