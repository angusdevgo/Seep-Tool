# Listary Pro · 自研弱校验算法

> **公告编号**：04
> **缺陷模式**：模式 06 · 自研弱校验算法（兼 模式 01）
> **关联 CWE**：`CWE-327` · `CWE-602`
> **风险等级**：🔴 高
> **披露状态**：待联系厂商
> **最后更新**：2026-10

---

## 摘要

Listary Pro 的许可证校验**完全由客户端独立完成**，
且采用了**自研的混合哈希方案**（多项式滚动哈希 + 变种哈希 + 多轮异或组合）
来校验授权密钥的合法性。

这是最典型的**密码学反模式**：自研算法未经公开审查、算法逻辑完全暴露在客户端、
校验过程不涉及任何服务端私钥。其直接后果是 ——
**攻击者可离线生成通过校验的凭据**，且一旦算法被还原，
**所有历史版本同时失效**（算法通常跨版本复用）。

| **链 B**（免算法还原） | AP-2 穷举校验段 | 低（校验位少） | 快速碰撞出通过校验的密钥 |

## 技术细节

### 1 · 密码学层：自研混合哈希方案

**观测事实**：校验链由**多个自研哈希函数组合**而成 ——
包括多项式滚动哈希、变种哈希、多轮异或混合，最终取特定位段作为校验依据。

**这是最典型的密码学反模式**：

| 问题 | 后果 |
|:---|:---|
| **未经公开密码学审查** | 抗分析强度远低于公开算法（无学术验证） |
| **算法逻辑完全暴露** | 客户端二进制可被逆向，算法可被完整还原 |
| **不涉及服务端私钥** | 攻击者可自行生成通过校验的凭据 |
| **校验位长度有限** | 搜索空间不足，可被离线穷举 |

**核心教训**：**"自研加密"是最昂贵的错觉** ——
它提供了虚假的安全感，却引入了真实的系统脆弱性。

---

### 2 · 熵层：校验位长度不足以抵抗穷举

**观测事实**：密钥中真正的校验依据仅占用**很短的位段**，
其余部分不参与密码学验证。

**安全含义** —— 位段长度与破解成本的直接关系：

| 校验位长度 | 离线穷举量级 | 评价 |
|:---:|:---|:---|
| < 16 bit | 秒级 | ❌ 等同于无校验 |
| 16 ~ 32 bit | 分钟 ~ 小时 | ❌ 不可接受 |
| 32 ~ 64 bit | 天 ~ 月 | ⚠️ 高风险 |
| 64 ~ 80 bit | 年（单机） | 🟡 仅在小规模下勉强 |
| **≥ 128 bit** | **计算上不可行** | ✅ **应有强度** |

**结论**：**校验强度必须达到 ≥ 128 bit，才能抵抗离线暴力破解。**

---

### 3 · 架构层：完全离线的校验闭环

**观测事实**：许可证校验**完全由客户端独立完成**，
云端仅承担账号相关功能，**不参与授权凭据的密码学验证**。

**安全含义**：与 01 号案例（Allen Explorer）同构 ——
客户端同时持有**生成权**与**验证权**，服务端不在信任链中。

---

### 4 · 修复难度：需要架构重构

**这是本案例与 07 号案例（Snipaste）的关键差异**：

| 维度 | Listary Pro（本案例） | Snipaste PRO（07 号） |
|:---|:---|:---|
| 算法类型 | 自研对称哈希 | 标准非对称（Ed25519） |
| 修复方式 | **推倒重建** | **补短板** |
| 工作量 | 高（重构授权体系） | 低（补公钥校验） |
| 版本影响 | **算法复用 → 影响多版本** | 单版本修复即可 |

> 📌 **对厂商的现实提示**：
> 自研算法一旦公开分析，**"换密钥"无法解决问题** ——
> 必须迁移到标准非对称体系。

## 影响面

### 商业影响

- 可离线生成有效授权密钥，**永久激活专业版**；
- **自研算法一旦还原，所有历史版本同时失效** ——
  按单一版本售卖的商业模型受到根本冲击；
- **无法通过换密钥修复**，必须重构整个授权体系；
- 算法具有跨版本复用性，**历史版本的授权凭证全部失效**。

### 安全影响

- 自研算法可能存在其他未发现的实现缺陷（如侧信道、整数溢出）；
- 弱校验位段降低了整体授权体系的可靠兜底能力。

### 合规影响

- 使用自研弱密码算法不符合部分行业密码应用规范
  （如金融、政务领域对密码算法的合规要求）。

## 加固方案

### 1 · 算法层：迁移至标准非对称签名（最高优先级）

```csharp
// ❌ 当前实现（示意）：自研组合哈希
static bool CheckKey(string key)
{
    int h1 = 0;
    foreach (char c in key) h1 = (h1 * 43 + c) & 0xFFFF;   // 多项式滚动
    int h2 = CustomElfHash(key);                            // 变种哈希
    int h3 = 0;
    for (int i = 0; i < 4; i++) h3 ^= (h1 << i) | h2;       // 多轮异或
    return (h3 & 0x3FF) == ExtractSegment(key);             // 短校验段 ← 致命
}

// ✅ 加固后：Ed25519 标准验签
static bool CheckLicense(byte[] license, byte[] signature)
{
    // 1) 标准非对称验签（256 bit 安全强度）
    if (!Ed25519.Verify(signature, license, ServerPublicKey))
        return false;

    // 2) 载荷绑定校验
    var payload = LicensePayload.Parse(license);
    return payload.DeviceHash == ComputeDeviceHash()
        && payload.ExpiresAt > DateTimeOffset.UtcNow.ToUnixTimeSeconds()
        && payload.Nonce      == _expectedNonce;
}
```

**强度对比**：

| 指标 | 自研方案 | Ed25519 |
|:---|:---|:---|
| 安全强度 | 取决于校验位长度（可能 < 16 bit） | **≥ 128 bit** |
| 抗穷举 | ❌ 可能秒级破解 | ✅ 计算上不可行 |
| 抗伪造 | ❌ 无信任根 | ✅ 私钥签发 |
| 学术审查 | 无 | ✅ 广泛验证 |

### 2 · 配置层

| 措施 | 说明 |
|:---|:---|
| 凭据不可伪造 | 依赖 AP-1 修复 |
| 配置完整性 | 配置文件加校验和，异常则拒绝加载 |
| Fail-Closed | 校验不确定时按未授权处理 |

### 3 · 通道层

| 措施 | 说明 |
|:---|:---|
| HTTPS + 证书绑定 | 防中间人 |
| 响应验签 | 客户端验证服务端响应签名 |
| **Fail-Closed** | 通道被阻断时**不得静默降级**为"信任本地状态" |

### 4 · 加固优先级

```
第一优先（架构级，必须重构）
  └─ 自研哈希 → Ed25519 非对称签名                 ← 消除 AP-1 / AP-2

第二优先
  ├─ 私钥迁移至 HSM / 离线签名机
  └─ 凭据载荷绑定 设备指纹 + 有效期 + Nonce

第三优先
  ├─ 配置文件完整性校验                            ← 消除 AP-3
  └─ 云端通道签名 + Fail-Closed                    ← 消除 AP-4
```

> ⚠️ **特别提示**：由于自研算法具有**跨版本复用性**，
> 修复时必须**同时废弃全部历史算法分支**，
> 否则旧版本仍可被继续利用。
