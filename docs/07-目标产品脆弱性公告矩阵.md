> **文档性质**：安全公告（Security Advisory）合集 · 负责任披露格式
> **编写目的**：为软件开发者提供真实的 CWE-602 缺陷样本库，帮助研发团队识别并修复同类架构缺陷。
>
> ⚠️ **本矩阵遵循负责任披露原则**：
> 公开**受影响版本、缺陷分类、架构根因与加固方案**；
> **不公开**具体内存偏移、补丁字节、绕过步骤或任何可执行脚本。

## 01 · Allen Explorer 资源管理器

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 本地授权凭据模块 + 云端吊销校验通道 |
| **缺陷类别** | `CWE-602` 客户端裁决 · `CWE-321` 硬编码加密密钥 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 2（硬编码对称密钥）、模式 1（单点布尔裁决） |

### 架构层根因分析

该产品采用**完全离线**的授权模型：客户端根据本机特征（硬件指纹）与内置的**对称派生算法**，
在本地计算出授权凭据并写入配置文件。整个过程**没有任何服务端签名参与**。

这意味着授权凭据的**生成权与验证权同时存在于客户端**。
在密码学上，这等价于"锁和钥匙都挂在门上"—— 攻击者只需复现派生算法，
即可在任意机器上生成合法凭据，而服务端无从区分真伪。

同时，该产品的云端吊销通道（用于封禁异常设备）**未做完整性保护**，
使得客户端可以单方面阻断该通道，从而让已吊销的设备继续维持授权状态。

### 影响面

- 未授权用户可获得完整专业版功能；
- 厂商的**设备吊销机制完全失效**，无法远程封禁滥用账号；
- 无法区分"合法购买"与"本地伪造"，商业损失不可计量。

### 审计要点（通用方法）

审计同类离线授权实现时，重点关注：

1. 凭据生成是否**完全在客户端完成**（是否有服务端私钥参与）；
2. 客户端内置的是**对称密钥**还是**公钥**；
3. 云端校验通道是否有**防篡改/防阻断**设计；
4. 设备指纹是否与凭据做**密码学绑定**（而非简单字符串比较）。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **架构** | 授权凭据必须由**服务端私钥签发**，客户端仅做**公钥验签** |
| **密码学** | 弃用对称派生，改用 **Ed25519**（参见 [文档 04](04-Ed25519离线许可体系设计.md)） |
| **通道** | 云端校验启用 **HTTPS + 证书绑定（Certificate Pinning）**，并校验响应签名 |
| **兜底** | 关键权益采用**服务端异步二次确认**，离线凭据仅作为临时宽限 |

## 02 · Bandizip (Enterprise 版)

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 主程序动态库加载链（`version.dll` 搜索顺序） |
| **缺陷类别** | `CWE-427` 不受控搜索路径 · `CWE-602` 本地状态裁决 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 3（动态库加载顺序缺陷）、模式 1（单点布尔裁决） |

### 架构层根因分析

该产品主程序在启动阶段以**裸 `LoadLibrary`** 方式加载动态库，
**未使用 `SetDefaultDllDirectories` 限定搜索路径**，也未对加载的库做签名校验。

这构成典型的 **DLL 搜索顺序劫持（T1574.001）** 缺陷：攻击者只需在程序目录放置
一个同名代理库，即可在**主程序自身进程内**获得代码执行权 ——
**且由于是合法进程加载，不触发任何安全软件告警**。

获得进程内执行权后，攻击者可进一步操纵该产品的**企业版/社区版区分标志**。
该标志存储于进程内可写内存，判定逻辑为单点分支，缺乏任何完整性保护。

### 影响面

- 攻击者可获得企业版全部功能；
- **DLL 劫持本身是比授权绕过更严重的安全问题** —— 它意味着任何本地攻击者
  都能在该进程内执行任意代码（可窃取剪贴板、读取已解压文件、注入恶意载荷）；
- 攻击者可**绕过厂商的黑名单校验**，被拉黑的用户仍可正常使用。

### 审计要点

1. 程序启动时是否调用 `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`；
2. 所有 `LoadLibrary` / `LoadLibraryEx` 调用是否使用了**绝对路径**；
3. 加载的模块是否做了 **Authenticode 签名验证**；
4. 授权等级标志是否可通过内存扫描定位（字符串引用 / 导出符号）。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **加载安全** | 启动首行调用 `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`，仅从系统目录加载 |
| **签名校验** | 对加载的模块执行 `WinVerifyTrust` 校验，拒绝未签名/签名不符的库 |
| **状态保护** | 授权等级改用服务端签名凭据，不在内存中以明文布尔量存在 |
| **混淆** | 关键判定逻辑内联化，消除独立的可定位分支 |

## 03 · Burp Suite Professional

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 原生启动器加载链 + JVM 引导参数 |
| **缺陷类别** | `CWE-427` 加载链劫持 · `CWE-602` 客户端裁决 |
| **风险等级** | 🟠 中高 |
| **对应模式** | 模式 3（加载顺序缺陷）、模式 1（单点裁决） |

### 架构层根因分析

该产品采用 **原生启动器（Launcher）+ Java 运行时**的混合架构。
启动器负责定位并拉起 JVM，但**未对自身加载的动态库做路径限定与签名校验**。

由于 Java 虚拟机支持通过**启动参数动态加载 Agent**，
一旦攻击者获得原生层的加载链控制权，即可向 JVM 注入自定义 Agent，
在**字节码层面**改写授权状态机 —— 这种方式**完全不修改官方二进制文件**，
因此传统的文件完整性校验无法察觉。

### 影响面

- 攻击者可解锁专业版全部功能（含漏洞扫描器）；
- 加载链缺陷同样意味着**本地任意代码执行**风险；
- 字节码层改写**不触碰磁盘文件**，导致取证与检测难度大幅上升。

### 审计要点

1. 原生启动器是否存在不受控的 DLL 搜索路径；
2. JVM 启动参数是否可被外部配置影响（`-javaagent` 注入面）；
3. 授权状态机是否可被运行时改写（是否存在可写状态字段）；
4. 是否实施了 **JAR 包签名校验**与**类加载器白名单**。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **加载安全** | 启动器限定 DLL 搜索目录 + 自身签名自校验 |
| **JVM 层** | 校验 `-javaagent` 来源白名单；启用 JAR 签名校验 |
| **状态机** | 授权状态下沉至 Native 层，并对 Native 状态做完整性校验 |
| **运行时** | 实施类加载器监控，检测运行时字节码篡改 |

## 04 · Listary Pro

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 本地许可证校验模块 |
| **缺陷类别** | `CWE-602` 客户端裁决 · `CWE-327` 自研弱哈希算法 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 6（自研弱校验算法）、模式 1（单点裁决） |

### 架构层根因分析

该产品的许可证校验**完全由客户端独立完成**，且采用了**自研的混合哈希方案**
（多项式滚动哈希 + 变种哈希 + 多轮异或组合）来校验授权密钥的合法性。

**这是最典型的密码学反模式**：
- 自研算法未经公开密码学审查，其抗分析强度远低于标准算法；
- 算法逻辑完全暴露在客户端二进制中，可被逆向还原；
- 校验过程**不涉及任何服务端私钥**，因此攻击者可自行生成通过校验的凭据；
- 密钥校验段长度有限，搜索空间不足以抵抗离线计算。

### 影响面

- 攻击者可离线生成有效授权密钥，永久激活专业版；
- 自研算法一旦被还原，**所有历史版本同时失效**（算法通常跨版本复用）；
- 无法通过"换密钥"修复，必须重构整个授权体系。

### 审计要点

1. 许可证校验是否使用**公开标准算法**（Ed25519 / RSA-PSS / ECDSA）；
2. 是否存在"多项式哈希""查表异或""自研编码"等自造轮子；
3. 校验密钥长度与熵是否足够（< 128 bit 视为不足）；
4. 校验是否绑定服务端签名。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **算法** | 全面迁移至 **Ed25519** 非对称签名体系，彻底废弃自研哈希 |
| **密钥** | 私钥仅存于服务端离线保管（HSM / 离线签名机） |
| **载荷** | 许可证载荷绑定 `设备指纹 + 有效期 + Nonce`，防止跨机复用 |
| **工程** | 建立"禁止自研密码学"的代码审查红线 |

## 05 · PixPin 截图贴图工具

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | `PixAuth.dll` 会员特权判定 |
| **缺陷类别** | `CWE-602` 客户端裁决 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 1（单点布尔裁决） |

### 架构层根因分析

该产品的 14 项会员功能，每一项都由 `PixAuth.dll` 中**独立的导出布尔函数**
（形如 `IsVipFeatureXxx()`）来判定是否开放。

这种设计存在**三重架构缺陷**：

1. **判定点分散且显式**：14 个独立导出函数，每个都是单点分支，
   意味着有 14 个可被独立定位的攻击面（而非 1 个）；
2. **判定与业务解耦**：特权判定只是返回布尔值，与真正的功能实现之间
   存在清晰的调用边界 —— 攻击者只需让判定恒真，业务逻辑自然全部开放；
3. **无完整性保护**：该 DLL 未做自身校验，也未与主程序做交叉验证。

**根本问题**：把"是否允许"和"如何实现"分成了两层，
使得前者成为可以单独攻破的"开关"。

### 影响面

- 攻击者可解锁全部 14 项 VIP 功能（长截图、离线 OCR、翻译、高级标注等）；
- 分散的判定点意味着**修复成本高**（需要重构 14 处调用关系）；
- 该 DLL 同时承载云端配置逻辑，其完整性缺失还会影响云控更新等安全机制。

### 审计要点

1. 特权判定是否为**独立导出函数**（可用 `dumpbin /exports` 快速识别）；
2. 判定结果与业务逻辑之间是否存在**清晰的调用边界**；
3. 判定函数是否为**单一条件分支**（`test`/`jz` 模式）；
4. 是否存在对判定模块自身的**完整性校验**。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **内联化** | 取消独立导出，将特权判定**内联进各业务实现**，消除单点开关 |
| **状态化** | 改为"服务端签发的权限位图"（Bitmask），由签名保护 |
| **完整性** | 对鉴权模块做自身哈希校验，并与其他模块交叉验证 |
| **混淆** | 判定逻辑做控制流平坦化，消除显式条件跳转模式 |

## 06 · Seer 极速文件预览

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 主程序授权判定入口（`AppLicenser` 模块） |
| **缺陷类别** | `CWE-602` 客户端裁决 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 1（单点布尔裁决） |

### 架构层根因分析

该产品的授权判定集中在**单一决策函数**上：
一个 `isLicensed()` 判定决定全部授权状态，
另一个独立的函数负责试用倒计时与购买弹窗的触发。

**这是"单点故障"式的安全设计**：
- 授权状态由一个函数的返回值完全决定；
- 该函数的返回值是**显式的布尔量**，可通过单条指令改写；
- 试用期的限制逻辑与授权判定**完全解耦**，因此可以独立解除；
- 二进制未做控制流混淆，判定入口可被直接定位。

值得注意的是，该产品**尝试了"双点防护"**（授权判定 + 弹窗拦截），
但由于两个点都是**同一层级的客户端逻辑**，防护效果等同于单点。

### 影响面

- 攻击者可永久解除试用限制，无限期使用完整功能；
- 试用倒计时机制形同虚设，产品无法有效转化付费用户；
- 攻击面清晰且唯一，**攻击成本极低**（适合作为入门级研究样本）。

### 审计要点

1. 授权判定是否集中在**单一函数**；
2. 该函数的返回值是否**直接控制**全部特权；
3. 是否存在"补丁一个点就能解锁全部"的结构；
4. 是否有反调试、控制流混淆等对抗措施。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **分散化** | 授权校验**多点交叉**：在 3~5 处不相关的代码路径中重复校验 |
| **绑定** | 特权功能实现中**内嵌**授权校验，而非先判后用 |
| **混淆** | 关键判定采用**控制流平坦化 + 虚假控制流**（OLLVM） |
| **虚拟化** | 授权核心逻辑使用 **VMP** 保护，消除直接的 `cmp/test` 模式 |

## 07 · Snipaste PRO

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 内嵌验签公钥 |
| **缺陷类别** | `CWE-602` 客户端裁决 · `CWE-321` 硬编码密钥材料 |
| **风险等级** | 🟠 中高 |
| **对应模式** | 模式 2（硬编码密钥材料） |

### 架构层根因分析

**这是一个"方向正确但实现不完整"的典型案例，很值得学习。**

该产品采用了**正确的密码学方向** —— 使用 **Ed25519 非对称签名**校验授权码，
私钥保留在服务端，客户端只内置公钥。这在架构上是**符合最佳实践的**。

然而，实现上存在两个缺口：

1. **公钥硬编码且缺乏交叉校验**：公钥以明文常量形式存在于只读数据节区，
   且**没有任何机制校验公钥自身的完整性**。一旦公钥被替换，
   攻击者用自己生成的私钥签发的凭据即可通过验证 ——
   **非对称体系的安全根基（"私钥不可得"）被绕过**；

2. **公钥未被多点引用**：若公钥在多个不相关的代码路径中被交叉校验，
   替换成本会大幅上升；而单点引用意味着只需替换一处。

**核心教训**：**非对称签名 ≠ 绝对安全，前提是公钥本身不可被替换。**

### 影响面

- 攻击者可自行签发有效授权码，实现永久激活；
- 该缺陷**不影响服务端私钥安全**，但使客户端验签完全失效；
- 由于使用了标准算法，**修复成本较低**（补充公钥完整性校验即可）。

### 审计要点

1. 客户端内置的是**公钥**还是对称密钥（本案例是公钥，方向正确）；
2. 公钥是否**多点交叉校验**（哈希指纹在多处比对）；
3. 验签逻辑是否与二进制完整性校验**联动**；
4. 是否校验了签名载荷的**设备绑定与有效期**。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **公钥保护** | 公钥指纹在**多个不相关函数**中交叉校验，任一处不符即拒绝运行 |
| **完整性** | 结合 **Authenticode 签名**对自身二进制做运行时复核 |
| **载荷** | 签名载荷强制包含 `设备指纹 + 有效期 + Nonce`，防跨机复用 |
| **纵深** | 验签通过后仍需**服务端异步确认**关键权益 |

## 08 · Uninstall Tool

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 鉴权内核 + 主程序进程间通信 |
| **缺陷类别** | `CWE-602` 客户端裁决 · `CWE-311` 缺失数据保护 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 5（明文进程间通信） |

### 架构层根因分析

该产品将授权鉴权逻辑**下沉到独立的外部服务进程**，
并通过**进程间通信（IPC）**将鉴权结果传回主程序。

**架构上，"鉴权逻辑独立进程化" 是一个好设计** —— 它提高了攻击门槛。
但实现上存在致命缺口：

1. **IPC 消息无完整性保护**：主程序仅校验返回值的**数值表示**，
   未对消息来源做任何认证（无 HMAC、无签名、无时戳）；
2. **信任边界模糊**：主程序**无条件信任**来自 IPC 通道的状态码，
   未验证对端进程的真实性；
3. **结果可预测**：鉴权结果是一个**小整数**，搜索空间极小。

**核心教训**：**把逻辑搬到另一个进程，如果通信通道不安全，等于没搬。**

### 影响面

- 攻击者可通过伪造 IPC 响应，让主程序认为已获得商业授权；
- 该缺陷**不依赖逆向鉴权算法**（算法甚至可以是强保护的），
  攻击点转移到了更薄弱的通信层；
- 同类问题也可能导致**本地提权**风险（若 IPC 通道可被其他进程接入）。

### 审计要点

1. 进程间通信是否使用**命名管道/共享内存**等本地 IPC；
2. 消息是否附带 **HMAC 或数字签名**；
3. 是否校验**对端进程身份**（PID、路径、签名）；
4. 消息是否包含**时戳与 Nonce** 以抵抗重放。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **消息认证** | IPC 消息附加 **HMAC-SHA256**（密钥由两进程协商，不落盘） |
| **防重放** | 每条消息携带**单调递增序号 + 高精度时戳** |
| **身份校验** | 校验对端进程的**完整路径 + Authenticode 签名** |
| **通道加固** | 使用**访问控制列表（ACL）**限制管道仅本用户可访问 |
| **纵深** | 关键权益仍以**服务端签发凭据**为最终依据 |

## 09 · XYplorer

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 动态库加载链 + 进程内授权状态变量 |
| **缺陷类别** | `CWE-427` 加载链劫持 · `CWE-602` 客户端裁决 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 3（加载顺序缺陷）、模式 4（可写全局状态） |

### 架构层根因分析

该产品存在**两处独立的架构缺陷**，可被分别或组合利用：

**缺陷一：动态库加载链未加固**
与 02 号案例类似，主程序以不受控的搜索路径加载动态库，
使攻击者可获得**进程内代码执行权**。

**缺陷二：授权状态依赖进程内可写全局变量**
产品的授权等级完全由进程内一个**可写的全局变量**（`license_type`）决定。
该变量的读写点分散在标题栏渲染、功能门控、关于框等多个位置。

此外，其注册码校验仅采用**4 字符静态前缀弱匹配**（无签名、无服务端回执），
这在密码学上等同于**无校验** —— 前缀空间可被瞬间枚举。

**核心教训**：**"状态变量驱动"的设计，等于把授权开关暴露在内存里。**

### 影响面

- 攻击者可解锁终身专业版授权；
- **加载链缺陷带来的任意代码执行风险，严重性高于授权绕过本身**；
- 弱前缀校验意味着**任何 4 字符匹配的字符串都能通过**；
- 由于授权状态被多处 UI 直接引用，绕过效果会**自动扩散到整个界面**。

### 审计要点

1. 动态库加载路径是否受控；
2. 授权状态是否为**进程内可写全局变量**；
3. 注册码校验的**熵与强度**（长度、是否含签名）；
4. 授权状态被多少处 UI 逻辑直接引用。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **加载安全** | `SetDefaultDllDirectories` + 模块签名校验 |
| **状态保护** | 授权状态改为**堆中加密存储**，用毕即时擦除 |
| **校验强度** | 弃用前缀匹配，改用**服务端签名凭据** |
| **一致性** | 授权校验**多点交叉**，避免单变量驱动全局 |
| **完整性** | 运行时自校验二进制，检测内存篡改 |

## 10 · BoosterX 系统优化工具

| 字段 | 内容 |
|:---|:---|
| **受影响组件** | 本地授权判定模块 · 代码虚拟化运行时 · 配置状态存储 · 授权网络通道 |
| **缺陷类别** | `CWE-602` 客户端裁决 · `CWE-287` 鉴权逻辑缺陷 · `CWE-863` 授权错误 · `CWE-319` 明文传输 · `CWE-798` 硬编码凭据 |
| **风险等级** | 🔴 高 |
| **对应模式** | 模式 1（单点布尔裁决）、模式 2（硬编码密钥材料）、模式 4（可写全局状态）、模式 7（空值短路校验） |

### 架构层根因分析

该产品采用了**商业级混淆器全保护模式**（符号重命名 + 字符串加密 + 程序集代码加密 + 代码虚拟化），
保护强度在同类产品中属于上乘。但审计结果表明：
**混淆与虚拟化只能提高分析成本，无法改变"裁决权在客户端"这一架构事实。**
本案例的价值恰在于它提供了一个"**保护层很厚、架构层很薄**"的典型样本。

该产品存在**四处彼此独立的架构缺陷**，可被分别或组合利用：

**缺陷一：付费权益（PRO）的裁决权完全在客户端**（模式 1）

产品的付费权益由**本地布尔量**决定：全部功能设置项中存在若干项在构造时被打上"PRO 专属"标记，
另有一个**全局授权态查询入口**被多处 UI 与业务逻辑（激活页状态显示、任务执行流程、
设置项可编辑性、页面级功能门控）直接引用。

整个权益判定链路**不依赖任何服务端签发的权益凭证** —— 客户端既是运动员又是裁判。
一旦该布尔量的判定被改写，绕过效果会**自动扩散到所有引用点**，无需逐处处理。

**缺陷二：授权校验存在 Fail-Open 短路**（模式 7 · 本案例新识别模式）

启动期授权装载流程中，判定点的语义是"**凭据是否为空 / 无效**"。
当凭据为 `null`、空字符串或字面量 `"null"` 时，客户端将其解释为"**无需校验**"，
直接跳入"校验通过"分支 —— **整个过程中不向服务端发起任何请求**。

这是典型的 **Fail-Open** 设计：把"**无法判定**"错误地当作"**判定通过**"。
安全上正确的做法应当是 **Fail-Closed**：凭据缺失或无效时一律视为校验失败。

该缺陷的严重性在于：它**不需要任何代码修改**，仅靠一份空配置即可触发，
且在流量层表现为"客户端完全静默"，难以被服务端侧的风控发现。

**缺陷三：特权状态存放于用户可写位置**（模式 4）

全部功能开关（含所有 PRO 相关开关，共数十项）以**明文布尔值**存放于当前用户注册表 hive。
该位置任何用户态进程均可读写，且客户端读取后**未做任何完整性或来源校验**。

这意味着：**无需触碰二进制文件**，仅靠配置写入即可改变功能行为。

**缺陷四：传输层与密钥材料缺陷**（模式 2）

授权校验接口走 **明文 HTTP**，且请求/响应体仅用**全局硬编码的对称密钥**加密。
由于该密钥随客户端分发，任何持有客户端的攻击者都能离线解密历史流量并自行构造
格式合法的授权响应。

**核心教训**：
1. **保护层 ≠ 安全架构** —— 代码虚拟化把分析成本从"小时级"提升到"天级"，
   但一旦架构层存在"裁决权在客户端"的根本缺陷，最终仍会被突破；
2. **Fail-Open 是最危险的鉴权反模式** —— 它让"配置缺失"变成了"免检通道"；
3. **布尔量是授权体系的最弱环节** —— 无论它藏得多深，本质都只是一个可被翻转的状态位。

### 影响面

- **付费墙失效**：客户端侧的全部 PRO 权益可被离线获取，授权体系丧失商业保护能力；
- **服务端不可感知**：客户端在旁路状态下完全不发请求，服务端风控无任何异常信号；
- **明文传输泄露**：授权协议与硬编码密钥暴露，可被离线分析并用于伪造响应；
- **横向扩散**：由于授权态被多处 UI 直接引用，单一判定点的失守会自动扩散至整个界面；
- **合规风险**：明文 HTTP 传输授权相关数据，可能不符合数据安全传输的合规要求。

### 审计要点

审计同类"重型混淆 + 本地授权"实现时，重点关注：

1. **剥离保护层看架构**：不要被混淆强度吓退 —— 先问"**最终裁决权在谁手里**"，
   再决定是否值得投入时间还原被保护逻辑；
2. **枚举权益判定出口**：统计"PRO 专属"标记的**总数**，以及授权态查询入口的**被引用次数**
   —— 引用点越多，单点失守的扩散面越大；
3. **审计鉴权分支的空值语义**：逐一检查"凭据为空 / 缺失 / 格式错误"时程序走向哪个分支，
   重点找 **Fail-Open** 短路；
4. **检查本地状态的存放位置与完整性**：特权状态是否落在用户可写位置？读取时是否校验完整性？
5. **检查传输层与密钥来源**：授权接口是否强制 HTTPS？密钥是协商产生还是随包分发？
6. **识别代码虚拟化的还原特征**：虚拟化保护常伴随"方法名自描述令牌"
   （名称本身编码了方法在字节码流中的位置）与"位置相关的流加密"，
   这类设计一旦被识别，整条保护链可被系统性还原。

### 加固方案

| 层级 | 措施 |
|:---|:---|
| **架构** | 确立"**服务端权威**"：客户端只持有并呈递凭据，不参与"是否付费"的裁决；核心权益对应的资源/数据由服务端加密下发 |
| **鉴权逻辑** | 全面改为 **Fail-Closed**：凭据缺失、为空、格式非法一律判定失败；消除"空值即通过"的所有分支 |
| **凭据形态** | 改用**非对称签名凭据**（Ed25519 / RSA-PSS）：服务端私钥签发，客户端仅做验签；绑定硬件指纹与有效期，支持远程吊销 |
| **传输层** | 全链路 HTTPS + 证书绑定（SSL Pinning）；移除裸 IP 兜底地址；请求加入 Nonce + 时戳 + 请求签名防重放 |
| **密钥管理** | 移除随包分发的对称密钥，改为每次会话协商的临时密钥（ECDH）+ 服务端签名 |
| **本地状态** | 本地配置仅作为"用户偏好"，**不得作为权益判据**；权益判据必须来自签名凭据 |
| **运行时** | 关键判定下沉 Native 并做完整性自校验；现有反篡改机制应"解不开即拒绝运行"，而非静默降级 |
| **兜底** | 服务端记录授权请求的设备指纹与频率，对异常模式告警；关键权益接口做服务端二次鉴权 |

## 横向统计与结论

### 缺陷类型分布

| 缺陷类型 | 命中产品数 | 占比 |
|:---|:---:|:---:|
| **CWE-602 客户端裁决** | 10 / 10 | **100%** |
| CWE-427 加载链缺陷 | 4 / 10 | 40% |
| CWE-321/327/798 密码学与密钥材料缺陷 | 4 / 10 | 40% |
| CWE-287 鉴权分支逻辑缺陷 | 2 / 10 | 20% |
| CWE-863 授权错误 | 1 / 10 | 10% |
| CWE-311 缺失数据保护 | 1 / 10 | 10% |
| CWE-319 明文传输 | 1 / 10 | 10% |

### 关键结论

> ### 📌 核心发现
> **所有 10 款产品无一例外都存在 CWE-602 架构缺陷。**
>
> 这印证了本文档集的核心论点：
> **CWE-602 不是"某几款软件的疏忽"，而是桌面商业软件行业的系统性设计问题。**
> 其根源在于"离线可用性"与"授权可信性"之间的固有张力。
>
> 特别值得注意的是 **10 号案例（BoosterX）**：该产品使用了商业级代码虚拟化保护，
> 保护强度在所有样本中最高，**但架构层缺陷依然完整存在**。
> 这直接证明了：**混淆强度与安全架构是两个正交维度，前者无法弥补后者的缺失。**

### 给开发者的三条铁律

1. **裁决权必须在服务端** —— 客户端只能"持有并呈递"凭据，不能"决定"权益；
2. **禁止自研密码学** —— 使用 Ed25519 / RSA-PSS 等标准原语，私钥离线保管；
3. **纵深防御是必需的，但不是充分的** —— 混淆与反调试只能提高成本，
   **无法替代架构修正**。
