## 2. 缺陷成因（源码层）

### 2.1 三种形态（靶场全部演示）

```csharp
// ── 形态 A · 注册表明文布尔值 ──
public static bool ReadFlagFromRegistry(string name)
{
    using (RegistryKey k = Registry.CurrentUser.OpenSubKey(@"Software\SeepLab\Pattern04"))
    {
        object v = k?.GetValue(name);
        return (v is int) && ((int)v != 0);      // ★ 读取后无完整性校验
    }
}
public static void FeatureGate_FromRegistry()
{
    bool isPro = ReadFlagFromRegistry("IsPro");  // ★ 权益判据来自用户可写位置
    Console.WriteLine(isPro ? "  [PRO] 已解锁" : "  [FREE] 已锁定");
}

// ── 形态 B · 配置文件明文字段 ──
public static void FeatureGate_FromConfig(string path)
{
    string content = File.ReadAllText(path);
    bool isPro = content.Contains("\"edition\": \"pro\"");   // ★ 明文匹配
    ...
}

// ── 形态 C · 环境变量 ──
public static void FeatureGate_FromEnv()
{
    string v = Environment.GetEnvironmentVariable("SEEPLAB_PRO");
    Console.WriteLine(v == "1" ? "  [PRO] 已解锁" : "  [FREE] 已锁定");
}
```

### 2.2 为什么这是缺陷

| 问题 | 后果 |
|:---|:---|
| **权益判据在用户可写位置** | 任何同用户进程都能改 |
| **读取后无完整性校验** | 改了就生效，客户端照单全收 |
| **无需触碰二进制** | 攻击成本极低（纯配置写入） |
| **明文存储** | 可用文本编辑器直接修改 |

> ### 🔑 核心教训
> **本地配置只能作为「用户偏好」，绝不能作为「权益判据」。**
>
> 判断标准很简单：
> **如果这个值被用户改了，厂商会损失利益吗？**
> 会 → 它就不该放在本地。

## 3. 二进制分析与点位特征

### 3.1 三种形态的定位特征

| 形态 | 定位特征 | 偏移（参考构建） |
|:---|:---|:---|
| **A 注册表** | UTF-16 字符串 `Software\SeepLab\Pattern04`、`IsPro` | `IsPro` @ `0x003fd0` |
| **B 配置文件** | ASCII/UTF-16 字符串 `edition`、`"pro"`、`"free"` | 搜索 `edition` |
| **C 环境变量** | UTF-16 字符串 `SEEPLAB_PRO` | `0x004146` |

### 3.2 关键观察

```
字符串 "IsPro" 在文件中出现 3 次：
  0x003fd0  ← 读取方法中的键名
  0x003ff8  ← 写入方法中的键名
  0x00403a  ← 初始化中的键名

→ 同一个键名在多个方法中重复出现，说明：
  ① 该键被多处读写 → 攻击面扩散
  ② 可通过字符串引用交叉定位全部相关方法
```

## 4. 完整点位表 ★

### 4.1 形态 A · 注册表（无需修改二进制）

| # | 操作 | 命令 / 位置 | 原始值 | 修改后 | 效果 |
|---:|:---|:---|:---|:---|:---|
| **P1** | 注册表写入 | `HKCU\Software\SeepLab\Pattern04` → `IsPro` | `0` (DWORD) | `1` (DWORD) | 🔴 **功能解锁** |

```powershell
# 攻击模拟（教学用）
reg add "HKCU\Software\SeepLab\Pattern04" /v IsPro /t REG_DWORD /d 1 /f
.\SeepLab.exe 04 | Select-String "阶段 1" -Context 0,3
```

> ⭐ **这是本模式最重要的教学点**：
> **完全不需要触碰二进制文件** —— 一次注册表写入即可改变功能行为。
> 这意味着**任何文件完整性校验机制都无法发现**。

### 4.2 形态 B · 配置文件（无需修改二进制）

| # | 文件 | 原始内容 | 修改后 | 效果 |
|---:|:---|:---|:---|:---|
| **P2** | `lab04.json` | `{ "edition": "free" }` | `{ "edition": "pro" }` | 🔴 **功能解锁** |

### 4.3 形态 C · 环境变量（无需修改二进制）

| # | 变量 | 原始 | 修改后 | 效果 |
|---:|:---|:---|:---|:---|
| **P3** | `SEEPLAB_PRO` | 未设置 | `1` | 🔴 **功能解锁** |

### 4.4 二进制修改点位（对照实验）

| # | 目标 | 偏移 | 原始字节 | 修补思路 | 效果 |
|---:|:---|:---|:---|:---|:---|
| **P4** | 注册表键名 | `0x003fd0` | `49 00 73 00 50 00 72 00 6F 00` | 改为不存在的键名 | 读取恒为空 → 功能**永久锁定** |
| **P5** | 配置字段名 | 搜索 `edition` | `65 00 64 00 69 00 ...` | 改为其他字段名 | 明文匹配恒失败 |

> 💡 **P4/P5 的价值**：它们演示了"**改键名 vs 改值**"的区别 ——
> * **改值**（P1/P2/P3）：攻击者做，成本极低
> * **改键名**（P4/P5）：防御者可做的**临时缓解**（让攻击者找不到键）
>
> **但这只是"隐蔽"，不是"安全"** —— 攻击者仍可通过字符串引用重新定位。

### 4.5 三种形态的对比 ★

| 维度 | 注册表 | 配置文件 | 环境变量 |
|:---|:---:|:---:|:---:|
| 攻击成本 | 极低 | 极低 | 极低 |
| 是否触碰二进制 | ❌ 否 | ❌ 否 | ❌ 否 |
| 文件完整性校验能否发现 | ❌ 不能 | ❌ 不能 | ❌ 不能 |
| 持久性 | 高（重启仍生效） | 高 | 中（会话级） |
| 审计难度 | 中（需查注册表） | 低（文本可读） | 中 |

> ### 🔑 核心结论
> **"配置层攻击"是文件完整性校验的盲区。**
> 无论二进制保护做得多好，只要权益判据存放在用户可写位置，
> 攻击者就能绕过全部二进制防护。

### 5.3 通用判定方法（★ 最重要的技能）

```
审计任何程序时，判断"权益判据是否在本地"的方法：

  1. 用 Process Monitor 监控程序的【全部文件与注册表访问】
  2. 找到程序【读取授权相关数据】的位置
  3. 问三个问题：
     ① 这个位置用户可写吗？
        → 可写 = 🔴 高危
     ② 读取后做了完整性校验吗？
        → 无校验 = 🔴 高危
     ③ 修改它会影响功能吗？
        → 会 = 确认是权益判据
```

**这个方法不依赖任何偏移，可套用于任何产品。**

## 9. 防御加固方案

### 9.1 核心原则

```
本地存储允许的用途          本地存储禁止的用途
─────────────────────      ─────────────────────
✅ 界面偏好（主题、语言）     ❌ 权益等级（是否 PRO）
✅ 窗口位置、大小            ❌ 授权到期时间
✅ 最近打开的文件            ❌ 功能开关状态
✅ 用户自定义快捷键          ❌ 试用剩余天数
```

### 9.2 正确实现

```csharp
// ❌ 反面：本地配置直接决定权益
bool isPro = ReadRegistryBool("IsPro");
if (isPro) EnableProFeatures();

// ✅ 正面：本地配置仅作偏好，权益判据来自签名凭据
public static bool TryExecutePro(string feature, Action action)
{
    // 本地配置只用于「用户偏好」，不参与权益判定
    if (!UserPrefs.EnableProUi) return false;

    // 权益判据：必须来自服务端签名凭据
    using (var cred = LicenseStore.LoadDecrypted())
    {
        if (cred == null) return false;
        if (!Ed25519.Verify(cred.Signature, cred.Payload, ServerPublicKey)) return false;
        if (!cred.Payload.MatchesDevice(DeviceFingerprint.Compute()))       return false;
        if (!cred.Payload.IsValidNow(MonotonicClock.Now))                   return false;
        if (!cred.Payload.Grants(feature))                                  return false;

        action();
        return true;
    }
}
```

### 9.3 若必须本地存储，需加完整性保护

```csharp
// ✅ 加密 + HMAC 保护本地状态
public static bool ReadProtectedFlag(string name)
{
    byte[] blob = ReadRaw(name);
    if (blob == null || blob.Length < 32) return false;

    // 分离载荷与 HMAC
    byte[] payload = Take(blob, 0, blob.Length - 32);
    byte[] mac     = Take(blob, blob.Length - 32, 32);

    // 校验 HMAC（密钥派生自设备指纹，不落盘）
    byte[] key = DeriveKeyFromDevice();
    byte[] expect = ComputeHmac(key, payload);
    if (!FixedTimeEquals(mac, expect)) return false;      // 被篡改 → 拒绝

    return payload[0] != 0;
}
```

> ⚠️ **注意**：即使加了 HMAC，如果**密钥派生自本机信息**，
> 攻击者仍可能在同一台机器上重算 HMAC。
> **因此这只是"提高成本"，不是"根除"。**

### 9.4 加固优先级

```
第一优先（架构级，必须做）
  └─ 权益判据改为服务端签名凭据                ← 消除"本地判据"本身

第二优先（成本低）
  ├─ 本地存储仅保留「用户偏好」类数据
  └─ 移除所有以本地配置作为权益判据的代码路径

第三优先（提高成本）
  ├─ 本地状态加密 + HMAC 保护
  └─ 密钥派生绑定设备指纹（注意：非根本解）
```
