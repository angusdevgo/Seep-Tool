## 2. 缺陷成因（源码层）

### 2.1 缺陷核心

```csharp
// ★ DEFECT-01：授权状态 —— 静态、可写、明文、无完整性保护
public static bool g_license_state = false;

// ★ DEFECT-02：Fail-Open —— 凭据为空被当作"无需校验"
public static void LoadLicense(string credential)
{
    if (string.IsNullOrEmpty(credential))
    {
        g_license_state = true;          // ← 免检通道
        return;
    }
    // ★ DEFECT-03：本地校验，无服务端参与
    if (credential.StartsWith("LAB-"))
        g_license_state = true;
    else
        g_license_state = false;
}
```

### 2.2 扩散效应：3 处读取点

```csharp
public static void ProFeatureA()
{
    if (g_license_state)                 // ← 读取点 #1
        Console.WriteLine("  [PRO-A] 高级功能 A 已解锁：批量导出");
}

public static void ProFeatureB()
{
    if (g_license_state)                 // ← 读取点 #2
        Console.WriteLine("  [PRO-B] 高级功能 B 已解锁：离线 OCR");
}

public static void PrintStatus()
{
    string edition = g_license_state ? "PROFESSIONAL" : "TRIAL";   // ← 读取点 #3
    Console.WriteLine("  [UI]    当前版本 = " + edition + " Edition");
}
```

### 2.3 为什么这是缺陷

| 问题 | 后果 |
|:---|:---|
| **单一真相源** | 全部特权由 1 个布尔量决定 → 改 1 处 = 解锁全部 |
| **明文可写** | 无校验和、无加密 → 可被内存扫描直接定位 |
| **判定与业务解耦** | `if (g_license_state)` 与业务实现之间有清晰边界 |
| **无服务端参与** | 客户端既是运动员又是裁判 |

> ### 🔑 核心教训
> **单点布尔裁决 = 把授权开关直接暴露在进程内存里。**
> 攻击者不需要理解任何业务逻辑，只需翻转 1 个 bit。

## 3. 二进制分析（参考构建）

### 3.1 关键字符串常量偏移

| 字符串 | 编码 | 文件偏移 | 用途 |
|:---|:---|:---|:---|
| `TRIAL` | UTF-16LE | `0x003212` | 未授权时的版本名 |
| `PROFESSIONAL` | UTF-16LE | `0x00321e` | 已授权时的版本名 |
| `LAB-` | UTF-16LE | `0x0030c4` | 本地校验前缀（★ 弱校验特征） |

> 💡 **观察点**：`TRIAL` 与 `PROFESSIONAL` 在文件中仅相隔 12 字节
> （`0x00321e - 0x003212 = 12` = 5 个字符 × 2 字节 + 2 字节终止符），
> 说明它们是**同一处三元表达式**的两个分支常量 —— 这直接指向 `PrintStatus()`。

### 3.2 方法元数据偏移（.NET 元数据字符串，UTF-8）

| 方法名 | 元数据偏移 |
|:---|:---|
| `g_license_state` | `0x00204c` |
| `LoadLicense` | `0x00205c` |
| `ProFeatureA` | `0x002068` |
| `ProFeatureB` | `0x002074` |
| `PrintStatus` | `0x002080` |

> 💡 **观察点**：这 5 个名字在元数据中**连续排列**且间隔固定（12 字节），
> 说明它们是同一个类的成员 —— 攻击者只需找到第一个，就能顺藤摸瓜找出全部。

### 3.3 判定指令的特征形态

在 IL 层面，`if (g_license_state)` 会被编译为：

```il
ldsfld     bool SeepLab.Pattern01::g_license_state    // 读取静态字段
brfalse.s  LABEL_FREE                                  // 为零则跳到 FREE 分支
// fall-through = PRO 分支
```

关键特征：**`ldsfld` + `brfalse` 的固定组合**。
这就是"单点布尔裁决"在二进制中的**指纹**。

## 4. 完整点位表 ★

> 下表针对**参考构建**（SHA256 `5218d0e8…`）。
> 若是其他构建，请用 §5 的方法重新定位。

### 4.1 字符串常量点位（可直接用 HxD 十六进制编辑）

| # | 文件偏移 | 功能 | 原始字节 | 修补字节 | 效果 |
|---:|:---|:---|:---|:---|:---|
| **P1** | `0x003212` | 版本名显示 | `54 00 52 00 49 00 41 00 4C 00` | `50 00 52 00 4F 00 20 00 00 00` | 界面强制显示 `PRO` |
| **P2** | `0x0030c4` | 校验前缀 | `4C 00 41 00 42 00 2D 00` | `58 00 58 00 58 00 2D 00` | 改变校验前缀（观察行为变化） |

> ⚠️ **P1 说明**：`TRIAL`（5 字符）比 `PROFESSIONAL`（12 字符）短，
> 因此修补时需用 `PRO`（3 字符）+ 终止符，或改用其他等长字符串。
> **等长替换是二进制修补的第一原则** —— 超过原长度会破坏后续数据结构。

### 4.2 IL 指令点位（需用 dnSpy / ILSpy 定位）

| # | 目标方法 | 指令特征 | 原始 IL | 修补思路 | 效果 |
|---:|:---|:---|:---|:---|:---|
| **P3** | `LoadLicense` | `ldc.i4.1` + `stsfld g_license_state` | `17 80 xx xx xx xx` | 分支改写为无条件写入 | 强制授权通过 |
| **P4** | `LoadLicense` | `brfalse.s`（空值分支） | `2C xx` | 改为 `br.s`（无条件跳过） | 消除 Fail-Open 通道 |
| **P5** | `ProFeatureA/B` | `ldsfld g_license_state` + `brfalse.s` | `7E xx xx xx xx 2C xx` | `brfalse.s` → `pop` + `nop` | 强制走 PRO 分支 |

> 💡 **P3/P4 的关键区别**：
> * **P3（改数据）**：改的是"授权状态写入什么值" → 需要每次启动都写
> * **P4（改控制流）**：改的是"走哪条分支" → 效果更彻底
> * **P5（改消费端）**：改的是"读取点怎么判断" → 需改 3 处（对应 3 个读取点）

### 4.3 三种改法的对比实验 ★

这是靶场最重要的教学点 —— **务必亲手试一遍**：

| 改法 | 改几处 | 效果 | 教学结论 |
|:---|:---:|:---|:---|
| **改 P1**（字符串） | 1 处 | 仅界面显示变化，功能仍锁定 | ❌ **改 UI ≠ 改权益** |
| **改 P3/P4**（写入端） | 1 处 | 全功能解锁 | ✅ 攻击**决策源头**最省力 |
| **改 P5**（读取端） | **3 处** | 全功能解锁，但需改 3 个点 | ⚠️ 改**消费端**成本高 |

> ### 🔑 核心结论
> **改"决策源头"（1 处）远比改"决策消费端"（3 处）省力。**
> 这正是「单点布尔裁决」致命的根本原因 —— **只有一个源头可攻击**。
>
> 反之，**防御方向**就是：**消除单点源头**，把判定分散到多个不相关的路径。

### 5.3 定位 IL 判定指令（推荐工具：dnSpy）

```
1. 用 dnSpy 打开 SeepLab.exe
2. 展开 SeepLab → Pattern01
3. 双击 LoadLicense → 右上角切换视图为 "IL"

5. 右键 → "编辑 IL 指令" → 修改后保存
```

**判定指令的通用识别特征**：

| 模式 | 含义 | 对应源码 |
|:---|:---|:---|
| `ldsfld` + `brfalse[.s]` | 读取静态字段，为零则跳转 | `if (g_state) {...}` |
| `ldloc` + `brfalse[.s]` | 读取局部变量，为零则跳转 | `if (localVar) {...}` |
| `call` + `brtrue[.s]` | 调用方法，非零则跳转 | `if (IsPro()) {...}` |
| `ldc.i4.1` + `stsfld` | 写入常量 1 到静态字段 | `g_state = true;` |

**预期对照**：

| 状态 | `[UI]` 输出 | `[FREE]/[PRO-]` 输出 |
|:---|:---|:---|
| 原始 | `TRIAL Edition` | `FREE`（锁定） |
| 改 P1 后 | `PRO Edition` | **仍为 `FREE`** ← 关键教学点 |
| 改 P3/P4 后 | `PROFESSIONAL Edition` | `PRO`（解锁） |

> 💡 **对照实验的价值**：改字符串只改了"显示"，改控制流才改"权益"。
> **这个区别在真实产品审计中极其重要** —— 很多初学者的误区就是
> "改了界面提示以为成功了，其实权益闸门根本没动"。

## 9. 防御加固方案

### 9.1 消除单点状态

```csharp
// ❌ 反面：静态可写状态
public static bool g_license_state = false;
if (g_license_state) { DoPro(); }

// ✅ 正面：凭据驱动 + 每次重新验签 + 校验与执行合一
public static bool TryExecutePro(string feature, Action action)
{
    using (var cred = LicenseStore.LoadDecrypted())
    {
        if (cred == null) return false;
        if (!Ed25519.Verify(cred.Signature, cred.Payload, ServerPublicKey)) return false;
        if (!cred.Payload.MatchesDevice(DeviceFingerprint.Compute()))       return false;
        if (!cred.Payload.IsValidNow(MonotonicClock.Now))                   return false;
        if (!cred.Payload.Grants(feature))                                  return false;

        action();                       // 无独立判定出口，无中间状态
        return true;
    }
}
```

### 9.2 消除 Fail-Open 通道

```csharp
// ❌ 反面
if (string.IsNullOrEmpty(credential)) return true;   // 空值即通过

// ✅ 正面（Fail-Closed）
if (string.IsNullOrWhiteSpace(credential)
    || credential == "null") return false;           // 空值一律拒绝
```

### 9.3 加固优先级

```
第一优先（架构级）
  └─ 取消静态可写状态，改为凭据驱动              ← 消除单点源头

第二优先（成本低）
  └─ 空值分支改为 Fail-Closed                    ← 消除免检通道

第三优先（提高成本）
  ├─ 关键判定控制流平坦化
  └─ 二进制完整性自检
```
