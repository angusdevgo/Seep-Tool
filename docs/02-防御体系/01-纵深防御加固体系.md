# 03 · 纵深防御加固体系

> 本文给出**三层纵深防御架构（Defense-in-Depth）**的工程落地指南。
> 核心原则：**架构修正为主，运行时防护为辅，混淆提高成本。**

---

## 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│  第一层 · 传输与权威层 (Server-Side Authority)                     │
│    目标：从架构上根除"客户端裁决"缺陷                                │
│    ────────────────────────────────────────────────────────────  │
│    • 服务端权威原则：核心权益由服务端签发并二次验签                     │
│    • 非对称签名：Ed25519 离线许可证，私钥永不离线                     │
│    • 传输安全：双向 mTLS + 证书绑定 + 时戳 Nonce 防重放               │
├──────────────────────────────────────────────────────────────────┤
│  第二层 · 环境与运行时层 (Runtime Integrity)                       │
│    目标：提高动态篡改与注入的成本                                     │
│    ────────────────────────────────────────────────────────────  │
│    • DLL 加载路径白名单 (SetDefaultDllDirectories)                 │
│    • 二进制 Authenticode 签名运行时复核                             │
│    • 敏感内存加密存储 + 用毕即时擦除                                 │
│    • IPC 消息 HMAC 认证 + 对端进程身份校验                           │
├──────────────────────────────────────────────────────────────────┤
│  第三层 · 代码形态与混淆层 (Obfuscation)                            │
│    目标：提高静态分析与定位的成本                                     │
│    ────────────────────────────────────────────────────────────  │
│    • 控制流平坦化 (Control Flow Flattening)                        │
│    • 关键逻辑代码虚拟化 (VMP)                                       │
│    • 符号剥离 + 敏感字符串动态解密                                    │
└──────────────────────────────────────────────────────────────────┘
```

> ⚠️ **重要认知**：三层是**递进关系**，不是**并列关系**。
> 第一层是**必需**的（架构修正）；第二、三层是**辅助**的（提高成本）。
> **只用第二三层、不做第一层修正的产品，依然存在 CWE-602 缺陷。**

---

## 第一层 · 传输与权威层

### 1.1 服务端权威原则（Server-Side Authority）

**核心思想**：客户端只能"**持有并呈递**"凭据，不能"**决定**"权益。

| 错误做法 | 正确做法 |
|:---|:---|
| 客户端本地计算授权等级 | 服务端签发**签名凭据**，客户端仅验签 |
| 客户端缓存布尔授权状态 | 每次使用前**重新验签** |
| 离线时信任本地状态 | 离线凭据带**有效期**，超期强制联网复核 |
| 关键权益纯本地解锁 | 关键操作需**服务端异步二次确认** |

**决策矩阵**：

| 功能类型 | 推荐策略 |
|:---|:---|
| 低频关键权益（如导出、发布） | 🔒 **强制服务端在线确认** |
| 高频日常功能（如快捷键、基础编辑） | 🔑 离线签名凭据 + 有效期 |
| 纯展示类功能 | 🆓 无需鉴权 |

### 1.2 非对称签名体系

**必须使用标准算法，禁止自研。**

| 算法 | 密钥长度 | 签名长度 | 适用场景 |
|:---|:---|:---|:---|
| **Ed25519** | 32 字节 | 64 字节 | ✅ **首选**：快、短、安全 |
| ECDSA P-256 | 32 字节 | ~72 字节 | 需要 NIST 合规时 |
| RSA-PSS 3072 | 384 字节 | 384 字节 | 遗留系统兼容 |

**私钥保管要求**：

```
┌─────────────────────────────────────────────┐
│  服务端私钥保管（三级安全要求）                │
├─────────────────────────────────────────────┤
│  L1  离线签名机（物理隔离，永不联网）           │
│  L2  HSM 硬件安全模块（推荐用于批量签发）       │
│  L3  密钥分片存储（Shamir 秘密共享，多人授权）   │
└─────────────────────────────────────────────┘
```

**绝对禁止**：
- ❌ 私钥写入任何客户端代码或配置
- ❌ 私钥提交到版本控制系统
- ❌ 私钥出现在日志、异常堆栈或内存转储中

> 📖 完整实现见 [04 · Ed25519 离线许可体系设计](02-Ed25519离线许可体系设计.md)

### 1.3 传输安全

| 措施 | 说明 |
|:---|:---|
| **HTTPS 强制** | 禁用 HTTP 回退，启用 HSTS |
| **证书绑定（Certificate Pinning）** | 防止中间人劫持 |
| **双向 mTLS** | 客户端与服务端互相验证证书 |
| **请求签名** | 每个请求携带 `HMAC(请求体 + 时戳 + Nonce)` |
| **防重放** | 服务端维护 Nonce 缓存，拒绝重复请求 |
| **响应签名** | 关键响应由服务端签名，客户端验签 |

## 第二层 · 环境与运行时层

### 2.1 DLL 加载安全

```cpp
// 启动首行必须执行
SetDefaultDllDirectories(
    LOAD_LIBRARY_SEARCH_SYSTEM32 |
    LOAD_LIBRARY_SEARCH_APPLICATION_DIR);

// 加载第三方库时使用绝对路径 + 签名校验
HMODULE LoadSecureLibrary(const std::wstring& absPath)
{
    // 1. 校验签名
    if (!VerifyAuthenticode(absPath)) return nullptr;

    // 2. 绝对路径加载
    return LoadLibraryExW(absPath.c_str(), nullptr,
                          LOAD_LIBRARY_SEARCH_SYSTEM32);
}
```

**检查清单**：
- [ ] 是否存在裸 `LoadLibrary` 调用
- [ ] 是否调用了 `SetDefaultDllDirectories`
- [ ] 是否校验了加载模块的签名
- [ ] 是否使用了相对路径或仅文件名加载

### 2.2 二进制完整性自检

```csharp
// 运行时自校验（防止内存补丁）
public static bool VerifySelfIntegrity()
{
    // 1. 读取自身磁盘镜像的 Authenticode 签名
    var selfPath = Process.GetCurrentProcess().MainModule.FileName;
    if (!WinVerifyTrust(selfPath)) return false;

    // 2. 计算关键代码段哈希，与编译期预置值比对
    var codeHash = ComputeCodeSectionHash(selfPath);
    if (!CryptographicOperations.FixedTimeEquals(codeHash, ExpectedCodeHash))
        return false;

    return true;
}

// 建议：在多个不相关的时机重复调用（启动、关键操作前、定时）
```

### 2.3 敏感内存保护

| 技术 | 说明 |
|:---|:---|
| **加密存储** | 敏感数据在堆中以会话密钥加密 |
| **用毕擦除** | 使用 `CryptographicOperations.ZeroMemory` 立即清零 |
| **禁止分页** | `VirtualLock` 防止敏感页写入磁盘 |
| **访问监控** | 对敏感内存页设置 `PAGE_GUARD` 检测越权读取 |
| **不缓存布尔结果** | 每次查询重新验签，不存储中间状态 |

```csharp
// 正确用法示例
using (var buffer = new SecureBuffer(1024))
{
    // 敏感数据操作
    ProcessSensitiveData(buffer.Span);
    // 离开作用域时自动 ZeroMemory
}
```

### 2.4 IPC 安全

```csharp
// 命名管道加固三要素
var pipe = new NamedPipeServerStream(
    pipeName,
    PipeDirection.InOut,
    1,
    PipeTransmissionMode.Byte,
    PipeOptions.WriteThrough);

// 1. 设置 ACL，仅当前用户可访问
SetPipeSecurity(pipe, WindowsIdentity.GetCurrent().User);

// 2. 校验对端进程身份
if (!VerifyPeerProcess(pipe)) return;

// 3. 消息级 HMAC 认证
var (payload, mac) = ReadFramed(pipe);
if (!VerifyHMAC(payload, mac, sessionKey)) return;
```

## 第三层 · 代码形态与混淆层

> ⚠️ **再次强调**：本层是**成本提升手段**，**不能替代**架构修正。

### 3.1 控制流平坦化（Control Flow Flattening）

将线性控制流转换为**状态机 + 分发器**结构，消除可读的 `if/else` 分支模式。

```cpp
// 混淆前：清晰的判定分支
if (IsLicensed()) { EnablePro(); }
else { ShowTrial(); }

// 混淆后：状态机分发（示意）
while (state != END) {
    switch (dispatcher[state]) {
        case 0x3F2A: state = cond ? 0x11B4 : 0x9C07; break;
        case 0x11B4: EnablePro(); state = END; break;
        case 0x9C07: ShowTrial(); state = END; break;
        // ... 大量虚假分支
    }
}
```

**效果**：消除显式的 `cmp/test + jz` 模式，静态分析难度大幅上升。

### 3.2 代码虚拟化（VMP）

将关键逻辑编译为**自定义字节码**，由内置虚拟机解释执行。

| 优势 | 代价 |
|:---|:---|
| 分析难度最高 | 性能下降 10~100 倍 |
| 逻辑不可直接反编译 | 增加二进制体积 |
| 平台无关 | 兼容性问题（杀软误报） |

**适用建议**：
- ✅ 仅对**授权校验核心逻辑**使用（不要全程序虚拟化）
- ✅ 配合**反调试**使用
- ❌ 不要对性能敏感的算法使用

### 3.3 符号与字符串保护

```csharp
// ❌ 反例：明文符号与字符串
public static bool IsLicensed() { ... }

// ✅ 正例：剥离符号 + 字符串动态解密
private static bool a1()   // 无意义名称
{
    // 字符串运行时解密，不留在二进制中
    var msg = DecryptString(new byte[] { 0x3A, 0x7F, ... });
    ...
}
```

**措施清单**：
- [ ] 剥离调试符号（Release 构建）
- [ ] 移除有意义的函数/变量名
- [ ] 敏感字符串加密存储，运行时解密
- [ ] 移除异常堆栈中的敏感信息
- [ ] 禁用反射元数据（如适用）

## 反调试与反注入

| 技术 | 说明 | 注意事项 |
|:---|:---|:---|
| **PEB 调试标志检查** | 检测 `BeingDebugged` | 易被绕过，需多点检测 |
| **时间差检测** | 检测调试器导致的时间异常 | 可能误报（虚拟机、低配机） |
| **硬件断点检测** | 检查调试寄存器 | 需处理异常 |
| **内存断点检测** | 检查代码段完整性 | 需处理自修改代码 |
| **父进程校验** | 校验启动者身份 | 可能影响正常集成场景 |

> ⚠️ **反调试的定位**：它是**成本提升手段**，不是安全边界。
> 有决心的攻击者一定能绕过。**真正的安全来自第一层的架构修正。**

## 落地路线图

建议按以下阶段推进加固：

```
阶段 1（1~2 周）· 低成本高收益
  ├─ SetDefaultDllDirectories           ← 修复 CWE-427
  ├─ IPC 消息 HMAC 认证                  ← 修复 CWE-311
  └─ 敏感内存用毕擦除                     ← 降低泄露面

阶段 2（1~2 月）· 架构修正
  ├─ 迁移至 Ed25519 非对称签名            ← 修复 CWE-321/327
  ├─ 判定逻辑内联化                       ← 修复 CWE-602
  └─ 取消独立布尔判定出口                  ← 修复 CWE-602

阶段 3（持续）· 纵深加固
  ├─ 二进制完整性自检
  ├─ 控制流平坦化
  └─ 关键逻辑 VMP 保护
```
